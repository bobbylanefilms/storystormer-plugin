# StoryStormer · Migrate

You are moving a story from the store it lives in now (the **source**) to another backend the author chooses (the **target**). Everything goes through `references/store.md`: the source is read through its binding, the target is written through its binding, and nothing here names a backend’s tools. The source is never modified, and this skill never offers to delete it; the author deletes it by hand once they are satisfied, and the report says where it is.

Always follow `references/plan-first.md`. The **preflight is the plan**: nothing is created on the target until the author has seen it and said go.

## What you produce

- The project on the target: every document the target can hold, written through its binding in canonical order, with the target’s own `storage` block in its config and `storage_kind` in its `state.md`.
- The **flip**: the one write outside the target, the open folder’s `.storystormer/config.json` `storage` block, so the next session resolves to the new home (§ Verify, then flip).
- A report: counts by category, anything stored as unmapped on the target, anything skipped and why, where the untouched source is, and how to go back.

## Source and target

**Source** is the session’s binding, resolved per `store.md` § Resolve. In a hybrid session (a Dropbox project bound locally through `local_root`), the source is that Dropbox project, read through the local binding, which is the fast path to the same files.

**Target** options are init’s (`storystormer-init` § Where a new project lives): this folder, when there is an open folder; and each backend in `store.md` § Bindings that is not pending and whose binding’s tool check passes. Leave out the source’s own kind (both `local` and `dropbox` in a hybrid session, since they are the same files). With one option left, name it and confirm; with none, say why each backend is unavailable (pending, connector missing, it is the source, no open folder) and stop. After a completed move the session resolves to the new home, so the old kind is an ordinary target again (a move back: § Same slug recognizes the copy the earlier move left there and offers a plain flip when it still matches, else the refusal and merge); a completed move is never re-copied to the home it already reached.

**The slug** is the source’s: the Dropbox folder name, the Notion row’s `Slug`, or for a local project the folder’s name in kebab case, NFC (the title’s kebab case when the folder name won’t serve). The preflight names it; the author can change it. Validate it, whoever chose it (a Notion source’s `Slug` included): kebab case, `[a-z0-9-]` only, NFC, no `/`, no `..`, no leading dot. Anything else, ask for a slug that passes rather than repair it silently.

**A local target** is the open folder. It may hold nothing but the pointer config that sends the session to the source (and OS clutter); anything else is named, and the author is asked before anything is written into it. A folder holding a full config is an existing project (§ Same slug), and another slug can’t help, since the destination is the folder itself: offer to merge into it, or to open or choose another folder and run `migrate` there.

## The preflight (the plan)

`store.list('**')` on the source, then work out, without writing anything:

- **Counts by category:** canon (`characters/`, `worldbuilding/`), story documents (`primer.md`, `treatment.md`, `manifest.md`, `series.md`, `voice/`, `research/`), `outline/`, chapters (folders and artifacts), the logs (decision and question **entries**, not just two files: read `decisions.md` and `questions.md` to count them; a log the source doesn’t have counts as zero entries, not an error), snapshots (`.storystormer/history/` folders and each chapter’s `.history/`), the init archive (§ What happens to each item), and everything else. A series counts the shared root, then each book. The plan shows every category with its count, zero included (“init archive: none found”), so an empty category is visible to the author rather than silently absent.
- **The inventory, cross-checked.** Check the listing against an independent count where the source binding offers one, and for completeness where it offers only that (its `list` realization says which): on Notion, the root row’s relation lists are a second count for its rows, while its child pages are only checked for completeness (the row’s fetch whole, every tag mapped); on Dropbox, `has_more` paged to its end, and on a folder the listing’s count check, are completeness signals, not a second count. A shortfall is listed again, never planned around: the copy and the verification both work from this inventory, so a gap here would balance on both sides and pass unseen.
- **What normalization will change**, when the target’s binding normalizes author markup on the way in (its § Rendering): read each markdown document and count, by file and by construct, what `references/markdown-profile.md` § Rewrite table will rewrite (count non-breaking spaces by byte, U+00A0, never by eye: a read shows them as spaces, and a live run’s normalizers reported none in two files holding 36) (`primer.md`: 1 HTML table → pipe table; `chapters/chapter-03/ch03-prose.md`: 14 two-space line breaks → bare newlines), plus, listed apart, any construct the profile puts under No in-profile form, which the target changes and nothing keeps, and every bare filename or path whose entity the target decodes (`The_Good_Dog_-_Brainstorming_&amp;_Future_Plot_Points.md` → `…_&_…`: the profile’s § Kept as written), since after the move the text no longer names the real file. Documents already in the profile change nothing and are counted as such. Past `references/subagent-pattern.md` § When to dispatch’s threshold, counting subagents do these reads, one per category, read-only, with the rewrite table and the two lists pasted as the copy briefs carry them, and return counts by file and construct only, never document text, so the main session’s window holds the plan, not the project. Approving the plan approves these rewrites; the source is never changed.
- **What Exists text that won’t survive.** Every target recomputes `state.md`’s What Exists (the table below), so read that section in each source `state.md` and sort what is in it. **Computed lines:** the first `- **<Label>** — …` line for each label `file-schemas.md` § `state.md` lists (or the series form’s lines), one line per label; the target recomputes them, so say once that their own prose is replaced by the recomputed form. **Carried lines:** a `- **<Label>** — …` line whose label names documents the project holds but isn’t a computed label (`**Research**`, `**Handoff**`, `**Methodology**`); the target keeps it as written (`file-schemas.md` § `state.md`, update rules; on Notion, the binding’s carried lines). **Everything else is dropped:** a second line with a label already seen (a repeated `- **Prose chapters** —`), a sub-bullet under a line, a free paragraph, a retained earlier count line. Name each dropped piece by its first few words and its word count, and say the source keeps it. With none, say so.
- **Computed documents with the author’s own text.** Where the target computes `characters/_index.md`, `outline/_index.md` or `voice/README.md` (the table below), the source’s copy is replaced by the target’s rendering. Compare each source copy with what the target will compute from the same documents, and name any text the rendering won’t hold (an index’s hand-written notes, a tier or one-liner column, a “Not yet written” list) by its first few words and its word count; say the source keeps it. With none, say so.
- **Damaged rows** (a Notion source): any row whose `Meta` the binding reports as damaged (`references/store/notion.md` § Frontmatter ↔ properties, rows stored in the earlier form) is named with its note: its frontmatter crosses as the typed properties render it, and its source frontmatter can’t be recovered from Notion.
- **What happens to each**, by the table below: copied, mapped to the target’s realization, computed by the target, stored as unmapped, or skipped (with the reason and the paths).
- **Same slug** on the target (§ Same slug): clear, or the refusal and its merge prompt, or a recognized unfinished or flip-pending earlier run.
- **Names the target can’t keep apart.** On Dropbox, whose paths are case-insensitive and must be NFC (`references/store/dropbox.md` § Quirks), list any source paths that differ only by case and any names not in NFC; on a local target on a case-insensitive filesystem (macOS’s default), list the paths that differ only by case (NFC is Dropbox’s rule, not checked here). Either way, stop for the author’s call (rename in the source, or skip one) rather than collide mid-run.
- **Where it will live** (the Dropbox path, the Notion hub and whether a new hub and tables are created, or this folder) and **what the flip will write** into the open folder, or that there is no open folder to flip.
- **Call volume**, estimated from the counts and the target’s capabilities line, roughly: on a local target, one write per document; on Dropbox (`write: delete-create`), one create per document plus one per new folder, and about four calls and 20 seconds for each document an overwrite replaces (delete, one poll, create, and a verify read, as observed); on Notion, three to four per document (create, the async poll, a second content call when the body opens with an H1 (`# `), and the read-back, § Copy), the log entries in batches (one create carries several rows; a live run sent 68 decisions in 10 creates) with their numbering checks, plus about ten for a new hub. Add the source’s reads: one per document, two on Notion, and into Notion the preflight’s reads for the normalization count. A 150-document project with 200 log entries is on the order of five hundred calls into Notion and a couple of hundred into Dropbox; a live run of 97 documents and 109 entries took about 310 Notion calls and over an hour. Into Notion, the config’s last write is usually a no-op: its fields are the Projects row’s properties, set at scaffolding, so it writes only what changed since. Moving back to a copy left behind normalizes that copy’s documents to compare them (§ Same slug), model work that takes minutes on a project of a hundred documents; count it in the estimate. Say plainly that a big project takes a while, that an interrupted run resumes by running `migrate` again (identical writes are no-ops), and that edits made elsewhere during the move land only in the source.

Then wait for the author’s go. That approval is the confirmation for every mutation in the run (`store.md` § Confirmation posture), on every binding.

| Item | Target with `history: snapshots` (local, Dropbox) | Target that computes documents (Notion) |
|---|---|---|
| Canon, story documents, outline, chapter artifacts and scenes (`.md`) | copied, path for path | rows per the binding’s path map |
| `decisions.md`, `questions.md` | copied, one write each | one row per entry through the binding’s writable realizations, each keeping its own number (`references/store/notion.md` § IDs, imports: the number is set to the entry’s own when free, so a gap such as D-001, D-003 stays a gap and chapters citing D-003 still point at it); decisions before questions, so a `resolved (D-###)` can link its row; `Superseded by` links set once both rows exist. Each entry keeps its exact text (extra fields, status prose, header suffixes, values outside the selects: the binding’s § Stored and computed, log entries), and each log’s frontmatter and preamble go to the Projects row’s `Decisions Head` or `Questions Head`. From then on the document is the rendering of those rows |
| `state.md` (root, and each book’s) | written last by the main session: `storage_kind` = the target’s kind, What Exists recomputed from what the target holds (its carried lines kept as written, anything else dropped, as the plan named), the Storage line per `file-schemas.md` § `state.md` (a source’s line is dropped where it no longer applies) | frontmatter → the Projects row (created first, at scaffolding, since every other row relates to it, **with no page content**); the rest of the body (an opening H1, `## Summary`, `## What's Next`, `## Last Session` and any other section, in order) → the row’s content, last, in order; What Exists’ carried lines go to the row (the binding computes the rest) |
| `.storystormer/config.json` | written last, the source’s fields with the target’s `storage` block (a field the config mirrors from `state.md`, such as the title, that disagrees with it is named in the preflight: Notion keeps one value, `state.md`’s); on a merge into a series, `books` is merged (target-only books kept, the source’s added or updated), never replaced wholesale | root fields → Projects properties (a series’ `books` → book rows, set at scaffolding; on a merge, the same merged `books`, so the realization never sees a book removed); `storage` is never written (the row is Notion’s) |
| `characters/_index.md`, `outline/_index.md`, `voice/README.md` | copied | not copied: the target computes them |
| `.storystormer/history/**`, `chapters/*/.history/**` (snapshots) | copied as they are | **skipped**, counted, and left in the source. Notion keeps its own page history from the moment each row is created, so those snapshot files stay the only record of versions before the move; the report says so |
| `.storystormer/history/<timestamp>-init/` (init’s intake archive on a snapshots store) | copied with the snapshots | its markdown re-filed to `.storystormer/intake/<timestamp>/` (the folder name without `-init`, each file’s path inside the folder kept: the binding’s § Scaffolding, step 5), where init files the archive on such a store; child pages, reported as unmapped |
| `.storystormer/intake/<timestamp>/` holding an init archive (`intake-original-names.md`, `superseded-prose/`; an older init filed it as `originals/` and `superseded/`, which counts too), as a store that computes documents files it | re-filed to `.storystormer/history/<timestamp>-init/`, subpaths kept, where init files it on a snapshots store, so a project that went to Notion and comes back has its archive where it started | copied |
| `.storystormer/intake/**` (other than an init archive), `.storystormer/canon-sync/*.md`, `kitbash/`, other `.md` outside the path map | copied | child pages titled with the path (the binding’s unmapped-path rule), listed in the report as stored as unmapped |
| `.storystormer/genre-reference.md` | copied | its Assets row |
| Text that isn’t markdown (`.txt`, `.fountain`, `.py`, a `.json` other than the config) | copied as is | **skipped** and named: the binding holds markdown only and normalizes it as markdown, so the file would not come back as it went in |
| Binary files (`.docx`, images, PDFs) | **skipped** and named on every target: the store operations carry text, so no binding can copy one. They stay in the source; the author can carry them over by hand where the target is a folder |
| OS and tool clutter (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `._*`, `.git/`) | never copied, never listed one by one; the report gives a count |

**From a store that computes documents** (Notion → a folder or Dropbox), each rendered read is written as a stored file: `decisions.md` and `questions.md` as the rendered logs, the indexes and `voice/README.md` as rendered, child pages as files at their path titles, `.storystormer/intake/**` as ordinary files (an init archive among them re-filed per the table). The rendered config is written with its `storage` block replaced by the target’s, and `state.md` with `storage_kind` replaced. **A second rendering of every frontmatter.** Nothing on the target checks a rendering, so each document’s frontmatter is rendered twice, by the copy subagent from its read and, independently, by another agent (or the main session): a row’s from a rows query of the same rows (properties and `Meta` only: about one query per hundred rows), a child page’s from a second fetch of that page (its frontmatter is the `yaml` fence at the top of its body, `references/store/notion.md` § Frontmatter ↔ properties, Child pages). The checking agent compares its rendering with the file as written (or its read-back), and the two must match exactly, the one empty line after the frontmatter included when the document has a body; any difference is a `mismatch` on that document (*observed (2026-10-24)*: without it, a quoting slip on `act: 1` in four chapter files and a lost empty line after a style guide’s frontmatter crossed unseen). A document that entered Notion through its normalization comes back in profile form, exactly as it was sent; text an author wrote in Notion, or that reached it before that normalization, comes back in Notion’s form (`references/store/notion.md` § Rendering, Known limit), and the report says so once.

## Same slug

Use the target binding’s own § Locate and § Scaffolding checks: on Dropbox, a `/StoryStormer/<slug>` folder holding a config (the raw listing, compared case-insensitively); on Notion, a Projects row with that `Slug` in the chosen hub; on a local target, a full config in the open folder.

- **Clear:** go on. On Notion, after the go, run the binding’s § Scaffolding steps 1–2 only as needed (a hub and tables when there is no hub) and step 3 always (the Projects row, and every book row in a series), created from the frontmatter and config fields with no page content; Dropbox runs its steps 1–2 (slug check, folders).
- **Taken:** refuse, say what is there (its title, stage and last session from that project’s `state.md`), and ask whether the author meant to **merge** into it or to pick another slug. Don’t guess.
- **An unfinished earlier run of this migration:** the target holds the slug but no config (a stored target) or a Projects row with no content (Notion), every document it holds is the target path of a source path under this skill’s own mapping (the table above, the init archive’s re-filing included: a Notion target holds `.storystormer/intake/<timestamp>/…` for a local `.storystormer/history/<timestamp>-init/…`, and the other way round), and each matches the source’s exactly (the target binding’s rendered read against the source document, in its normalized form when the target normalizes: § Copy, the normalized form) or is one of the per-document cases named there (a construct with no in-profile form; a document that differs since, such as one an interrupted run left mismatched or half-written). Those are listed and shown to the author, both versions, and the resume rewrites them. A target `state.md` (written just before the config, so present when a run stopped between them) matches when it differs from the source’s only by the migration’s own transforms: `storage_kind`, What Exists, and the Storage line. Say so and offer to **resume**: a merge into that folder or row with nothing to conflict, where every identical write is a no-op. A configless folder or content-less row that doesn’t fit this (it holds a path the source doesn’t, or the author doesn’t recognize the differences shown) is someone else’s; ask before writing into it, as the binding does.
- **Complete, flip pending:** the same, but the target’s config and `state.md` were written (the run stopped between them and the flip). It is not taken: say so and offer to finish, which re-runs verification (§ Verify, then flip) and does the flip.
- **The copy an earlier move left behind** (a move back to an earlier home): the target holds the slug with its own full config, the two hold the same documents, and every one matches, compared exactly as above: the two rendered reads, each in its normalized form when either side’s binding normalizes (normalizing text already in the profile changes nothing, so in effect it is the copy that never went through Notion that gets normalized, and a flip back to it returns its original markup, which the report says). Leave out only what the table above skips or computes and the differences a migration makes by design: the config’s `storage` block, `state.md`’s `storage_kind`, What Exists, and the Storage line. Everything else in the config and every `state.md` is compared too, so a later change the author made there (`target_word_count`, `current_focus`, What’s Next) is never discarded. When all of that matches, it is not taken: say so and offer to **just flip**, with no copy. The flip writes the open folder’s config `storage` block as the target’s, whether it names the source or the target now (a pointer to another project is left alone, § Verify, then flip): when the target is this folder (the original local project, whose config still names the backend it moved to), its `storage` becomes `{"kind": "local"}`; otherwise the pointer becomes the target’s block (§ Verify, then flip). Then the session rebinds there. Any document that differs (in the compared parts) or exists on one side only means it is not a plain left-behind copy: show the differences and ask, with the refusal and merge prompt as usual.

**Merge** means: write the source over the target path by path through the target binding, with its concurrency guard (the baseline is the target’s read at preflight) and, where its `history` is `snapshots`, a snapshot of each document replaced (operation `migrate`, per `store.md`). Never delete a target-only document. The logs merge by entry, never by file: a source entry the target lacks is added under its own number; one whose number the target holds with different content is a **conflict**, not copied, and listed. Anything that references a held-back entry is held back too and listed beside it (a question `resolved (D-###)` by it, a `Superseded by` naming it, a chapter or other document citing it), so nothing attaches to the target’s different entry under that number. A guard mismatch is a conflict too: stop that document, show the author both versions, write nothing until they choose. The report lists every conflict and every document replaced.

## Copy

**Order.** The canonical order (canon; story documents; outline; chapters; the logs; everything else; snapshots) has only these real barriers: **canon first**, alone, because a target that indexes cross-references needs it in place (Notion links each chapter row to the characters and places it names); **decisions before questions** inside the logs category (a `resolved (D-###)` links a row); **chapters in chapter order** inside the chapters category; and in a series, **shared root first, then each book in `books` order** inside every category. After canon the categories don’t depend on each other, so they run in parallel. `state.md` and then the config come last, in that order, from the main session, after verification (§ Verify, then flip): the config is the very last write to the target, so a half-finished stored target has no config and is recognizable as unfinished.

**The normalized form.** On a target whose binding normalizes author markup on the way in, each document is written in its **normalized form**: the source’s text with `references/markdown-profile.md` § Rewrite table applied, and nothing else. The table is a markup-only mapping, idempotent by design: it leaves words, code, frontmatter and everything under § Kept as written alone, and text already in the profile (anything the plugin wrote, and anything read back from a Notion row written with this normalization) normalizes to itself. Applying it is model work, since there is no script at runtime, so the table is what makes it repeatable: a resume in a fresh session recomputes the normalized form from the source and must get the same text. **A miss made consistently would pass unseen,** since the read-back compares against the same normalized text, so before writing, a different agent from the one that normalized the document (another subagent, or the main session) goes through the rewrite table row by row over the normalized text, looking at lines rather than reading for sense (for the block rows: every heading, table, quote, list, fence and HTML comment line has an empty line or the document’s edge on each side, and a field label line under a list item in a log entry has one above it; for the emphasis rows: every `*`, `_` and `~` run is checked against the table’s forms): it must find nothing, and anything it finds is a rewrite the first pass missed, which is applied and counted against the preflight’s numbers (*observed (2026-10-24)*: the normalizer’s own second pass missed a whole row, nine headings run into paragraphs in one file; in the second ring a different agent reading for sense missed eighteen in two files, and both passes missed HTML comment lines run into paragraphs). Right after each write the document is read back through the target binding and compared with that form exactly. Every comparison this skill makes against such a target is exact against it, and is a comparison of renderings, never of what a row stores (a log row’s `Meta`, where its `Resolution` starts, the order of its `_as_written` entries or a derived `Name` are the writer’s choices, and two correct writes may store them differently), and where exact can’t hold, the case is handled by name, never by a looser match:

- **A construct with no in-profile form** (the profile’s § No in-profile form): the target changes it and nothing keeps it, so the plan names the document, its read-back `mismatch` is reported with the difference rather than blocking, and a resume or left-behind check shows that document to the author instead of counting it as matched.
- **A mismatch that a rewrite reproduces:** when a document failed its read-back and one rewrite (a retry or a resume) gives the same mismatch, rewriting again can’t help and would keep the flip blocked for good. Stop rewriting it, show the author both versions and the difference, and ask: name it for this run, where it then counts as a No in-profile form case (reported with its difference, not blocking the flip, and listed as such in the report), or stop the run there, leaving the source as it is and the target unflipped.
- **A document edited in Notion since the move,** or a recomputed normalization that comes out different: it doesn’t match, and is treated as any differing document is (both versions shown, the author chooses between rewriting it and the refusal and merge prompt).
- **A row stored before this normalization** (a 0.20.x `init` or `migrate`), or one whose `Meta` the binding reports as damaged (`references/store/notion.md` § Frontmatter ↔ properties, rows stored in the earlier form; its note travels with the document into the report): it can read back in Notion’s own form, which the table still changes (split emphasis such as `**bold *****inner***** bold**`). So on such a project, moving back to a copy left behind shows those documents as differing even when no one edited them: the author sees each with both versions and the difference, and chooses as for any differing document.
- **A log** is rows, not a document: after the logs subagent writes a log’s entries, the rendered `decisions.md` (then `questions.md`) is read back once and compared exactly with the normalized source log, so a dropped field or a wrong `_layout` shows as a `mismatch` on that log.

**Subagents.** Past `references/subagent-pattern.md` § When to dispatch’s threshold, dispatch one execution subagent per category: canon first and alone, and wait for its report before dispatching the rest (a host may launch subagents asynchronously whatever synchronous option the call offers, as observed in Cowork), then the others in a single message so they run in parallel, each keeping the order its own category needs (above). Below it, copy directly in the main session. Every brief carries two store blocks, as `storystormer-init`’s intake briefs do: a **source** block (binding, root, capabilities line, its `read` and `list` realizations; read-only) and a **target** block (binding, root, capabilities line, the realization of every operation used, and the triggered clauses pasted as text: write recovery where `write` is not `native`, the confirmation posture, the documents the target computes and must not be written except through the realizations named for them, and on a merge or resume each target’s baseline and snapshot path), **plus every binding section those realizations cite, pasted as text**, since a subagent can’t open the bundle. On Notion that is the hub’s five data-source URLs, the Projects row id (and book row ids in a series), the path map, frontmatter ↔ properties (with `file-schemas.md`’s frontmatter key order for each kind of document the brief writes, which `_keys` is measured against), rendering, § IDs (with the import rule), § Async (with its two-in-a-row rule: once two consecutive calls fail to queue, the rest go synchronously) and query pagination, and the run’s async state, since the count belongs to the run: the brief carries the run’s count of consecutive queueing failures in, and when the run has already fallen back to synchronous sends it says so and the subagent sends synchronously from its first call; the logs subagent also gets the decisions and questions realizations and the entry formats verbatim. A target that normalizes also needs `references/markdown-profile.md` § Rewrite table, § Kept as written and § No in-profile form, which normalization applies. On Dropbox it is § Write, its recovery and the quirks the writes depend on (case, NFC, the trailing newline). The rule for any binding: whatever a pasted realization refers to travels with it. Each brief lists its paths with source path → target path and the action (copy, or skip and why), and asks for a per-path log: written, identical (no-op), stored as unmapped, skipped (only a skip the approved plan named, with its reason), conflict, **mismatch** (the read-back differs from the normalized form, with the first line that differs), or **failed** (an error the binding’s recovery couldn’t clear, with the error), with counts, plus `async: switched` when the subagent fell back to synchronous sends (the binding’s § Async): the main session then briefs every later dispatch to send synchronously from its first call and reports the switch once. A path the plan didn’t skip is never logged as skipped. Reject a log that names a local filesystem path for a non-local target (`subagent-pattern.md` § Mandatory brief fields) and re-dispatch.

The main session aggregates the logs. Any renumbered log entry (a Notion race, which a new project shouldn’t meet) is reported with both IDs.

## Verify, then flip

**Verify.** Before writing the target’s `state.md` and config, `store.list('**')` on the target and check, leaving out the written-last documents (every `state.md` and the config, which don’t exist yet on a fresh target):

- **Sizes, into a folder:** when the target is a folder and the source’s listing gives each file’s size in bytes (Dropbox), each written file’s size must equal the listed one, allowing for the final newline: a read ends every document in exactly one `\n` (`references/store.md` § Operations, the final newline), so a source file with no final newline is written one byte larger, and one ending in several `\n` smaller by the extra ones. The source binding’s read says how many the stored file had (the Dropbox binding’s read does), and the copy subagent logs that count with the path; any other difference, wherever the host can measure a written file, is a `mismatch`. It costs no extra call, and it is the only content check a copy into a folder gets. Where the host can’t measure, say so.
- **Paths:** every path the logs call written, identical, mismatch or stored as unmapped appears in the listing. Checking the path set, not just a count, also catches a merge where pre-existing target files would mask a missing one.
- **Balance, per category:** the source’s count equals written + identical + mismatch + stored as unmapped + skipped + computed by the target + conflict, so nothing fell through unaccounted.
- **No failures:** any `failed` path blocks the flip, and so does any `mismatch`, except at a document the plan named for a No in-profile form construct, or that the author named for this run after a rewrite reproduced its mismatch (§ Copy), which is reported with its difference.
- **The target’s listing, checked** as the source inventory was (§ The preflight): against its binding’s independent count where there is one, for completeness where there is only that.
- On Notion, the Decisions and Questions row counts match the entries sent, and each log’s read-back matched (§ Copy).

Verification itself re-reads nothing: on a target that normalizes, each document’s content, and each log’s rendering, was already compared at its read-back, and the listing catches a lost write. Anything wrong stops the run before the target’s config and before the flip: report the category, the paths missing or failed, and that re-running resumes.

**Then** the main session writes the target’s `state.md` first (with any What's Next change the move calls for, § Report) and its `.storystormer/config.json` second, the very last write to the target (§ What happens to each item; on Notion the Projects row’s sections), lists the target once more to see they are there (on Notion, that the Projects row now has its sections), and only then **the flip**:

- **A local source:** in the open folder’s config, replace the `storage` block whole with the target’s (`{"kind": "notion", "root": "<row id>"}`, `{"kind": "dropbox", "root": "/StoryStormer/<slug>"}`, with `local_root` only in the hybrid) and keep every other field. No source document changes; going back is restoring `"storage": {"kind": "local"}`, which returns to the project as it was when it moved, without anything done since. The source’s `state.md` keeps `storage_kind: local`; nothing reads it while the config points elsewhere, and the mirror rule leaves it alone (`file-schemas.md` § `.storystormer/config.json`).
- **A connector source with an open folder** whose pointer names this source: rewrite the pointer as exactly `{"storage": {…the target’s block…}}`, the wrapper and nothing else, or, when the target is this folder, the target’s full config has already replaced it.
- **A hybrid source:** the open folder’s config is also the Dropbox project’s config, so the flip changes that one file’s `storage` block; it is the one exception to the untouched source, and restoring the old block undoes it.
- **No config in the open folder** (a local target that was empty, reached from a connector source with no pointer here): the config just written is this folder’s own config. There is no flip.
- **An open folder with no config, and a target that isn’t this folder** (a connector source reached through the locator, moved to another connector): there is no flip, and nothing is written into the folder, since it never pointed at the source. The report says the locator finds the project, as with no open folder.
- **An open folder whose pointer names a different project** (its `storage` block isn’t the source’s: the author reached this source through the locator from another project’s folder): leave the folder alone, write nothing into it, and report that it points at another project and that the locator finds this one.
- **No open folder:** there is nothing to flip. The report gives the new location and says the locator will now list the project on both backends under the same slug until the author deletes the source.
- **Never** a source store’s own config: a Dropbox project’s stored config stays as it was, and a Notion source’s config is computed, so its `storage` is never written.

**After the flip the session moves too.** Replace the binding, root and capabilities line the session remembers (`store.md` § Resolve, “What the session remembers”) with the target’s, by resolving again (with no open folder, bind the target directly, since its root is known, rather than run the locator), so that a decision captured or a document written next lands in the new home and not in the source. The report says the session is now working there.

## The hybrid (local → its own Dropbox)

A local source whose folder syncs through Dropbox, migrated to Dropbox, becomes one store seen two ways: a session with the folder open resolves local, one with no folder resolves Dropbox, and both see the same files. The sync root is the Dropbox folder itself (`~/Dropbox`, `~/Library/CloudStorage/Dropbox`), as in `storystormer-init` § Where a new project lives.

- **The folder already is `<Dropbox sync root>/StoryStormer/<slug>`.** No copy at all. The same-slug check finds this folder’s own config, which is not a conflict. Tell that it is this folder’s own by comparing the config the Dropbox binding reads at `/StoryStormer/<slug>/.storystormer/config.json` with the one the local binding reads here: the same (final newline aside) → its own; different → the cloud holds another version (sync behind, or another project under that slug): stop and show the author both. The plan is two writes through the local binding, config last: `state.md` gets `storage_kind: dropbox` and the hybrid Storage line (`file-schemas.md` § `state.md`), then the config’s `storage` becomes `{"kind": "dropbox", "root": "/StoryStormer/<slug>", "local_root": "<this folder’s absolute path>"}`.
- **The folder syncs through Dropbox but sits elsewhere** (`~/Dropbox/Novels/the-good-dog`). Copy to `/StoryStormer/<slug>`. When the local binding can reach the sync-root path (Claude Code can; a Cowork folder connection that exposes only the project folder can’t), write through the **local binding rooted at `<Dropbox sync root>/StoryStormer/<slug>`** on this machine: the Dropbox binding’s tree is the local tree byte for byte, so these are the files it would hold, written in one native call each instead of delete-create through the connector, and the Dropbox app syncs them up. The same-slug check still runs through the Dropbox binding, which sees the cloud even when this machine’s sync is behind or selective, and the local folder is checked too, through the local binding: it must be absent, or match the approved merge baseline. A folder the cloud doesn’t show but this machine holds (not yet synced) is named and asked about, never overwritten. Verification lists through the local binding; the report says the copy reaches other devices as the Dropbox app syncs it. The new folder gets the full config with `local_root` = its own path and the hybrid Storage line. The old folder’s config is flipped to the same `storage` block, `local_root` included, so opening the old folder resolves to the new synced copy: that `local_root` names the synced copy of the block’s own Dropbox root, the one case where a config outside that folder may carry one (`store.md` § Resolve). When the local binding can’t reach the sync-root path, copy through the Dropbox binding instead, and set `local_root` (in the new config and the flipped one) only if the synced path exists on this machine.
- **A folder outside Dropbox** goes through the Dropbox binding with no `local_root`, unless the author names their Dropbox folder on this machine and it exists (ask; don’t guess), in which case it is the second case.

## Report

- **Where it lives now:** the backend, its root, and the way in (the Dropbox path, the Notion row’s link, the folder), that this session now works there, and how the next session finds it: the open folder resolves there; with no folder, the locator lists it.
- **Dropped from What Exists and computed documents:** the text the plan named, and that the source still holds it.
- **Counts** by category: written, identical (no-op), mismatch (with the paths and the difference), computed by the target, stored as unmapped (with the paths), skipped (with paths and reasons: snapshots on a target without them, non-markdown on Notion, binaries, and the clutter count).
- **Failures** (each path and its error; any blocks the flip, and re-running resumes), **conflicts** and the entries held back with them, **replacements** on a merge, and any log entry renumbered.
- **The source:** where it is, that it is untouched (or, in a hybrid source, that only its config’s `storage` block changed), that `migrate` never deletes it, and that deleting it by hand stops the locator listing two copies. Any snapshots or files that stayed behind are there.
- **Going back:** the `storage` block to restore, and that it returns to the source as it was at the move.
- The binding’s own once-per-run notes: Dropbox’s way to revert; into Notion, the documents normalized and what changed in each, as the plan approved, and visible HTML comments; out of Notion, that text written there or before normalization came back in Notion’s form.

Change the target’s `state.md` → What's Next only if the move changes what the author should do next (it usually doesn’t), and fold that change into the `state.md` write before the config (§ Verify, then flip), so the config stays the last write.

## What this skill does not do

- **Delete or edit the source**, or offer to. The single write outside the target is the flip.
- **Sync two stores.** After the flip the target is the project; the hybrid is one store seen two ways, not two stores kept in step.
- **Convert files.** A binary or non-markdown file the target can’t hold stays where it is and is named.
- **Improve content on the way.** Documents cross as they are, apart from the `storage` fields, the What Exists recount and, into a target that normalizes, the markup normalization the plan approved.
