# StoryStormer Binding

The store is a project in the StoryStormer app, reached through the StoryStormer connector (the app’s MCP server). The server presents the project as a folder of Markdown files in layout 2, path for path the tree `references/file-schemas.md` defines, and keeps each document in the app’s own records, so the author sees every write in the app at once. Read `references/store.md` first; this document only says how each operation is realized here.

## Capabilities

```
identity: path · write: native · edit: native · list: glob · history: versions · open: url · size: ~1 MB / ~1 MB · confirm: none
```

What the store adds beside the line, each used below: `new` writes whose number the server assigns; a document **revision** on every read, listing and write result, sent back as `if_revision` on `write` and `edit` (the guard, § Concurrency guard); a `request_id` on every write, so a retry is exact (§ Request ids); frontmatter-only and batch reads (`frontmatter_only`, `read_many`); a batch write (`write_many`) with `finish_batch` and `dismiss_batch` for one that stopped partway; and listings that can carry each file’s revision and index keys.

**Size:** a document is one database row, about 1 MB with its frontmatter; a stored file (§ Stored and computed) at most 900 KiB (921,600 bytes); a frontmatter block at most 64 KiB (65,536 bytes), and a character or worldbuilding entry’s `## Revelation Log` at most 256 KiB (262,144 bytes). `read_many` and `write_many` take at most 50 paths a call. No story document comes near these; a write over one is refused with the limit named, and nothing is written, so stop and report it rather than split the document.

**Confirmation:** the connector asks nothing, for writes or deletes. The plan-first approval is the only confirmation.

## Tools

The StoryStormer connector’s `list_projects`, `list`, `read`, `read_many`, `write`, `write_many`, `finish_batch`, `dismiss_batch`, `edit`, `delete`, `history` and `open_in_app`. Resolution’s tool check passes when all twelve are present (`finish_batch` and `dismiss_batch` complete `write_many`, which is required, so they are required with it). Optional: `create_project` (`init` and `migrate` create a project here only with it, § Scaffolding a project), `search` and `whoami` (neither is a contract operation; `whoami` names the account the connector acts as, for a report that needs it). Every file tool takes the project id as `project_id` and a contract path as `path`; nothing else addresses a project. No shell, and nothing local except the pointer (§ Root).

**Verified on:** 2026-10-27, written against the server code with the CL101 server changes reflected (whole-document `edit`, the `state.md` revision, journal relabeling, the listing’s `slug`, `finish_batch`/`dismiss_batch`, seven decision types); its live acceptance run (AP4 § 4) is still to come. The behaviors marked *observed* come from the server’s 2026-10-25 live ring (The Good Dog, 155 documents through the server and back, 152 byte-identical).

## Root

The project id, which `list_projects` returns as each project’s `id`. The config’s `storage` block is computed by the server, never written: `{"kind": "storystormer", "root": "<project id>"}`. A contract path is passed as it is: `treatment.md` is `path: "treatment.md"` with `project_id: "<root>"`, and in a series a book’s documents are under `books/<slug>/` (the slugs come back in `list_projects` and in the root `state.md`’s `books`).

**The pointer.** An open folder that should reach this project next session holds `.storystormer/config.json` as exactly `{"storage": {"kind": "storystormer", "root": "<project id>"}}`, written through the local binding, and nothing else. Only resolution reads it; `store.read('.storystormer/config.json')` on this binding returns the computed config, never the pointer.

## Scaffolding a project

`create_project` makes a new project; `init` and `migrate storystormer` are its only callers. **Arguments:** `title`; `type` (`novel`, `novella`, `short_story`, `screenplay` or `series`); optionally `genre`, `target_word_count` (omitted, the type’s default) and, for a series only, `books`, the books’ titles in order (omitted, one book); and a `request_id` (§ Request ids). There is no logline, slug, stage or type-list argument: those are `state.md`’s frontmatter, written through its realization (§ Stored and computed). **Returns** the project’s `id` (the root), `title`, `type`, `paths` (every path the new project lists: the computed documents and, in a series, each book’s `state.md`), its `openUrl` (the project’s Home in the app) and, for a retried `request_id`, `replayed: true` (the first call’s project; nothing created now). The project has `layout: 2` from the create, so the config needs no write. **Book slugs are by position:** `book-1` … `book-N` in the order given, so a caller never offers the author other slugs for a new project here. A slug appended later to `state.md`’s `books` adds a book under that slug. A failure after the project exists (a book not added) names the project id; retrying with the same `request_id` finishes it.

## Stored and computed

Every path the contract defines resolves on the server to one of three things:

- **An app record** (the primer, treatment, manifest, canon, research, voice files, `outline/structure.md`, the genre reference, every chapter file, every entry): `read` renders it as the plugin’s file, frontmatter first, and `write` and `edit` land through the app’s own writers. The frontmatter block is kept exactly as written and reads back byte for byte until the app changes one of its keys, when only that key’s line changes.
- **A stored file:** any path with no app record (`chapters/chapter-NN/kitbash/…`, `.storystormer/canon-sync/*.md`, an intake archive, `series.md` in a project that is not a series), kept as written.
- **A computed document,** rendered from the project on every read. Skills never write one; a step that only regenerates it is skipped (`store.md` § Local-mode clauses):

| Document | What is computed | Writable realization |
|---|---|---|
| `decisions/_index.md` · `questions/_index.md` | the whole index, from the entries | none: write the entry, and its row follows |
| `characters/_index.md` · `outline/_index.md` · `voice/README.md` | the whole document | none |
| `chapters/chapter-NN/.history/*` | the chapter files’ versions, as read-only files | none |
| a multi-scene chapter’s `chNN-prose.md` | the scene files joined by `* * *` | none: write the scene files (§ Quirks) |
| `.storystormer/config.json` | `storage`, and the layout | `write` (or `edit`) setting `layout: 2`, the layout upgrade’s last step; any other key is refused, pointing at `state.md` |
| `state.md` (root) | frontmatter `project_type`, `session_count` and `last_session` (the journal’s highest session and newest date); What Exists’ counted lines; the unfinished-batch lines under What’s Next (§ Batches); the journal reference in Last Session; and, for a project with no Summary of its own, a fallback Summary under a `<!-- storystormer:summary-fallback … -->` marker (computed, never stored: writing the marked text back stores nothing, and editing the text under it makes it the author’s Summary) | `write` or `edit` of the document as read: `## Summary`, `## What's Next`, `## Last Session` and What Exists’ carried lines are stored; the frontmatter’s settings keys change the project (`title`, `genre`, `genre_secondary`, `logline`, `target_word_count`, `people_types`, `world_types`, and in a series `books`, appending a slug to add a book, and `current_focus`, one of the books); every other plugin key (`stage`, …) is stored as written. A changed set-once `slug`, `created` or `initial_maturity` refuses the whole write, naming the key; a changed computed key does too, unless `if_revision` matches, when a stale computed key is ignored with a note; an `edit` that changes only computed parts is refused with the reason |
| `books/<slug>/state.md` | its series keys | as the root’s, for its own sections; its frontmatter sets the book’s `title` and `target_word_count` |
| `series.md` (a series) | everything except the “Cross-Book Setups and Payoffs” section | `write` of the document as read: that section is stored |

Snapshots are never written (`history: versions`, § Operations `history`): `.storystormer/history/` and a chapter folder’s `.history/` are never a write target, whatever a skill’s snapshot step says (`store.md` § Local-mode clauses → Snapshot). The entry indexes are never kept a row at a time here: the index-row step of `file-schemas.md` § Who rebuilds an index is skipped, since the row is the entry’s own.

## Operations

| Operation | Realization |
|---|---|
| `list(glob)` | `list` with `glob` (`*`, `**` and `?` match in the store; a folder name lists everything under it; omitted, the whole project). Returns `entries` of `path`, `kind`, `title`, `updatedAt` and `size`; past 2,000 entries it sets `truncated`, so list again folder by folder, and a single folder that still truncates (a long `journal/`) by filename pattern within it (`journal/2026-*`, then by month), until every listing comes back without `truncated`. A migration or a `checkpoint` report uses only a complete listing, never a truncated one. A chapter folder’s `.history/` files are listed only when the glob stays inside that one chapter’s folder. `with: ["revision"]` adds each file’s revision (a guard baseline, read’s exact size), `with: ["fields"]` each entry’s and canon file’s index keys (`id`, `type`, `topic`, `integrated`, `superseded_by`, `retracted`, `status`, `resolved_by`, `name`, …); each renders every listed file, so narrow the glob. An index check is one such call. An empty folder lists nothing, which is not an error |
| `read(path)` | `read`; the result’s `content` ends in exactly one newline, and carries the document’s `revision` and `size` and, in `meta`, its `openUrl`. *Frontmatter only:* `frontmatter_only: true` returns just the block (fences included; `""` for a document without one), with the whole document’s revision, so it is still a guard baseline. Several documents: `read_many` with up to 50 `paths`, one result per path in order, a failing path carrying its own `error` while the rest still answer. A missing path is an error naming its nearest siblings. An old name of a renamed document is refused with `renamedTo` (§ Quirks) |
| `write(path, content)` | `write` with `content`, `if_revision` (§ Concurrency guard) when the path exists, and a `request_id` (§ Request ids). A byte-equal write is a no-op (`unchanged: true`); a changed one keeps the prior text as a version. An absent path is created at exactly that path. The result carries `revision`, `size`, `created`, `openUrl`, `notes` (a type that fell back, a lowercase word matched, a log line not yet placed: pass them on in the report) and, for an entry, `number` |
| `write(path, content, new)` | `write` with `mode: "new"`. **An entry** (`decisions/D-###.md`, `questions/Q-###.md`, `journal/<date>-s<NN>.md`, or `-s??.md` to let the server choose): the server assigns the next number in the create itself, rewrites the proposed number in the entry’s own content (a decision’s or question’s `id` and its mentions in the body; a journal entry’s own `sNN` citations, in the frontmatter and the body alike, while a filename dated another day, such as `journal/2026-10-20-s14.md`, names that day’s session and is left alone), and returns it as `number` beside the `proposed` one and the entry’s final `path`; use those from then on (`store.md` § New entries). There is no collision to retry: two sessions creating at once each get their own number. **Any other path:** created only if absent; an existing path is refused, nothing written |
| `edit(path, edits, reason)` | `edit` with `edits`, `reason`, `if_revision` and a `request_id`. Each contract item without `replace_all` is `{"op": "replace_range", "anchor_quote": <old>, "new_text": <new>}` (must occur once: a missing anchor is `anchor_not_found`, a repeated one `anchor_ambiguous`); one with `replace_all` is `{"op": "find_replace", "find": <old>, "replace": <new>, "replace_all": true}`. Never send `find_replace` without `replace_all: true` (it replaces the first match, where the contract demands exactly one). All or nothing in the store. `edit` covers the whole document as `read` returns it, for every kind: frontmatter included, a canon entry’s `## Revelation Log` too (log lines still anchor to chapters, as a write’s do), and a stored file. `reason` is kept in the version history for a document that has versions. |
| `history(path)` | `history` with `path` (20 versions by default; `limit` up to 50 when the caller needs more, and a result still `truncated` at 50 means 50 or more): the document’s versions newest first, each `version`, `at` (a timestamp) and `changeDescription`, with `truncated` when older ones exist. A chapter file’s versions are also readable as files: `read` `chapters/chapter-NN/.history/chNN-<stage>-v<n>-<date>.md` (`list` that `.history/` for the names). Another document’s versions are metadata here; their text is in the app’s version history (`open`). An entry, a stored file and a computed document keep no versions: the call says so, and the document’s last change is the `updatedAt` its `list` entry carries |
| `open(path)` | The `openUrl` the path’s last `read`, `write` or `edit` result carried (no extra call); otherwise `open_in_app`, whose `url` opens the document in the app (a bio on People, worldbuilding on World, the primer and treatment on Story, entries on Session, `state.md` on the project’s Home). Every write report gives the link for each document it names |
| `move(from, to)` | `read(from)` (its revision is the baseline), `write(to, …, new)` (a refusal means `to` exists: stop and report both paths), then `read(from)` with `frontmatter_only` and compare its revision with the baseline’s: moved means another writer changed the source after the read, so stop and report both paths, deleting nothing (`delete` takes no revision guard); unchanged, `delete(from)`. A canon document renamed by its title is not a move: write it with the new `name` and the server moves it (§ Quirks) |
| `delete(path)` | `delete`. A document goes to the app’s Trash (restorable there for 30 days); a stored file is marked deleted. Refused, with the way in: an entry (never deleted: retract a decision with `retracted: <date>`, invalidate a question with `status: invalidated`), a chapter file (the author deletes drafts, Blueprints, notes and chapters in the app; name the path for them), a computed document |

## Concurrency guard

The equivalent check (`store.md` § Concurrency guard) is the document’s **revision**, the hash of the document exactly as `read` returns it. Record it at the baseline, from the read the new content was prepared from (`read`, `read_many`, a frontmatter-only read, or `list` with `with: ["revision"]`), or from this session’s own last `write` or `edit` of the path, whose result carries the new one. Send it as `if_revision` on every `write` and `edit` of an existing path; a `new` write needs none. The server compares it inside the write’s own transaction, so **never re-read before a write** to check.

- **A match** writes, and the result’s `revision` is the baseline for the session’s next write of the path.
- **A refusal** (“changed since it was read”) writes nothing and returns `conflict`: the current `revision`, `size` and `content`. That is the guard’s re-read: show the author what the store holds now beside what this session was about to write, and write nothing until they choose. Their choice is written with `if_revision` set to the conflict’s `revision` and a **new** `request_id`, since the content changed.

A revision moves only when the document as read changes, so a refusal is always a real change (the app’s edit, another session’s write), never a stamp moving on its own. `state.md`’s revision covers only its writable parts: the frontmatter minus the computed keys (`project_type`, `session_count`, `last_session`, a book’s series keys), Summary, What’s Next, Last Session (without the journal reference the server keeps current) and What Exists’ carried lines. What Exists’ counted lines, the unfinished-batch lines and the computed fallback Summary are not covered, so the session’s own journal, decision and primer writes never move it. A session writes `state.md` last with the revision it read at the start of the step.

## Numbers and the journal

Decisions, questions and the journal’s session numbers are stored by the server and never reused (`store.md` § New entries). A `new` write is the create; the server assigns the number in that call and writes it into the entry’s own content, so the skill fixes only **other** documents that cite the proposed number (the journal’s lists, a question’s `resolved_by`, prose), and the report names both numbers when they differ.

The journal entry is created by the session’s first write as `file-schemas.md` § `journal/` says, with `mode: "new"` on `journal/<today>-s??.md` (or the proposed number): the result’s `path` is the entry for the rest of the session, extended with `edit`. A journal entry’s `date` never changes after it is created. `state.md`’s `session_count` and `last_session` are computed from the journal, so the session writes no counter: `state.md` carries them as the step’s read shows them, and a stale computed key is ignored with a note when `if_revision` matches (§ Stored and computed); without `if_revision`, a changed one is refused.

## Request ids

Every `write`, `edit`, `write_many` path and `create_project` carries a `request_id`: the session’s id (minted once at resolve, say the date, time and four random characters) plus a step counter, `2026-10-26T09-14-k3x9-17`, never reused within the session for different content. A subagent’s brief gives it its own prefix (`…-k3x9-a2-`), so two agents never share an id. A retry of a call whose answer was lost (a timeout, a dropped connection) resends the **same** call with the same id:

- **`replayed: true`:** the first call’s result, and nothing was written now.
- **`unchanged: true`, `created: false`:** the document already reads exactly as this call writes it, because the first call landed (*observed (2026-10-25)*). That is success: carry on with the result’s revision.
- **`resultUnknown: true`:** the first call landed but its result was lost; `read` the path for its revision and content, and never resend it.
- **`resumed: true`:** a chapter write whose save landed and whose follow-up steps ran now.
- **Refused as in progress:** the first attempt is still running; retry shortly with the same id.

Receipts last 24 hours. The same id with different content is refused, so content the author changed after a conflict always takes a new id.

## Batches

A step that writes several documents (`treatment-update`’s treatment and the decisions it integrated) may write them with **`write_many`**: `files`, each with its own `path`, `content`, `mode`, `if_revision` and `request_id`, plus a `request_id` for the batch, up to 50 paths a call. The order rule (`store.md` § Operations, Batches) is the order of `files`: the referenced document first. **A numbered `new` entry is never batched with a document that cites it:** `write_many` does not carry an assigned number into the later files of the same batch, so a `superseded_by: D-069` there would name the wrong decision when the server assigns `D-070`. Write the `new` entry on its own first, build the documents that cite it from the returned number, then batch those. `state.md` is never in a batch with the journal entry or entries it counts: a `write_many` preflight compares the project row as loaded, so it is written alone, last.

Every path is checked first (resolved, parsed, its `if_revision`, its `mode`); if any is refused, **nothing is written** and every refusal comes back, so a stale baseline anywhere stops the batch before it starts, and the guard runs per path as above. Then the files are written in order, stopping at the first failure, with one result per path: `landed`, `unchanged`, `refused` or `not_attempted` (`finished` says whether all landed). It is ordered, not one transaction.

**An unfinished batch** (stopped partway and still open ten minutes later) shows as a computed line under the root `state.md`’s What’s Next, “A batch from <date> didn’t finish: …”, and as `unfinishedBatches` in `list_projects`, for up to seven days. The line names what landed and what wasn’t written, the batch id (the batch’s `request_id`) and which call to use. The server keeps the content of every path it didn’t write (up to 900 KB per batch) for those seven days. Offer it to the author at session start (`store.md` § Operations, Batches): **finish** or **dismiss**.

- **Finish:** `finish_batch { project_id, batch_id }` writes the rest in order with the original per-path request ids, skips paths that landed, and returns `write_many`’s per-path results plus `not_kept`, the paths over the cap whose content wasn’t kept; only those need the skill step rerun. A batch that kept nothing says so and names the paths. In the session that started it, a rerun of `write_many` with the same batch `request_id` and per-path ids still works.
- **Dismiss:** `dismiss_batch { project_id, batch_id }` ends it and returns `landed` and `unwritten`. A dismissed batch can’t be rerun or finished, and its `request_id` is spent. The app’s Session notice has the same dismiss, an X.

## Subagents

A subagent brief (`store.md` § Resolve, Subagents never resolve) carries: the project id; the capabilities line; each operation’s realization from § Operations that the subagent will use, written out (the tool, its arguments, the result fields it reads); the baseline revision of every document it may write, sent as `if_revision`; its `request_id` prefix; the computed documents from § Stored and computed that it must never write; and, written out because it cannot reach the bundle, § Concurrency guard (how a refusal is handled and shown), § Request ids, § Numbers and the journal, and the batch order rule from § Batches. A subagent that reads several documents reads them with `read_many`, in calls of at most 50 paths. Its report names the paths it wrote with their revisions and `openUrl`s; a report naming a local path means it wrote outside the store, and the main session rejects it.

## Locate

The well-known root is the connected account: `list_projects` lists every project it holds, newest first, in one call.

**Returns**, per project: `id` (the root), `title`, `type`, `genre`, `updatedAt` (the last-modified time), `isSeries` and a series’ `books` (each `slug` and `title`), `slug` (`state.md`’s set-once `slug`, `null` when unset), `stage` and `last_session` (the values `state.md`’s frontmatter reads), and `unfinishedBatches` when a batch on it didn’t finish (say so beside it). There are no pointers or synced local copies here, and the layout comes from the project’s computed config (`store.md` § Resolve, step 4). **Fails** when the call errors (the connector not connected, or its sign-in expired: tell the author to reconnect the StoryStormer connector); an empty list means no projects here, which is not a failure. **Cost:** one call.

## Quirks

- **`state.md` is written last, with the revision read at the step’s start.** Its revision covers only its writable parts (§ Concurrency guard), so the step’s journal, decision and primer writes leave it alone: prepare it from the step’s own baseline read, change What’s Next and Last Session, and `write` it after the other documents. A refusal means the author or another session changed a writable part meanwhile, which is a conflict per `store.md`: show both, and write nothing until the author chooses.
- **Canon paths follow the name.** A bio, worldbuilding or research file is named by its full `name` (`characters/tommy-marsh.md`, not `tommy.md`), and renaming the document in the app or by writing a new `name` moves it. Use the `path` a write returns. An old path’s `read`, `write`, `edit` or `delete` is refused with `renamedTo`: use that path, and fix any document that cites the old one (notes, proposals, `Appears in`). Only a `new` write may take a freed path, and it creates a new document there (*observed (2026-10-25)*).
- **An outline’s frontmatter** must carry `title` and `summary` (and `chapter`, `pov`, `act` as the schema says); when an outline written elsewhere lacks a `summary`, compose a one-line one from its body before writing it, or the write (and a whole `write_many`) is refused (*observed (2026-10-25)*). An author-written outline is replaced only by a `write` with `force: true`, passed only when the author asked for the change; never `edit` a protected outline.
- **Lowercase types are matched:** `tier: major`, `category: location` and the like are read as the project’s types (`Major`, `Locations`), and the write says so in `notes`; the file keeps its own word (*observed (2026-10-25)*). A type the project lacks falls back with a note, never silently.
- **Earlier prose drafts** are the app’s draft switcher, not `.history/`: a prose `write` or `edit` always lands as a new draft, and the previous one stays in the app, reachable through `open`. A prose revision loop’s archive step writes nothing here.
- **A prose file’s `synopsis`** fills the chapter’s synopsis only when the chapter has none; an existing one is kept, with a note. When the author asks for the prose’s synopsis to replace it, write it as the outline’s `## Synopsis`, which the outline write applies.
- **Multi-scene chapters:** once a chapter has more than one scene, its prose and Blueprints are per scene: write `scenes/chNN-scene-MM.md` and `scenes/chNN-scene-MM-blueprint.md`, and read the scene files (not the joined `chNN-prose.md`, which is read-only and carries no `status`, `authorship` or POV keys) for anything that gates on the prose’s state (notes, canon-sync’s adjudication). The outline, the notes and `chNN-blueprint.md` (scene 1’s) stay chapter-level. Writing the scene file one past a chapter’s last scene adds that scene.
- **Blueprint provenance:** a Blueprint write carries `sources`, the paths it was built from (the outline, the canon read), so the app can tell when it is stale; a Blueprint `read` reports `stale`.
- **`outline/_index.md`** shows the chapters that exist; planned spine slots come from `outline/structure.md`, so a progress count reads its denominator there.
- **The series Manifest** is the project-level `manifest.md`; a series keeps one.
- **Series numbering:** under `books/<slug>/` chapters and acts are the book’s own, 1…n, and only the book’s next chapter can be created. A Revelation Log’s `Ch N` is the project-wide chapter number; `Ch B2-07` is also read.
- **Canon-sync run records** are stored files under `.storystormer/canon-sync/`, written and read as any stored file.
- **Text only:** a binary intake original (`.docx`, an image) can’t be stored; convert prose to Markdown before writing it, and name any other binary in the report.
- **The development deployment:** until the app has a production deployment, the connector’s URL serves the development database. Nothing changes for the binding.

## Migration in and out

**Into the server** (`migrate storystormer`, this binding the target): each document is a plain `write` at its own path, entries included, so every entry keeps its number (a plain write to an absent entry path imports it at exactly that number; a number the project already holds is the mismatch `migrate` reports). Each write’s `request_id` is derived from the move, not the session, and kept under the server’s 200-character cap: `migrate-<target project id>-<path>` when that fits (every path but a very deep intake or kit-bash one does); a path too long for it gets `migrate-<target project id>-long-<n>`, `n` its 1-based position among the move’s over-long paths in the source listing’s sorted order, which the plan lists path by path. The rule is deterministic (a skill has no shell to hash with) and collision-free within a move: no two paths share an id, however alike. So a rerun after an interruption resends identical calls: landed ones answer `replayed` or `unchanged`, and nothing is written twice or duplicated. A source document edited between the runs has new content, which its old id refuses, and so does an over-long path whose `n` shifted because the source gained or lost one: give that path a new id (`…-2`), as the refusal names it. Large sets go through `write_many` in batches of up to 50, entries before the documents that cite them, and the entries ordered among themselves so every referenced entry precedes its referrer (a decision before the one whose `superseded_by` names it, a resolving decision before the question whose `resolved_by` names it), since the entry writers require the referenced entry to exist. `state.md` is written alone, after every batch has landed (a batch’s preflight checks it against the project as it stands, before the journal entries it counts exist), and read back after its write so its writable parts are verified like every other document’s content before the flip. **Computed documents are not written:** skip `characters/_index.md`, `decisions/_index.md`, `questions/_index.md`, `outline/_index.md`, `voice/README.md`, the config (the server computes `storage`; only `layout: 2` is set, by the upgrade) and, in a series, `series.md` except its Cross-Book Setups and Payoffs section; a multi-scene chapter’s joined `chNN-prose.md` is read-only too (its scene files carry the prose). The source is never touched. **The verify:** `read_many` every written path, 50 at a time, whatever the project’s size (a large project is more calls, never fewer paths), and compare each with the source’s content (the final newline aside), so a lost paragraph shows before the flip makes this the active store; a document the server computes in part (a series’ `series.md`, whose only writable section is Cross-Book Setups and Payoffs; `state.md`’s writable parts) is compared on that part alone, since the rest reads back as the server’s rendering by design. A `list` with `fields` checks the entry keys and numbers but cannot see a lost paragraph, so it is in addition to the read, never instead of it.

**Out of the server** (this binding the source): `list` the project, `read_many` 50 paths at a time, and write each to the target through its binding. Computed documents read like any other; the target binding decides whether it stores them. There are no book-level snapshots here (those documents’ versions stay in the app). A chapter folder’s `.history/` files do travel, since they read as files: a project-wide `list` never includes them, so `list` each chapter folder on its own to carry them out; they are skipped (and counted) only when the target binding doesn’t store history files. The app’s Export is the way out without Claude.

## `checkpoint`

`history: versions`, so `checkpoint` writes nothing and reports what changed since a point instead (`commands/checkpoint.md`). The cheap realization over a whole project: one `list` of the project gives every document’s `updatedAt`; each document changed after the point is then asked for its `history`, and the versions whose `at` is after the point are its count. A document with no versions of its own (an entry, a stored file) counts as changed by its `updatedAt` alone. Computed documents (`state.md`, `series.md`, the indexes, the config) carry neither `updatedAt` nor versions, so they are left out of the report, with a note saying so. Each `history` call passes `limit: 50`; a result still `truncated` is reported as “50+”, a lower bound, never an exact count.

## Worked example: `treatment-update` replaces `treatment.md`

1. **Baselines.** The skill read `treatment.md` and the decisions it integrates with `read_many`; each result’s `revision` is that document’s baseline.
2. **Journal.** The session’s first write, if it hasn’t happened: `write` `journal/2026-10-26-s??.md` with `mode: "new"`; the result’s `path` (`journal/2026-10-26-s14.md`) is the entry.
3. **No snapshot.** `history: versions`: the treatment’s prior text becomes a version when it is replaced, and the report says so instead of naming a snapshot folder.
4. **Batch.** `write_many` with the treatment first (its baseline as `if_revision`), then each decision with `integrated` set (each with its baseline), every path its own `request_id`. A stale baseline anywhere refuses the batch with nothing written: show the author that document beside this session’s, then rerun.
5. **Journal and `state.md`.** `edit` the journal entry (its revision from step 2), then `write` `state.md` last: the text read at the step’s start with What’s Next and Last Session changed, and that read’s revision as `if_revision` (§ Quirks).
6. **Open.** The report links `treatment.md` with its `openUrl` from step 4.

## Worked example: `decisions` logs a decision

1. **Journal.** A fresh session has no entry yet: its first write is `write` `journal/<today>-s??.md` with `mode: "new"`, and the result’s `path` is the entry.
2. **Number.** No listing needed for the number: `write` `decisions/D-069.md` (the skill’s proposal from the last listing it holds, or any) with `mode: "new"`. The app logged one meanwhile, so the result is `number: 70`, `proposed: 69`, `path: decisions/D-070.md`, and the server has written `D-070` into the entry. The report says `D-070 (proposed D-069)`.
3. **Supersede.** If it supersedes `D-041`, that decision is written after it (the order rule), built from the returned number: `superseded_by: D-070`, with `D-041`’s baseline revision.
4. **No index row:** `decisions/_index.md` is computed.
5. **Journal and `state.md`.** `edit` the journal entry to add `D-070`, then `write` `state.md` last, from the read taken at the start (§ Quirks).
6. **Cost:** about six calls (seven with the supersede), none carrying more than the entry or `state.md` itself.
