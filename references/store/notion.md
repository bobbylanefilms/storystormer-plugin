# Notion Binding

The store is a Notion workspace. Each project is one row in a **Projects** database; its documents are rows in four more databases (Assets, Chapters, Decisions, Questions) under a hub page, and anything the path map doesn’t cover is a child page of the project’s row. Skills still pass paths; this binding maps each path to a row and its properties. Read `references/store.md` first; this document only says how each operation is realized here.

## Capabilities

```
identity: id · write: native · edit: native · list: query · history: native · open: url · size: ~5k words sync, larger async · confirm: none
```

**Size in practice:** every create and update passes `allow_async: true` and waits for the task (§ Operations), so the write size never changes the procedure. One fetch returned a 12,700-word page (69 KB) whole, with no `truncated` flag.

**Confirmation:** the connector asks nothing except for trashing: `notion-delete-pages` refuses until called with `user_confirmed: true`. The plan-first approval that names the path is that confirmation (`store.md` § Confirmation posture); a delete outside the approved plan is asked for first.

## Tools

The Notion connector’s `notion-search`, `notion-fetch`, `notion-create-pages`, `notion-update-page`, `notion-create-database`, `notion-update-data-source`, `notion-query-data-sources`, `notion-get-async-task` and `notion-delete-pages`. Optional: `notion-move-pages` (`move` of a child page between rows), `notion-get-teams` (a teamspace hub at `init`) and `notion-get-self` (the user id that narrows hub search). Some surfaces expose the same tools without the `notion-` prefix; either spelling satisfies the tool check. No shell.

**Verified on:** 2026-10-16 (live probes) and 2026-10-17 (a live local → Notion → Dropbox → local migration ring of a 148-file project); findings are marked *observed*, those from the ring *observed (2026-10-17)*.

## Layout and root

- **Hub:** a page titled exactly `StoryStormer` at the workspace’s private root (empty ancestor path) or at a teamspace’s top level (an ancestor path naming only the teamspace; that form is unobserved), whose content holds the five databases as `<database>` children named Projects, Assets, Chapters, Decisions, Questions. One `notion-fetch` of the hub returns each database’s `data-source-url` (`collection://…`); every query and create uses those.
- **Finding hubs** (the locator and `init` both use this): `notion-search` for `StoryStormer` with `page_size` raised (25) and, where the surface offers it, `filters.created_by_user_ids` set to the connected user (`notion-get-self`); search is fuzzy and returns 10 by default. The creator filter hides a hub a colleague created in a teamspace, so when the filtered search finds no complete hub, search once more without it before concluding there is none. Read each result’s title and `path` from the search response itself (*observed (2026-10-17)*: results carry both, so a non-hub hit needs no fetch; one cost a 60 KB fetch): absent or empty is the private root, a teamspace name alone is a teamspace’s top level, anything longer is not a hub location. Fetch only the results titled exactly `StoryStormer` at a hub location, to see which databases they hold. A hub created earlier in this run may not be indexed yet: reuse the id you created rather than searching for it. A **complete** hub holds all five databases; a **partial** one holds one to four of them; a page with none is not a hub (a workspace may hold such a page elsewhere, and search is fuzzy). § Locate searches only complete hubs and reports the partials; `init` stops on a partial (§ Scaffolding).
- **Root** (`config.json` `storage.root`): the page id of the project’s Projects row. In a series the root is the series row; each book is a Projects row whose `Parent` is the series row (its `Books` relation fills itself), ordered by `Book Order`.
- **Unmapped paths** are child pages of the bound row (the book’s row under `books/<slug>/`), titled with the path. Notion parses a page title as inline markdown (*observed (2026-10-17)*: a `.md` basename comes back autolinked, `notes/[craft-document.md](http://craft-document.md)`, and `_x_` as italics, so four intake pages mapped back to the wrong path), so the title is sent as the path in one inline code span (`` `notes/craft-document.md` ``), inside which nothing is parsed (*unobserved*: after the first child-page create of a run, fetch it and check its `<properties>` title is that span; if not, retitle that page with the fallback form, a backslash before every ASCII punctuation character, fetch it again to confirm, and use that form for the rest of the run). **Reading a title:** take it from the page’s `<properties>` title or the parent’s `<page>` tag, never the fetch’s top-level `title`, which drops the markup (*observed (2026-10-17)*: `Jon_Hartley_-CharacterProfile.md`); a title in a code span is the path exactly as it stands between the backticks, with nothing unescaped or collapsed inside it (a literal `\` in a filename survives); any other title has its autolinks collapsed and escapes removed per § Rendering, and in a title written before this rule read `*…*` as the `_…_` it came from (a path holds no `*`).

## Path map

The descriptor table every operation uses; never branch on path strings outside it. **Filters:** Assets and Chapters selectors also filter `Project` = root and `Book` = the book’s row under `books/<slug>/…` (empty otherwise). Decisions and Questions filter `Project` only: they have no `Book`, a series keeps them at the root, and their scope is the `Scope` field. Projects rows are addressed by page id: the root, or a book row (`Parent` = root, `Slug` = slug).

| Path | Database | Selector |
|---|---|---|
| `state.md` · `.storystormer/config.json` | Projects | the root row (the book row for `books/<slug>/state.md`): computed |
| `primer.md` · `treatment.md` · `manifest.md` · `series.md` · `outline/structure.md` · `.storystormer/genre-reference.md` | Assets | `Kind` = primer · treatment · manifest · series · structure · genre-reference |
| `characters/<slug>.md` | Assets | `Kind` = character, `Slug` = slug |
| `worldbuilding/<folder>/<slug>.md` | Assets | `Kind` = worldbuilding, `Slug` = slug, kebab-case of `Category` = folder |
| `research/<slug>.md` · `voice/samples/<slug>.md` | Assets | `Kind` = research · voice-sample, `Slug` = slug |
| `voice/style-guide.md` · `voice/writing-sample.md` | Assets | `Kind` = voice-style-guide · voice-writing-sample |
| `characters/_index.md` · `outline/_index.md` · `voice/README.md` | none | computed from queries |
| `chapters/chapter-NN/ch<NN>-<artifact>.md` | Chapters | `Chapter` = NN, `Artifact` = outline · blueprint · prose · notes |
| `chapters/chapter-NN/scenes/ch<NN>-scene-MM.md` | Chapters | `Chapter` = NN, `Artifact` = scene, `Scene` = MM |
| `decisions.md` · `questions.md` | Decisions · Questions | every row of the project: computed |
| `.storystormer/history/**` · `chapters/*/.history/**` | none | never exist (`history: native`) |
| anything else (`kitbash/`, `.storystormer/canon-sync/*.md`, `.storystormer/intake/**`, …) | child page | parent = bound row, title = the path |

## Schema

`init` runs this through `notion-create-database` with `parent` = the hub, in this order (later tables relate to earlier ones; substitute each returned data-source id), then adds the two self-relations with `notion-update-data-source`, because a table can’t reference its own id before it exists.

```sql
-- 1 Projects
CREATE TABLE ("Name" TITLE, "Slug" RICH_TEXT, "Project Type" SELECT('novel','novella','short_story','screenplay','series'),
  "Genre" RICH_TEXT, "Genre Secondary" RICH_TEXT, "Logline" RICH_TEXT,
  "Stage" SELECT('concept','brain-dump','brainstorming','treatment-drafted','treatment-refined','canon-development','outlining','outline-drafted'),
  "Initial Maturity" SELECT('concept','brain-dump','brainstorming','treatment-drafted','treatment-refined'),
  "Surfacing Mode" SELECT('active','on-request'), "Created" DATE, "Last Session" DATE, "Session Count" NUMBER,
  "Target Word Count" NUMBER, "Current Focus" RICH_TEXT, "Book Order" NUMBER, "Storage Kind" SELECT('notion'),
  "Decisions Head" RICH_TEXT, "Questions Head" RICH_TEXT, "Last Edited" LAST_EDITED_TIME,
  "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 2 Assets
CREATE TABLE ("Name" TITLE, "Project" RELATION('<projects-ds>', DUAL 'Assets'), "Book" RELATION('<projects-ds>'),
  "Kind" SELECT('primer','treatment','manifest','series','structure','genre-reference','character','worldbuilding',
    'voice-style-guide','voice-writing-sample','voice-sample','research'),
  "Slug" RICH_TEXT, "Type" RICH_TEXT, "Category" RICH_TEXT, "Tags" RICH_TEXT, "Version" NUMBER, "Last Updated" DATE,
  "Primer Version" NUMBER, "Authorship" SELECT('author_written','ai_generated','ai_generated_author_revised'),
  "Body Words" NUMBER, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 3 Chapters
CREATE TABLE ("Name" TITLE, "Project" RELATION('<projects-ds>', DUAL 'Chapters'), "Book" RELATION('<projects-ds>'),
  "Chapter" NUMBER, "Artifact" SELECT('outline','blueprint','prose','notes','scene'), "Scene" NUMBER,
  "Title" RICH_TEXT, "POV" RICH_TEXT, "Act" RICH_TEXT, "Summary" RICH_TEXT, "Status" SELECT('drafted','revising','revised','retired'),
  "Authorship" SELECT('author_written','ai_generated','ai_generated_author_revised'), "Version" NUMBER,
  "Word Count" NUMBER, "Last Updated" DATE, "Related Assets" RELATION('<assets-ds>'), "Markers" RICH_TEXT,
  "Open Proposals" NUMBER, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 4 Decisions
CREATE TABLE ("Name" TITLE, "Number" NUMBER, "Project" RELATION('<projects-ds>', DUAL 'Decisions'),
  "Type" SELECT('plot','character','worldbuilding','structure','theme'), "Date" DATE, "Scope" RICH_TEXT,
  "Affects Books" RICH_TEXT, "Summary" RICH_TEXT, "Details" RICH_TEXT, "Affects" RICH_TEXT, "Source" RICH_TEXT,
  "Integrated" RICH_TEXT, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 5 Questions
CREATE TABLE ("Name" TITLE, "Number" NUMBER, "Project" RELATION('<projects-ds>', DUAL 'Questions'),
  "Priority" SELECT('critical','important','nice_to_resolve'),
  "Category" SELECT('Story Structure','Character','Plot','Worldbuilding','Theme','Setting','Pacing'),
  "Scope" RICH_TEXT, "Affects Books" RICH_TEXT, "Question" RICH_TEXT, "Why It Matters" RICH_TEXT,
  "Possible Approaches" RICH_TEXT, "Dependencies" RICH_TEXT, "Source" RICH_TEXT,
  "Status" SELECT('open','resolved','invalidated'), "Resolution" RICH_TEXT, "Resolved By" RELATION('<decisions-ds>'),
  "Date" DATE, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- then the self-relations:
-- on Projects
ADD COLUMN "Parent" RELATION('<projects-ds>', DUAL 'Books' 'books')
-- on Decisions
ADD COLUMN "Supersedes" RELATION('<decisions-ds>', DUAL 'Superseded By' 'superseded_by')
-- a hub created before prose could be retired: on Chapters, before the first `status: retired` write
ALTER COLUMN "Status" SET SELECT('drafted','revising','revised','retired')
```

The `DUAL` relations to Projects give the Projects row `Assets`, `Chapters`, `Decisions` and `Questions` lists; one fetch of the row returns each list whole (*observed*: 101 entries). Decisions `Type` and Questions `Category` are the app’s enums after AP0 Part B (`recordDecision.ts`, `createQuestion.ts`); a value outside them is stored as its mapped or closest option and kept verbatim (§ Frontmatter ↔ properties, Values).

**Schema upgrades.** A hub created by an earlier version of this binding lacks the columns added since (Decisions and Questions `Meta`; Projects `Decisions Head`, `Questions Head` and `Last Edited`). The hub fetch lists each data source’s columns; in any run with an approved plan, before its first write to the hub, add every missing one with `notion-update-data-source` (`ADD COLUMN "Meta" RICH_TEXT`, `ADD COLUMN "Last Edited" LAST_EDITED_TIME`), under that approval, and say so in the report. `Last Edited` is computed by Notion and never written, so it arrives with whatever run first writes to the hub, not with a write that needs it. Reads and § Locate never add a column: a missing one reads as empty, and Locate shows last edited as unknown until then.

## Frontmatter ↔ properties

**The rule:** `read` returns exactly the frontmatter the source wrote, keys, order and values, unless a property was changed in Notion since. **On write**, each frontmatter key lands in its property below and the markdown body becomes the page content. A key with no property goes into `Meta` as YAML text, verbatim and in the document’s order (block scalars such as `revision: >-` and a prose `synopsis: |` included). Path-derived properties (`Project`, `Book`, `Kind`, `Slug`, `Chapter`, `Artifact`, `Scene`, `Name` where no key supplies it) come from the path map. Three `Meta` keys belong to the binding (they start with `_`; a source key that starts with `_` stops the write, naming it), each written only when needed:

- **`_keys`:** the source’s frontmatter keys in its order (`[name, species, tier, version, last_updated]`), when that order differs from the one `file-schemas.md` gives for the document or the document has none (research, voice). *Observed (2026-10-17)*: without it, 19 files came back reordered.
- **`_as_written`:** for each key whose value, rendered back from its property, would not be the source’s exact text, a map entry `<key>: {stored: <the property value written>, value: <the source’s value text, quotes included>}`: a select value outside the options (stored as the closest option, or empty when none is close: `stage: outlining — partial spine committed (chapters 1–3, D-067)` stores `outlining`), an old spelling the binding normalized (`author-written`), a legacy worldbuilding `category` (below), an empty or `null` value, a number-looking text value written quoted (`act: "1"`).
- **`_derived`:** `{<Property>: <value>}` for each property the binding filled from something other than its own key (a character’s `Type` from a legacy `tier`).

**Overrides stay true.** An `_as_written` entry or a `_derived` value applies only while every property it covers still equals its recorded value. Every write or edit that sets a property refreshes the overrides covering its key in the same `update_properties` call: `_as_written` gets the new source text when it still differs from the property’s rendering and loses the entry when it doesn’t (an edit to `authorship: author_written` drops the old `author-written` override), `_derived` loses the property now set from its own key, and `_keys` is rewritten when the edit adds, removes or reorders keys. So no override survives whose recorded value the property no longer holds.

**On read**, properties and `Meta` render as frontmatter, values quoted per `file-schemas.md` § Frontmatter values, then the body. Keys come in `_keys` order when it is set (a set property whose key `_keys` doesn’t list, such as `storage_kind` or one filled in Notion since, goes after the nearest listed key that precedes it in `file-schemas.md`’s order, else first), else in `file-schemas.md`’s order for the document followed by the other `Meta` keys in stored order; `_` keys never render. A key in `_as_written` renders its `value` while its property still holds `stored`, and the property’s value once it doesn’t (the author changed it in Notion). A property in `_derived` renders only once it differs from the recorded value. An empty property renders nothing, except keys the schema requires on every write (an outline’s `pov`), which render empty, and keys `_as_written` keeps.

| Database | Property ← frontmatter key |
|---|---|
| Projects | `Name` ← `title` · `Genre` ← `genre` · `Genre Secondary` ← `genre_secondary` · `Project Type` ← `project_type` · `Target Word Count` ← `target_word_count` (on a book row, the book’s own value only: § Stored and computed) · `Storage Kind` ← `storage_kind` (always `notion`) · `Logline` ← `logline` · `Stage` ← `stage` · `Initial Maturity` ← `initial_maturity` · `Created` ← `created` · `Last Session` ← `last_session` · `Session Count` ← `session_count` · `Surfacing Mode` ← `surfacing_mode` · `Books` ← `books` (book rows’ `Slug`, by `Book Order`) · `Current Focus` ← `current_focus` · `Parent` ← `parent_series` (renders the parent row’s `Name`) · `Slug` ← the project or book slug |
| Assets | `Name` ← `name`, else `title` (`series.md`, research, the style guide), else the label: `Primer`, `Treatment`, `Manifest`, `Series`, `Structure`, `Genre Reference`, `Style Guide`, `Writing Sample`, and the slug for a research or voice-sample row without either key (a document holding both keeps `title` in `Meta`) · `Type` ← `type`, else from a bio’s legacy `tier` (`major` → `Major`, `supporting` → `Supporting`, `minor` → `Minor`, per `file-schemas.md`; recorded in `_derived`, and `tier` stays in `Meta`, so the bio renders `tier:` as written and What Exists and the index still see a type) · `Category` ← `category` when its kebab case is the entry’s folder, else the folder’s type name (`locations/` → `Locations`) with the source’s value in `_as_written` (`category: location` renders back as written) · `Tags` ← `tags` · `Version` ← `version` · `Last Updated` ← `last_updated` · `Primer Version` ← `primer_version` · `Authorship` ← `authorship` |
| Chapters | `Title` ← `title` · `POV` ← `pov` · `Act` ← `act` · `Summary` ← `summary` · `Status` ← `status` (prose, scenes) · `Authorship` ← `authorship` · `Version` ← `version` · `Word Count` ← `word_count` · `Last Updated` ← `last_updated` · `chapter` renders from `Chapter` · `Name` = `ch<NN>-<artifact>` or `ch<NN>-scene-MM` |

**Chapter identity.** The path decides `Chapter`, `Artifact` and `Scene`. A frontmatter `chapter` that disagrees with the path is an error: nothing is written, and the error names both. Renumbering is `move`.

**Values.** Dates are `YYYY-MM-DD`, sent as `date:<Property>:start` with `date:<Property>:is_datetime: 0`. Numbers are numbers and render without a decimal point. A list (`tags: [hope, "sector: 7"]`, or a block list) is stored as its YAML text verbatim and renders back as is, never split or joined. Relations take page ids when writing a property; query filters take page URLs (§ Queries). Selects accept only their listed options (*observed*: the connector rejects any other value, and adding one needs `ALTER COLUMN` naming every option to keep), so open lists (People types, worldbuilding types, tags, sources) are text. For a select, store the option the value maps to: an old spelling or retired value `file-schemas.md` maps (`author-written` → `author_written`, decision type `voice` → `theme`, question category `structure` → `Story Structure`), else the closest option by meaning (`premise` → `theme`, `process` → `structure`), else empty; never add an option. Whenever the stored option isn’t the source’s exact text, keep that text in `_as_written` (a log entry’s header in its `Meta`, § Stored and computed), so the rendering returns it. *Observed (2026-10-17)*: without this, 22 of 68 decision types and every question category came back remapped.

**Replacing a row** sets every property from the new content: a mapped key absent from it is set to `null`, and `Meta` is rewritten whole (`null` when no unmapped key remains). Path-derived properties keep their values.

**Binding-maintained** (rebuilt on every write and on every edit that changes the body; never rendered): Chapters `Markers` = every `[OPEN: Q-###]` and `[NEEDS DEVELOPMENT` in the body, comma-separated (a parse of the plugin’s own marker format); Chapters `Related Assets` = the project’s character and worldbuilding rows the body names, matched by the model against an Assets query’s `Name`s (an index that can lag edits made in Notion); Chapters `Open Proposals` (notes rows) = the unchecked `- [ ]` items under `## Proposals`; Assets `Body Words` = the body’s word count (body only, never frontmatter; a word is a whitespace-separated token holding at least one letter or digit), counted from the body on every write and body-changing edit, never carried over or adjusted. It is **approximate** on a host with no exact counter (*observed (2026-10-17)*: estimates were off by −179 to +336 words), so it feeds only What Exists’ `~<n>w` and nothing compares, gates or decides on it; `Change Note` = the edit’s `reason` on every row the edit touches, cleared by a `write`, so Notion’s version history keeps each change’s note with it.

**Child pages** have only a title (its form: § Layout and root, Unmapped paths), so the whole document goes in the body: the frontmatter, when present, as a first block fenced as ```` ```yaml ```` holding the lines between the `---` markers verbatim (code is stored literally, so key order and values survive as written), then the body. `read` renders a leading `yaml` fence back as `---`, its lines, `---`, then the body. A child page carries no `Change Note`; its `reason` is dropped.

## Rendering: plugin markdown ↔ Notion

Edit anchors match the document as `read` returns it (`store.md`), so `read` returns plugin markdown and `write` sends Notion’s enhanced markdown (`notion://docs/enhanced-markdown-spec`). Each rule is *observed* unless marked:

- **Backslashes and specials** (outside code): write doubles every `\`; read removes the backslash before **any** ASCII punctuation character, scanning left to right so `\\` yields `\`, and leaves a backslash before anything else alone. Notion escapes more than its documented set (*observed (2026-10-17)*: `6:00` came back `6\:00`), and every `\` an author wrote reaches Notion doubled, so a single backslash before punctuation is always Notion’s. So `C:\Users`, an author’s `\[lit\]` or `## 1\.`, `[OPEN: Q-001]` and `5 * 3` all round-trip, and the same rule applies to property text (`Meta`, `Tags`) and titles.
- **Code:** inline spans and fenced blocks are sent and returned literally, never escaped or unescaped. A bare fence is sent as ```` ```plain text ```` (Notion otherwise guesses a language: a bare fence came back `javascript`), and `plain text` reads back as a bare fence; `text` also comes back `plain text`.
- **Blank lines:** read puts one blank line between blocks; consecutive list items and the lines of a block stay together. Runs of blank lines collapse to one (Notion strips them). `<empty-block/>` (an empty paragraph made in Notion) reads as nothing, so a later write drops it; writes never send it.
- **Line breaks inside a block:** write sends a single newline inside a paragraph, quote or list item as `<br>` (a bare newline can split the block); read renders `<br>` in a block as a newline, and inside a quote each line after a `<br>` starts with `> ` (so `<br><br>` reads as a lone `>` line, the source’s paragraph break within the quote). In table cells `<br>` stays `<br>` both ways; in properties (`Meta` included) it reads as a newline.
- **Indentation:** write sends a tab for every two spaces of nesting (the spec’s form; two spaces also nested, through three levels); read renders two spaces per tab.
- **Tables:** write sends each pipe table as `<table header-row="true">` with one `<tr>` per row and one `<td>` per cell, cell text in write form with `\|` sent as a bare `|` (Notion’s pipe-table parser splits a cell at `\|`, breaking the table). Read rebuilds a pipe table with a `|---|` separator, writing `|` in a cell as `\|` and keeping `<br>`.
- **Scene breaks:** a `* * *` line is sent escaped, `\* \* \*` (Notion otherwise makes it three nested empty bullets), and reads back as `* * *` (*observed (2026-10-17)*).
- **Mentions:** a page, database or data-source mention renders as `[<title>](<url>)` (the fetch fills in the title even when the tag was sent self-closing), which the connector turns back into a mention on write; a user mention renders as its name; a date mention renders as the date (`2026-10-16`, a range as `start – end`, with time and zone when set) and is written back as text. A mention never renders as nothing.
- **Autolinks:** Notion links anything that looks like a domain, writing `[x.md](http://x.md)`, in bodies, property text (`Meta` included) and titles; inside a path only the basename is linked (`chapters/chapter-02/[ch02-prose.md](http://ch02-prose.md)`) (*observed (2026-10-17)*). Read collapses every `[t](http://t)` and `[t](https://t)` outside code, where the URL is exactly the scheme plus the link text, to `t`; any other link is the author’s and stays.
- **Dropped:** `<page url=…>` and `<database>` child tags (other paths; `replace_content` keeps them).
- **HTML comments** are stored as a visible paragraph of literal text and read back as `<!-- … -->`; tell the author once that they show in Notion.
- **Leading `#` heading:** a create silently drops the body’s first block when it is a `# …` heading (sync and async); `replace_content` keeps it. So when a body to create starts with `# `, follow the create with `replace_content` of the same body (§ Operations), and `read` returns what was written.
- **Final newline:** Notion stores none. `read` ends every document with exactly one newline, and every comparison against stored content (write’s identical-content no-op, the concurrency guard, `migrate`’s resume check) ignores whether the content ends with one. So a source without a final newline comes back with one (*observed (2026-10-17)*: 31 files).
- **Unchanged:** curly quotes and dashes in bodies, headings to `####` (`#####` and `######` become `####`), `---` rules, single-paragraph block quotes, bullet items and their nesting, to-dos (`- [ ]`, `- [x]`), table cell text.

**Known limit: Notion normalizes markdown.** Notion re-serializes each block from its own model, so these come back changed and the read can’t restore them. All *observed (2026-10-17)* on a 148-file round trip; a later portable-markdown profile is meant to avoid them at the source.

- **Emphasis pairing:** a `***` close is mis-paired (`**Never says *why***` → `**Never says \*why***`, a literal asterisk now stored); bold around inline code splits into `****` runs (`**Then `x` to…**` → `**Then ****`x`**** to…**`); a code span inside italics gains bold; `~~**x**~~` → `**~~x~~**`; some opening `**` and strike markers are lost; `_x_` becomes `*x*`, intra-word underscores included (`a_-_Brainstorming_&` → `a_-*Brainstorming*&`). The changed text then reads back as stored, so an edit anchor taken from an older copy can stop matching.
- **Ordered lists renumber from 1:** a list continued after a heading or paragraph restarts (`8.` → `1.`).
- **Hard line breaks:** a trailing two-space break comes back as a plain newline (the spaces gone), which markdown renders as one joined line.
- **List spacing:** marker padding goes (`-   ` → `- `, `1.  ` → `1. `), loose lists tighten (blank or space-only lines between items removed), continuation-line indentation and trailing spaces are stripped, and a quote holding a list becomes a bare indented list.
- **Blank lines** appear between blocks the source ran together (a heading and the line under it, consecutive one-line paragraphs, a label line and its list), from the read rule above.
- **Rules and tables:** `------` → `---`; a raw HTML `<table>` becomes a Notion table and reads back as a pipe table (styles and `<colgroup>` dropped, cell text kept); pipe-table spacing normalizes (`| --- |` → `|---|`, an empty cell `|  |`).
- **Multi-paragraph quotes** become one quote block joined by `<br><br>`; the `<br>` rule above restores the `>` lines, so a quote whose continuation lines had no `>` (lazy continuation) comes back with them.
- **Non-breaking spaces** become ordinary spaces.

So a stored document is not always byte-identical to its source; `init` keeps local intake originals for that reason, and `migrate` says so once.

**Truncation:** if a fetch reports `truncated`, `unknown_block_count` or `unknown_block_ids`, fetch each listed block id and splice its content in at its `<unknown url=…>` placeholder, in order, treating a truncated part the same way. The read fails, naming the page, when a fetch is truncated but lists no ids, when a part can’t be fetched, or when any part is still marked truncated after splicing: a partial page is never returned as the document. (Unobserved through 12,700 words.)

## Stored and computed

Stored rows: every Assets and Chapters path, and child pages. No snapshots are written. **Computed** (`store.md` § Local-mode clauses): `state.md`, `.storystormer/config.json`, `decisions.md`, `questions.md`, `characters/_index.md`, `outline/_index.md`, `voice/README.md`. `read` renders them as below. A `write` of one is diffed against the **baseline read** its content was prepared from (an `edit`, against the read it was applied to), never a fresh rendering that may already hold another session’s rows, and each change goes through the writable realization listed. Anything with no realization is refused by name, never dropped silently.

**What Exists** (standalone, or a book’s `state.md` over that book’s rows plus the shared root rows), recomputed on each read in `file-schemas.md`’s line order: Primer, Treatment, Manifest, Structure from their Assets rows (`Version`, `Last Updated`, `built_from_decisions` and `target_chapter_count` from `Meta`), a line whose row doesn’t exist rendering `not yet created` (`- **Treatment** — not yet created`); Character bios as `<Name> (<Type>, ~<Body Words>w)`; Worldbuilding as `<Name> (<Category>)`; Voice (`sample` when a writing-sample or voice-sample row exists, `+ style guide` when the style-guide row does, else `README only`); Chapter outlines, Blueprints, Prose chapters and Notes (Chapters rows per `Artifact` against the structure’s chapter count, or a count with no denominator, `6 written`, when there is no structure row; prose counts a chapter with a prose row or any scene row, skipping rows whose `Status` is `retired`; Notes adds how many are stale, `Meta` `prose_version` below the chapter’s prose `Version`, and the sum of `Open Proposals`); Decisions (rows in scope, `Scope` = `series` or `book-<slug>` for a book, and how many are integrated: standalone, the `Integrated into treatment` line says `yes`; series, the `<slug> treatment` line does); Open questions (`Status` = open, in scope, counted by `Priority`).

**Series root `state.md`** renders What Exists in the shape of `file-schemas.md` § Series-level state.md: Series document (the `series.md` row’s `Version` and `Last Updated`, and the rows of its Cross-Book Setups and Payoffs table), Shared manifest (version, date, counts), Shared character bios (counts by `Type`), Shared decisions (total, and counts by `Scope`), then one line per book row by `Book Order`: title, primer and treatment versions, outline and prose counts, `Stage`.

**Log entries** (`file-schemas.md` § `decisions.md`, § `questions.md`) render from one row each, and the rendering returns the entry exactly as the source wrote it unless a property was changed in Notion since. *Observed (2026-10-17)*: real logs are richer than the columns (extra bold fields, free paragraphs, status prose, header suffixes, a retained second copy of a question’s fields), and a column-only rendering lost about 1,350 words of one project’s questions.

- **Parsing on write.** The header gives `Number`, then `Date` and `Type` (decisions) or `Priority` and `Category` (questions), each select per § Frontmatter ↔ properties, Values. Below it a **field** starts at a line beginning `**<Label>**:` and runs to the line before the next such line, so free paragraphs, sub-lists and bold run-in paragraphs (`**Why it works.** …`) ride with the field above them. The first occurrence of each mapped label goes to its property, the value verbatim after `**<Label>**: ` (a value that starts on the next line, such as a `Possible approaches` list, keeps its leading newline). Decisions: `Scope`, `Affects books`, `Topic` → `Name`, `Summary`, `Details`, `Affects`, `Source`, the first run of consecutive `**Integrated into …**` fields → `Integrated` (every line as written, in order: `**Integrated into treatment**: no`, `**Integrated into structure**: yes (<date>)`, or a series’ `**Integrated into**:` with its book lines), `Superseded by` → the later row’s `Supersedes`, with any text after its `D-###` (` — narrowed by …`) kept on the placeholder line (below). Questions: `Scope`, `Affects books`, `Title` → `Name`, `Question`, `Why it matters`, `Possible approaches`, `Dependencies`, `Source`, `Date`, `Status`. Any other field (`**Resolves**`, `**Open**`, `**Note**`, `**Midpoint update, 2026-08-16**`), a repeat of a mapped label, and text before the first field stay in `_layout` (below). An import sets nothing the entry lacks: no `Source`, and a Questions `Date` that only records the row’s creation goes in `_derived`; an entry with no `Topic` or `Title` gets a short `Name` derived from its Summary or Question, also in `_derived`, so no `**Title**` line appears.
- **Status.** `Status` ← the state the status text names (`open`, `resolved`, `invalidated`; the closest for any other wording, `half-resolved` → `open`), `Resolved By` ← the row of its first `D-###` when resolved, `Resolution` ← the prose after the status word and its parenthetical (`midpoint candidate identified, act climax undecided`, with any paragraphs under it), or an invalidation’s reason. The canonical form the properties render is `open`, `resolved (D-<n>)` or `invalidated (<Resolution>)`, the first two followed by ` — <Resolution>` when it is set, so the prose renders for every status.
- **`Meta` on a log row** is YAML text holding, each only when needed: `_as_written` with **one entry per header part**, `date`, `type`, `priority`, `category`, each `{stored: <the property value>, value: <the source’s text for that part>}` (a remapped type or category, a case change: `category: {stored: Story Structure, value: structure}`), plus `suffix: {value: <text after the last part>}` (` ✅ RESOLVED`; on a question it also records `stored: <Status>` and covers `Status`, so it drops once the question is reopened), and `Status: {stored: <the canonical status>, value: <the source’s status text>}` (`**resolved (D-029)** — Tommy. …`, `✅ resolved 2026-08-17 (D-068). …`); `_derived`; and `_layout`, the entry below its header verbatim with each mapped field’s first occurrence replaced by a line holding `⟦<Property>⟧` (followed by its tail for `Supersedes`) (a YAML literal block, `|2-` when it opens with a blank line), written whenever the entry isn’t the default rendering below (another field order, an extra field, no blank line after the header).
- **Rendering.** The header is `## D-<Number> · <Date> · <Type>` or `## Q-<Number> · <Priority> · <Category>`, each part taken from its `_as_written` entry while that entry’s property still holds `stored`, else from the property, then the `suffix` while it applies. Parts are independent: changing only `Priority` in Notion keeps the source’s `structure` and its ` ✅ RESOLVED`. Then `_layout`, each `⟦<Property>⟧` line replaced by its field: `**<Label>**: <value>` (the label alone on its line when the value starts with a newline or a list item), `Integrated` verbatim, `**Superseded by**: D-<n>` from the `Superseded By` row followed by the placeholder line’s tail, `**Status**:` with `_as_written.Status`’s `value` while its `stored` is still the canonical status, else the canonical status. A placeholder whose property is empty renders the bare label (`**Dependencies**:`), so a field the source left empty survives; a field the default layout would show drops when its property is empty; a property set since, which `_layout` doesn’t name, goes after the field before it in the default order; a property in `_derived` renders only once it differs from the recorded value. With no `_layout`, the default: the header, a blank line, then decisions `**Scope**` and `**Affects books**` (series only), `**Topic**`, `**Summary**`, `**Details**`, `**Affects**`, `**Source**`, `Integrated`, `**Superseded by**`; questions `**Scope**`, `**Affects books**` (series), `**Title**`, `**Question**`, `**Why it matters**`, `**Possible approaches**` (a value typed in Notion as bare lines renders one `  - ` line per line), `**Dependencies**`, `**Source**`, `**Date**` (only when the source entry had one or it was set in Notion since: a `Date` in `_derived` is the row’s creation date and doesn’t render), `**Status**`; empty fields omitted. Entries are separated by one blank line (a longer gap in the source collapses to one); the page bodies of these rows are not rendered.

**IDs.** `Number` is the project’s own sequence, rendered zero-padded to three digits (`D-018`; four past 999). A new row takes one more than the project’s highest (query sorted by `Number` descending, `limit: 1`). **Imports** (`migrate` copying a log in, which keeps its numbers) are the exception: the row’s `Number` is the entry’s own when no row of the project holds it, so gaps survive and references stay true; only a real collision takes the next free number, with its references rewritten as below. After creating, query the project for that `Number`: if two rows hold it, the one whose page id sorts later is renumbered to the new highest plus one and checked again (both sessions see the same pair, so exactly one moves). When a row ends up with a different number from the entry the skill wrote, rewrite every reference to the provisional ID in the same submission (another new entry’s `**Dependencies**`, `**Superseded by**`, `resolved (D-###)`, prose that cites it, and the entry’s own `_as_written` header parts and `_layout`) before sending, or on rows already sent after a race, and report each ID used, which is how `decision-capture` learns it. Notion’s `UNIQUE_ID` is not used (*observed*: its prefix needs two or more characters, it counts per database across every project sharing it, it renders as a bare `1`, `2`, and a property named `ID` becomes `userDefined:ID`).

**Several rows from one call.** A computed-document write or edit can touch several rows (two new decisions and a supersession). Apply the changes in document order, recording each one (the row and its prior values, or that it was created); if one fails, undo the completed ones in reverse (prior values back, created rows trashed under the same approval) and report what was attempted. If an undo fails, name the rows it left changed.

**`open` and `history` of a computed document.** `open` gives the bound Projects row’s URL (its relation lists reach every source row) and shows the rendering in the chat: a stated exception to `store.md`’s never-paste rule, because the document exists only as that rendering. `history` names the rows that hold it (the Projects row for `state.md` and `config.json`, each entry’s row for the logs) with the version-history route below.

## Operations

| Operation | Realization |
|---|---|
| `list(glob)` | From the path map, work out which rows can match the glob, query each data source with those filters (§ Queries), and map rows back to paths. Add computed documents whose sources exist (`state.md`, `config.json` and `voice/README.md` always; `decisions.md` or `questions.md` with at least one row or a non-empty `Decisions Head` or `Questions Head`, since a log with a head and no entries is still a document; `characters/_index.md` with a character; `outline/_index.md` with a structure row, per book) and child pages whose path titles match. Filter by the glob in the model |
| `read(path)` | Selector query, then one `notion-fetch` of the row, rendered per § Rendering (child pages per § Frontmatter ↔ properties). No row is a missing-path error. *Frontmatter only:* the selector query’s row properties, rendered, with no fetch (a child page still needs it). Computed documents render per § Stored and computed |
| `write(path, content)` | Computed → its writable realizations. Otherwise split frontmatter from body, check chapter identity, and run the selector query. **No row:** `notion-create-pages` with `parent.data_source_id` (or `page_id` = the bound row and title = the path in its title form, § Layout and root, for a child page), the properties per § Frontmatter ↔ properties, and `content` = the body in write form; when the body starts with a `#` heading, then `replace_content` with the same body (§ Rendering). **One row:** concurrency guard; skip if the current rendering equals `content`; `notion-update-page` `replace_content` with the body in write form plus every child `<page url=…>` tag the fetch showed, then `update_properties` per § Frontmatter ↔ properties (replacing a row). If the properties call fails after the content call, `replace_content` with the markdown fetched before the replace and report; the row never disappears. **Two rows:** stop and name both URLs |
| `edit(path, edits, reason)` | Concurrency guard, then apply the items in the model to the rendered read; any missing or ambiguous anchor fails the call with nothing sent. A computed document, a child page, or an item whose anchor spans the frontmatter and the body becomes a whole-document change: the edited document goes through `write` (or the computed realizations). Otherwise body items go to **one** `update_content` call, one `content_updates` entry per item, with `old_str` = the span of the fetched Notion markdown that renders as the anchor and `new_str` = the replacement in write form (`replace_all` → `replace_all_matches`; the connector applies all or none, *observed*). Then one `update_properties` call: the changed frontmatter properties, `Meta` with the overrides for those keys refreshed (§ Frontmatter ↔ properties, Overrides stay true), the rebuilt binding-maintained ones when the body changed, and `Change Note` = `reason`. If `update_content` rejects an anchor the model accepted, send the whole edited document, frontmatter and body, through `write`. If `update_properties` fails after `update_content`, restore the body with `replace_content` from the fetched markdown and report. Report connector `warnings` (it silently corrects near-miss anchors; the model’s exact check is the guarantee) |
| `history(path)` | The connector can’t read page history. Return the row’s URL and say: in Notion, open the page, then ••• → Version history (how far back depends on the workspace’s plan) |
| `open(path)` | The row’s or child page’s URL (computed documents per § Stored and computed) |
| `move(from, to)` | **Same database:** run the destination’s selector query first; a row there stops the move and names both URLs. Then change the selector properties (`Slug` and `Name` for a renamed character, `Category` for a re-filed entry, `Chapter` and `Name` for a renumbered chapter, `Book` for a document moving into or out of `books/<slug>/`). **Child page:** retitle (the title form, § Layout and root), after checking no child page of the destination parent holds the title; to another parent, `notion-move-pages` first. **Across databases:** `read`, `write`, `delete`. **Computed documents** are skipped and the report says so: they follow their rows (series conversion’s `outline/_index.md` moves when the structure and chapter rows take the book’s `Book`) |
| `delete(path)` | `notion-delete-pages` with `user_confirmed: true` when the path is in the approved plan (see Capabilities). Trash is recoverable (Notion’s Trash, or the connector’s restore). Computed documents can’t be deleted |

**Batched creates and cost.** `notion-create-pages` takes up to 100 pages in one call, so a run creating many rows in one data source (a migration’s documents, one log’s entries) or many child pages under one parent sends them in batches, each one call plus its async poll, and follows only the `#`-opening bodies with `replace_content`. Estimate a migration into Notion at a few calls per batch of documents (create and poll), one more per heading-led body (its `replace_content`), one per five to ten log entries, plus the numbering check, the source reads and about ten for a new hub (*observed (2026-10-17)*: 34 rows, 109 log entries and 56 child pages took about 310 Notion calls; logs went 5–10 rows per create).

**Async:** every create and update passes `allow_async: true`. When the reply is an `async_task`, poll `notion-get-async-task` (honour `poll_after_seconds`) until `succeeded` before reporting, reading back, or the next dependent call; `failed` is a failed call.

**Concurrency guard:** before a write or edit that replaces an existing row, re-run its selector query and compare `Version` with the baseline (a child page: re-fetch and compare its fence’s `version`, or its whole rendering when it has none). Rows without a `Version` compare only what the change touches. Projects rows (`state.md`, `config.json`): re-fetch and compare each property and section being changed with the baseline read, What Exists excluded (it is recomputed on every read). Decisions and Questions rows carry no `Version` and are append-mostly: a new entry needs no guard (§ IDs settles its number), and a field change re-reads that row and compares the field with the baseline.

**`replace_content` and children:** a replace that omits a child page or database is refused with a list (*observed*). Keep their tags in `new_str`; never pass `allow_deleting_content` unless the author has approved deleting exactly what that list names. The hub’s content is never replaced.

## Queries

Use **rows mode** (`mode: "rows"`, the data-source URL, structured filters and sorts), which works on every plan: the filters from § Path map (`relation_contains` the root for `Project`; `relation_contains` the book row, or `is_empty`, for `Book`; `Parent` `relation_contains` the root for book rows), plus `enum_is` for selects, `number_equals` for numbers and `string_is` for text, with `limit: 100`. **A `relation_contains` value is the related page’s full URL** as the connector returns it (`https://www.notion.so/<id>`), never a bare page id: a bare id, dashed or not, is silently ignored and the query returns every project’s rows (*observed*, 2026-10-17), which would pull other projects into logs, listings, the next-number query and the duplicate checks. When a result could span projects (any count, number or duplicate check), confirm each row’s `Project` relation holds the root before trusting it. Rows mode returns properties, not bodies, and has no cursor (*observed*: 100 rows and `has_more`). Past 100:

- **Chapters, Decisions, Questions:** sort by `Chapter` or `Number` ascending; re-query with `number_greater_than_or_equal_to` the last key, drop URLs already seen, and repeat until fewer than 100 come back (*observed* on 101 Chapters rows). Ties can’t stall it: `Number` is unique per project, and one `Chapter` holds at most a few dozen rows (four artifacts plus scenes, per book).
- **Assets:** query one `Kind` at a time. If a single `Kind` returns 100, fall back to SQL mode with `ORDER BY url LIMIT 100 OFFSET n` (`url` is unique, so pages never overlap; take quoted column names from the fetched `<sqlite-table>`), which is unlimited only on Business or Enterprise with Notion AI and shares a workspace limit elsewhere. Failing that, fetch the root row’s `Assets` list, fetch the rows not yet seen, and apply the query’s `Kind`, `Book`, `Slug` and `Category` filters to them in the model, since the list holds every Assets row of the project.

SQL is never required, and nothing queries two data sources in one call.

## Locate

1. **Hubs.** Find hubs (§ Layout and root). Each complete hub is searched; each partial hub is reported with its link and the databases it lacks, never searched or repaired. No hub means no projects here, which is not a failure.
2. **Projects.** Query each complete hub’s Projects data source (its URL from the hub fetch) in rows mode with no filter, sorted by `Last Session` descending, `limit: 100`. Rows with an empty `Parent` are projects; rows with a `Parent` are books, named under their series by `Book Order`. If 100 rows come back, query again with `Parent` `is_empty` for the projects alone, and say the book lists may be incomplete.
3. **Fields** come from the row properties, the values a frontmatter-only read of `state.md` renders (§ Stored and computed), so no row is fetched: title ← `Name`, slug ← `Slug`, `stage` ← `Stage` (or its `_as_written` value in `Meta`), `last_session` ← `Last Session`, project type ← `Project Type`, last edited ← `Last Edited` (Notion’s own last-edited time of the Projects row, which every session’s `state.md` update moves; empty on a hub created before the column, § Schema upgrades, and reported as unknown). The root is the row’s page id.

**Returns**, per project: the hub (its link, and whether it sits at the private root or in a teamspace), title, slug, root, stage, last session, last edited and, for a series, its books. Last edited is what tells a same-slug pair apart (*observed (2026-10-17)*: a moved copy carries the source’s `last_session` unchanged, so both copies showed the same date): show it beside each copy of a slug that appears twice. Several complete hubs → every hub’s projects, labeled by hub. Keep the hub’s five data-source URLs with the pick, so binding needs no second search. **Fails** when search errors; a hub whose fetch or query errors is reported against that hub, beside the others. **Cost:** one `notion-search` (plus `notion-get-self` where used), one `notion-fetch` per result titled exactly `StoryStormer` at a hub location, and one query per complete hub (two past 100 rows).

## Scaffolding a project (`init` on Notion)

1. **Hub.** Find hubs (§ Layout and root). One complete hub → use it and its databases. Several → ask which. Any partial hub → stop and tell the author; don’t repair it by guessing and don’t create another. None → ask once whether it goes at the private root (default) or in a teamspace (`notion-get-teams`), then `notion-create-pages` titled `StoryStormer` with no parent (private) or `parent.teamspace_id`.
2. **Tables**, for a new hub only: the five `CREATE TABLE`s in order, then the two `ADD COLUMN`s; keep the returned data-source URLs.
3. **Project row.** First query the hub’s Projects data source for `Slug` = the slug: an existing row (a retried init, say, after a failed pointer write) stops init with the question Dropbox asks, another slug or whether they meant that project. Otherwise one Projects row from the new `state.md` frontmatter (`Storage Kind` = notion) with the new `state.md`’s body except What Exists (its opening text and sections, `## Summary`, `## What's Next`, `## Last Session`) as its content, sent per § Stored and computed (`insert_content` on a row created without it); in a series, the series row and one row per book with `Parent` set and `Book Order` 1…n.
4. **Pointer.** When the session has an open folder, write its `.storystormer/config.json` through the local binding as exactly `{"storage": {"kind": "notion", "root": "<row page id>"}}` and nothing else, so resolution finds the project next session. The pointer is read only by resolution; `store.read('.storystormer/config.json')` on this binding returns the computed config (§ Stored and computed), never the pointer.
5. **Intake.** Continue `init` through the contract; intake documents become rows. Notion keeps no snapshot folders, so init’s intake archive is `.storystormer/intake/<timestamp>/` (the snapshot-folder timestamp form, so a re-run keeps the earlier record), as child pages: `superseded-prose/<original filename>`, `intake-original-names.md`, and `sources/<original filename>` for each text source init read but didn’t re-file. **The same layout whoever writes it:** an archive is the tree init writes into its snapshot folder on a snapshots store, so `migrate`, re-filing a source’s `.storystormer/history/<timestamp>-init/`, writes `.storystormer/intake/<timestamp>/` + each file’s path inside that folder unchanged (an older archive’s `originals/` and `superseded/` stay as they are), where `<timestamp>` is the folder’s name without its `-init` suffix (`2026-05-11T14-33-init` → `2026-05-11T14-33`; an older `2026-08-15-init` → `2026-08-15`). Because this binding normalizes markdown, init keeps every local intake original (never deletes it) and says so in the report. Notion holds markdown only, so a non-markdown original (`.docx`, `.rtf`, `.scrivx`, …) stays where it is in the open local folder, is never deleted, and is named in the report with the canonical path it would have had (with no open folder, the report says it was not stored). Attaching it as a file needs the connector’s file upload plus an HTTP POST, which the plugin can’t require.

## `checkpoint`

`history: native`, so `checkpoint` refuses with exactly: “Nothing to checkpoint: this project lives in Notion, which keeps every page’s version history itself (open any page, then ••• → Version history). No snapshot was written.”

## Worked example: `character-bio` creates `characters/marlowe-reyes.md`

1. **Resolve** once: `kind: notion`, root = the project row’s id; the hub fetch gave the five data-source URLs.
2. **Read inputs** (`manifest.md`, `treatment.md`): rows query Assets (`Project`, `Book` empty, `Kind` = manifest), fetch, render.
3. **Write.** Selector query Assets (`Project`, `Book` empty, `Kind` = character, `Slug` = marlowe-reyes): no row. `notion-create-pages` into Assets with `Name` “Marlowe Reyes”, `Kind` character, `Slug`, `Type` Protagonist, `Tags` “[POV character, the bureau]”, `Version` 1, `Last Updated`, `Meta` “manifest_version: 2\ntreatment_version: 7”, `Body Words`, `Project`; content = the bio body in write form; wait on the async task.
4. **No snapshot or guard:** the row is new, and the report says Notion keeps the versions. `characters/_index.md` is computed, so its regeneration step is skipped; the `state.md` update writes only the frontmatter keys and Last Session.
5. **Open:** hand the author the row’s URL.

## Adversarial case: `blueprint` gathers every character in chapter 12

1. `store.read('chapters/chapter-12/ch12-outline.md')`: rows query Chapters with `Project` `relation_contains` root, `Book` (`is_empty`, or the book row in a series), `Chapter` `number_equals` 12, `Artifact` `enum_is` outline, then fetch. The row’s `Related Assets` holds the URLs of the Assets rows the outline names.
2. `store.list('characters/*.md')`: rows query Assets with `Project`, `Book` `is_empty` and `Kind` `enum_is` character, which returns `Name`, `Slug`, `Type` and the URL of each.

The characters whose URLs are in chapter 12’s `Related Assets` are the indexed set. `blueprint` still reads the outline body (and chapter 11’s notes End State) and adds any named character the index missed, since the index lags edits made in Notion.
