# Notion Binding

The store is a Notion workspace. Each project is one row in a **Projects** database; its documents are rows in five more databases (Assets, Chapters, Decisions, Questions, Journal) under a hub page, and anything the path map doesn’t cover is a child page of the project’s row. Skills still pass paths; this binding maps each path to a row and its properties. Read `references/store.md` first; this document only says how each operation is realized here.

## Capabilities

```
identity: id · write: native · edit: native · list: query · history: native · open: url · size: ~5k words sync, larger async · confirm: none
```

**Size in practice:** every create and update passes `allow_async: true` and waits for the task (§ Operations), so the write size never changes the procedure, except in the synchronous sends of a call that fails to queue, and of the rest of the session once two in a row have (§ Operations, Async). One fetch returned a 12,700-word page (69 KB) whole, with no `truncated` flag.

**Confirmation:** the connector asks nothing except for trashing, and that it enforces: `notion-delete-pages` refuses unless the user has explicitly asked, in this conversation, for that specific page to go (*observed (2026-10-25)*: a trash sent under a write’s approval was refused). So the binding trashes only in a real `delete`, one the author asked for (§ Operations, `delete`), and never to clean up after itself: a rollback or undo restores a row in place, or **withdraws** a row the session just created (§ Withdrawing a row).

## Tools

The Notion connector’s `notion-search`, `notion-fetch`, `notion-create-pages`, `notion-update-page`, `notion-create-database`, `notion-update-data-source`, `notion-query-data-sources`, `notion-get-async-task` and `notion-delete-pages`. Optional: `notion-move-pages` (`move` of a child page between rows), `notion-get-teams` (a teamspace hub at `init`) and `notion-get-self` (the user id that narrows hub search). Some surfaces expose the same tools without the `notion-` prefix; either spelling satisfies the tool check. No shell.

**Verified on:** 2026-10-16 (live probes), 2026-10-17 (a live local → Notion → Dropbox → local migration ring of a 148-file project) 2026-10-24 (a markdown probe of 243 constructs, `tests/markdown-profile/probe-results.md`) and 2026-10-25 (the SB7 live loops and ring); findings are marked *observed*, those from the ring *observed (2026-10-17)*, those from the markdown probe *observed (2026-10-24)*, those from SB7 *observed (2026-10-25)*.

## Layout and root

- **Hub:** a page titled exactly `StoryStormer` at the workspace’s private root (empty ancestor path) or at a teamspace’s top level (an ancestor path naming only the teamspace; that form is unobserved), whose content holds the databases as `<database>` children named Projects, Assets, Chapters, Decisions, Questions and Journal (a hub created before the journal existed lacks Journal until § Schema upgrades adds it). One `notion-fetch` of the hub returns each database’s `data-source-url` (`collection://…`); every query and create uses those.
- **Finding hubs** (the locator and `init` both use this): `notion-search` for `StoryStormer` with `page_size` raised (25) and, where the surface offers it, `filters.created_by_user_ids` set to the connected user (`notion-get-self`); search is fuzzy and returns 10 by default. The creator filter hides a hub a colleague created in a teamspace, so when the filtered search finds no complete hub, search once more without it before concluding there is none. Read each result’s title and `path` from the search response itself (*observed (2026-10-17)*: results carry both, so a non-hub hit needs no fetch; one cost a 60 KB fetch): absent or empty is the private root, a teamspace name alone is a teamspace’s top level, anything longer is not a hub location. Fetch only the results titled exactly `StoryStormer` at a hub location, to see which databases they hold. A hub created earlier in this run may not be indexed yet: reuse the id you created rather than searching for it. A **complete** hub holds the five core databases (Projects, Assets, Chapters, Decisions, Questions), with or without Journal; a **partial** one holds one to four of the five; a page with none is not a hub (a workspace may hold such a page elsewhere, and search is fuzzy). § Locate searches only complete hubs and reports the partials; `init` stops on a partial (§ Scaffolding).
- **Root** (`config.json` `storage.root`): the page id of the project’s Projects row. Resolution’s layout read (`store.md` § Resolve step 4, the computed config) fetches that row once per session, however the session was bound (a pointer, the locator, `init`), and the session keeps its `Slug` and `Layout` from that fetch for every rendering that needs them (an entry’s `storystormer_project`, the layout rules). In a series the root is the series row; each book is a Projects row whose `Parent` is the series row (its `Books` relation fills itself), ordered by `Book Order`.
- **Unmapped paths** are child pages of the bound row (the book’s row under `books/<slug>/`), titled with the path. Notion parses a page title as inline markdown (*observed (2026-10-17)*: a `.md` basename comes back autolinked, `notes/[craft-document.md](http://craft-document.md)`, and `_x_` as italics, so four intake pages mapped back to the wrong path), so the title is sent as the path in one inline code span (`` `notes/craft-document.md` ``), inside which nothing is parsed (*unobserved*: after the first child-page create of a run, fetch it and check its `<properties>` title is that span; if not, retitle that page with the fallback form, a backslash before every ASCII punctuation character, fetch it again to confirm, and use that form for the rest of the run). **Reading a title:** take it from the page’s `<properties>` title or the parent’s `<page>` tag, never the fetch’s top-level `title`, which drops the markup (*observed (2026-10-17)*: `Jon_Hartley_-CharacterProfile.md`); a title in a code span is the path exactly as it stands between the backticks, with nothing unescaped, collapsed or decoded inside it (a literal `\` in a filename survives, and so does an `&amp;` an author’s filename holds: no entity inside a `<code>` title is decoded; *observed (2026-10-24)*: such titles came back with `&amp;`, though whether Notion stores `&amp;` or `&` is *unverified*); any other title has its autolinks collapsed and escapes removed per § Rendering, and in a title written before this rule read `*…*` as the `_…_` it came from (a path holds no `*`).

## Path map

The descriptor table every operation uses; never branch on path strings outside it. **Filters:** Assets and Chapters selectors also filter `Project` = root and `Book` = the book’s row under `books/<slug>/…` (empty otherwise). Decisions, Questions and Journal filter `Project` only: they have no `Book`, a series keeps them at the root (the journal is the series’), and an entry’s scope is its `Scope` field. Projects rows are addressed by page id: the root, or a book row (`Parent` = root, `Slug` = slug).

| Path | Database | Selector |
|---|---|---|
| `state.md` · `.storystormer/config.json` | Projects | the root row (the book row for `books/<slug>/state.md`): computed |
| `primer.md` · `treatment.md` · `manifest.md` · `series.md` · `outline/structure.md` · `.storystormer/genre-reference.md` | Assets | `Kind` = primer · treatment · manifest · series · structure · genre-reference |
| `characters/<slug>.md` | Assets | `Kind` = character, `Slug` = slug |
| `worldbuilding/<folder>/<slug>.md` | Assets | `Kind` = worldbuilding, `Slug` = slug, kebab-case of `Category` = folder |
| `research/<slug>.md` · `voice/samples/<slug>.md` | Assets | `Kind` = research · voice-sample, `Slug` = slug |
| `voice/style-guide.md` · `voice/writing-sample.md` | Assets | `Kind` = voice-style-guide · voice-writing-sample |
| `characters/_index.md` · `outline/_index.md` · `voice/README.md` | none | computed from queries |
| `chapters/chapter-NN/ch<NN>-<artifact>.md` | Chapters | `Chapter` = NN, `Artifact` = outline · blueprint · prose · notes |
| `chapters/chapter-NN/scenes/ch<NN>-scene-MM.md` | Chapters | `Chapter` = NN, `Artifact` = scene, `Scene` = MM |
| `decisions/D-###.md` · `questions/Q-###.md` | Decisions · Questions | `Number` = ### (§ Frontmatter ↔ properties, Entries) |
| `decisions/_index.md` · `questions/_index.md` | none | computed from rows queries |
| `journal/<YYYY-MM-DD>-s<NN>.md` | Journal | `Date` = the date, `Session` = NN read as a number; a path, a `list` entry and a selector always write `Session` zero-padded, two digits and three past 99 (`s07`, `s100`) |
| `decisions.md` · `questions.md` | Decisions · Questions | old layout only: every row of the project, computed (§ Old-layout projects) |
| `.storystormer/history/**` · `chapters/*/.history/**` | none | never exist (`history: native`) |
| anything else (`kitbash/`, `.storystormer/canon-sync/*.md`, `.storystormer/intake/**`, …) | child page | parent = bound row, title = the path |

**The layout** is the root row’s `Layout` (§ Stored and computed, the config). In layout 2 the entry paths, the two indexes and the journal exist and the two logs don’t; in the old layout (`Layout` empty) it is the reverse, and the project’s Decisions and Questions rows render only as the logs (§ Old-layout projects).

## Schema

`init` runs this through `notion-create-database` with `parent` = the hub, in this order (later tables relate to earlier ones; substitute each returned data-source id), then adds the two self-relations with `notion-update-data-source`, because a table can’t reference its own id before it exists.

```sql
-- 1 Projects
CREATE TABLE ("Name" TITLE, "Slug" RICH_TEXT, "Project Type" SELECT('novel','novella','short_story','screenplay','series'),
  "Genre" RICH_TEXT, "Genre Secondary" RICH_TEXT, "Logline" RICH_TEXT,
  "Stage" SELECT('concept','brain-dump','brainstorming','treatment-drafted','treatment-refined','canon-development','outlining','outline-drafted'),
  "Initial Maturity" SELECT('concept','brain-dump','brainstorming','treatment-drafted','treatment-refined'),
  "Surfacing Mode" SELECT('active','on-request'), "Created" DATE, "Last Session" DATE, "Session Count" NUMBER,
  "Target Word Count" NUMBER, "Current Focus" RICH_TEXT, "Book Order" NUMBER, "Layout" NUMBER,
  "Last Edited" LAST_EDITED_TIME, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 2 Assets
CREATE TABLE ("Name" TITLE, "Project" RELATION('<projects-ds>', DUAL 'Assets'), "Book" RELATION('<projects-ds>'),
  "Kind" SELECT('primer','treatment','manifest','series','structure','genre-reference','character','worldbuilding',
    'voice-style-guide','voice-writing-sample','voice-sample','research'),
  "Slug" RICH_TEXT, "Type" RICH_TEXT, "Category" RICH_TEXT, "Tags" RICH_TEXT, "Version" NUMBER, "Last Updated" DATE,
  "Primer Version" NUMBER, "Authorship" SELECT('author_written','ai_generated','ai_generated_author_revised'),
  "Body Words" NUMBER, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 3 Chapters
CREATE TABLE ("Name" TITLE, "Project" RELATION('<projects-ds>', DUAL 'Chapters'), "Book" RELATION('<projects-ds>'),
  "Chapter" NUMBER, "Artifact" SELECT('outline','blueprint','prose','notes','scene'), "Scene" NUMBER,
  "Title" RICH_TEXT, "POV" RICH_TEXT, "Act" RICH_TEXT, "Summary" RICH_TEXT, "Status" SELECT('drafted','revising','revised','retired'),
  "Authorship" SELECT('author_written','ai_generated','ai_generated_author_revised'), "Version" NUMBER,
  "Word Count" NUMBER, "Last Updated" DATE, "Related Assets" RELATION('<assets-ds>'), "Markers" RICH_TEXT,
  "Open Proposals" NUMBER, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 4 Decisions
CREATE TABLE ("Name" TITLE, "Number" NUMBER, "Project" RELATION('<projects-ds>', DUAL 'Decisions'),
  "Type" SELECT('plot','character','worldbuilding','structure','theme'), "Date" DATE, "Scope" RICH_TEXT,
  "Affects Books" RICH_TEXT, "Source" RICH_TEXT, "Integrated" RICH_TEXT, "Retracted" DATE,
  "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 5 Questions
CREATE TABLE ("Name" TITLE, "Number" NUMBER, "Project" RELATION('<projects-ds>', DUAL 'Questions'),
  "Priority" SELECT('critical','important','nice_to_resolve'),
  "Category" SELECT('Story Structure','Character','Plot','Worldbuilding','Theme','Setting','Pacing'),
  "Scope" RICH_TEXT, "Affects Books" RICH_TEXT, "Source" RICH_TEXT,
  "Status" SELECT('open','resolved','invalidated'), "Resolved By" RELATION('<decisions-ds>'),
  "Date" DATE, "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- 6 Journal
CREATE TABLE ("Name" TITLE, "Project" RELATION('<projects-ds>', DUAL 'Journal'), "Date" DATE, "Session" NUMBER,
  "Skills" RICH_TEXT, "Decisions" RICH_TEXT, "Questions" RICH_TEXT, "Source" SELECT('plugin','app'),
  "Meta" RICH_TEXT, "Change Note" RICH_TEXT)
-- then the self-relations:
-- on Projects
ADD COLUMN "Parent" RELATION('<projects-ds>', DUAL 'Books' 'books')
-- on Decisions
ADD COLUMN "Supersedes" RELATION('<decisions-ds>', DUAL 'Superseded By' 'superseded_by')
-- a hub created before prose could be retired: on Chapters, before the first `status: retired` write
ALTER COLUMN "Status" SET SELECT('drafted','revising','revised','retired')
```

The `DUAL` relations to Projects give the Projects row `Assets`, `Chapters`, `Decisions`, `Questions` and `Journal` lists; one fetch of the row returns each list whole (*observed*: 101 entries). A journal entry’s `Decisions` and `Questions` are its ID lists as text, not relations, so an ID is kept as written. Decisions `Type` and Questions `Category` are the app’s enums after AP0 Part B (`recordDecision.ts`, `createQuestion.ts`); a value outside them is stored as its mapped or closest option and kept verbatim (§ Frontmatter ↔ properties, Values).

**Old-layout columns.** A hub created by an earlier version also holds the columns its old-layout projects render from (§ Old-layout projects): Projects `Storage Kind`, `Decisions Head` and `Questions Head`; Decisions `Summary`, `Details` and `Affects`; Questions `Question`, `Why It Matters`, `Possible Approaches`, `Dependencies` and `Resolution`. Nothing removes them, since dropping a column deletes every project’s values in it; a layout-2 row leaves them empty, and once no project on the hub is in the old layout the author may delete them in Notion.

**Schema upgrades.** A hub created by an earlier version of this binding lacks what was added since: Decisions and Questions `Meta`; Projects `Last Edited` and `Layout`; Decisions `Retracted`; and the Journal database. The hub fetch lists the databases but not their columns: fetch each data source (its `<sqlite-table>` names them; *observed (2026-10-17)*: five fetches on an existing hub). In any run with an approved plan, before its first write to the hub, add what is missing, under that approval, and say so in the report: a column with `notion-update-data-source` (`ADD COLUMN "Meta" RICH_TEXT`, `ADD COLUMN "Layout" NUMBER`, `ADD COLUMN "Retracted" DATE`, `ADD COLUMN "Last Edited" LAST_EDITED_TIME`); the Journal with `notion-create-database`, `parent` = the hub and table 6 above with the hub’s Projects data-source id substituted, keeping its returned data-source URL with the others. On an unknown outcome, fetch the hub and look for a database titled Journal before sending the create again. Create the Journal before adding `Layout`, so a hub whose Projects has `Layout` always has a Journal; a layout-2 project on a hub without one is an error that names the missing database. Adding `Layout` changes no project: every existing row’s is empty, which is the old layout. `Last Edited` is computed by Notion and never written, so it arrives with whatever run first writes to the hub, not with a write that needs it. Reads and § Locate never add a column or a database: a missing column reads as empty, and Locate shows last edited as unknown until then.

## Frontmatter ↔ properties

**The rule:** `read` returns exactly the frontmatter the source wrote, keys, order and values, unless a property was changed in Notion since. **On write**, each frontmatter key lands in its property below and the markdown body becomes the page content. A key with no property goes into `Meta`, in the document’s order, as its source text, never re-serialized, so a value that isn’t valid YAML on its own still round-trips (*observed (2026-10-17)*: a `related: [[…]]` list). Path-derived properties (`Project`, `Book`, `Kind`, `Slug`, `Chapter`, `Artifact`, `Scene`, `Name` where no key supplies it) come from the path map.

**`Meta`’s storage form.** Notion strips the whitespace at the start of every line of a multi-line rich-text property when it stores it, and reads property text as inline markdown (*observed (2026-10-24)*: a `source:` value’s indented continuation lines came back unindented, invalid YAML, while a row written 2026-10-17 kept its indents; `_x_` came back as italics and `**Note**` as bold; the probes are in `tests/markdown-profile/probe-results.md` § Mini round trip). So `Meta` is literal text (§ Rendering, Property text: every ASCII punctuation character sent escaped), and no stored line of it starts with whitespace:

- **A key’s source text** is its first line and every line after it up to the next line that starts at the margin with anything but `- ` (another key, a comment, the end): indented lines, empty lines, and `- ` items at the margin, which YAML reads as a block list under the key (`tags:`, then `- a` and `- b`).
- **When that text is one line** (with any empty lines after it) and holds no non-breaking space, the line is stored as it stands (`manifest_version: 2`, `note: "Foo: Bar"`), and the empty lines after it as empty lines, which Notion keeps (*observed (2026-10-24)*).
- **When it spans lines** (a block scalar such as `revision: >-` or a prose `synopsis: |`, a plain or quoted scalar continued onto indented lines, a block list or map), it is stored as one line, `<key>: "<text>"`, and the key is named in `_lines`. `<text>` is everything after the key’s colon to the end of its source text, exactly: the space after the colon, the indicator, every line’s indentation, and every empty line, those at its end included (a `|+` scalar keeps them), as a YAML double-quoted string (`\\` for a backslash, `\"` for a quote, `\n` for each line break). `synopsis: |` over two indented lines is stored as `synopsis: " |\n  The tide turns.\n  Ada waits."`.
- **A non-breaking space** (U+00A0) in a frontmatter value: the fetch returns a plain space for one in a body (`markdown-profile.md` § Rewrite table), and property text is taken to read back the same way (*unprobed* for properties). So a mapped key’s property holds the value with a plain space and `_as_written` keeps the source’s text with `\u00a0` in its JSON string; an unmapped key holding one is stored in the multi-line form above (`<key>: "<text>"`, named in `_lines`) with each U+00A0 as `\u00a0`, even when its text is one line. Both escapes are ASCII, so the read returns the source’s bytes.
- **The binding’s `_` keys** come after the source’s, in the order `_lines`, `_keys`, `_as_written`, `_derived`, `_entry`, `_words`, `_layout`, each on one line, its value written as JSON (YAML flow style with every key and string double-quoted, so a key such as `no`, `on`, `null` or `2026-10-24` stays a string): `_keys: ["name", "species", "tier"]`, `_lines: ["synopsis"]`, `_as_written: {"category": {"stored": "Locations", "value": "location"}}`, `_derived: {"Type": "Major"}`, `_entry: 2`, `_words: 412`, and on an old-layout log row `_layout: "\n⟦Scope⟧\n…"` (§ Old-layout projects).

Only the `_` keys and the strings of the keys `_lines` names are parsed. **On read**, in this order: render the property text back (§ Rendering, Property text: `<br />` as a newline, every unescaped link collapsed to its text, then the backslash rule), so the stored lines stand as they were sent; decode each string `_lines` names; parse the `_` keys. A key in `_lines` renders as `<key>:` followed by its decoded string, which returns the source’s lines exactly, and every other line renders as it stands. Seven `Meta` keys belong to the binding (they start with `_`; a source key that starts with `_` stops the write, naming it), each written only when needed:

- **`_lines`:** the keys stored as one double-quoted string because their source text spans lines or holds a non-breaking space (above), in any order: `["synopsis", "revision"]`.
- **`_keys`:** the source’s frontmatter keys in its order (`["name", "species", "tier", "version", "last_updated"]`), whenever the default order would render them differently: that order is `file-schemas.md`’s for the document, restricted to the keys the source holds, then the other `Meta` keys in stored order (§ On read, below). So a source that lacks some keys and adds others needs no `_keys` when the keys it holds come in that order with its extra keys after them, and needs it otherwise, as does any document with no `file-schemas.md` order (research, voice). *Observed (2026-10-17)*: without it, 19 files came back reordered.
- **`_as_written`:** for each key whose value, rendered back from its property by the default rendering (§ On read, below), would not be the source’s exact text, quoting included, a map entry `"<key>": {"stored": "<the property value written>", "value": "<the source’s value text, quotes included>"}`: a select value outside the options (stored as the closest option, or empty when none is close: `stage: outlining — partial spine committed (chapters 1–3, D-067)` stores `outlining`), an old spelling the binding normalized (`author-written`), a legacy worldbuilding `category` (below), an empty or `null` value, a number-looking value of a text property written bare (`act: 1`, since the default renders text that would read as a number quoted, `act: "1"`, per `file-schemas.md` § Frontmatter values; *observed (2026-10-24)*: the ring’s three outlines and a blueprint came back `act: "1"` without this entry). The write compares mapped keys only, every one of them, so any mapped value whose source form differs from the default gets its entry; an unmapped key is stored in `Meta` as its source text and renders back as written, so it never needs one. An entry may instead be named by a **property** (§ Schema’s names; the old layout’s `Decisions Head` and `Details`, § Old-layout projects), for a property whose own text Notion changes (§ Rendering, Property text); such an entry covers that property’s rendering only and never renders as a frontmatter key. **`stored` is what the property will hold;** when it is a prediction (the text with Notion’s stripping applied), the write reads the property back once (a rows query) and, when it differs, rewrites `stored` to what came back and says so in the report, so an override never lapses silently.
- **`_derived`:** `{"<Property>": "<value>"}` for each property the binding filled from something other than its own key (a character’s `Type` from a legacy `tier`, which `characters/_index.md` and What Exists then show: § Stored and computed).
- **`_entry`:** `2` on every Decisions, Questions and Journal row a layout-2 write creates or replaces, and on nothing else. It is the row’s own mark of its form: a row with it is an entry (body = page content), one without it on Decisions or Questions is an old-layout log row, whatever the project’s `Layout` says (§ Old-layout projects).
- **`_words`:** a number, written only by `migrate`’s layout upgrade on each row it converts: the converted entry’s word count (body and frontmatter values, as the upgrade’s fidelity check counts them), so a resumed upgrade in a new session can tell a checked, unchanged conversion from a damaged one (`skills/migrate/SKILL.md` § The layout upgrade, Resume). Any later write of the row drops it, like every other `Meta` key its new content doesn’t hold.
- **`_layout`:** an old-layout log row’s entry layout (§ Old-layout projects); never written.

**Rows stored in the earlier form.** A row written before this storage form holds `Meta` as the source’s lines verbatim, its `_` keys in block style and `_layout` as a `|2-` literal block; it has no `_lines`. Read accepts that form: a key renders as its stored lines and a `_` key in block style is parsed as YAML. Where Notion kept the indentation (rows written through 2026-10-17), it reads back exactly. **Where Notion stripped it, the row is damaged** and a parse can mislead: `_as_written:` with its entries unindented parses as `_as_written: null` followed by stray top-level `category`, `stored` and `value` keys. Read treats an earlier-form `Meta` as damaged when any of these holds: a `_` key parses as null or empty; a top-level key is named `stored` or `value`; a line at the margin follows a line ending in a block indicator (`|`, `>`, with any chomping or indentation mark); a line at the margin is none of a key, a comment, a `- ` item or an empty line (a stripped continuation line). A damaged row’s frontmatter renders from its typed properties only, in `file-schemas.md`’s order (an old-layout log row’s entry in the default layout); none of its `Meta` lines or overrides renders, and none is ever written back as a key. The read reports it in one line: `Damaged Meta: characters/ada-vale.md: Notion stripped its indentation, so the source’s frontmatter can’t be recovered from Notion; rendered from the properties only`. The next write or edit of that path stores `Meta` from its new content in the current form, and its report says the damaged `Meta` was replaced. `migrate` treats such a row as a differing document and carries the note (its § Copy).

**Overrides stay true.** An `_as_written` entry or a `_derived` value applies only while every property it covers still equals its recorded value. Every write or edit that sets a property refreshes the overrides covering its key in the same `update_properties` call: `_as_written` gets the new source text when it still differs from the property’s rendering and loses the entry when it doesn’t (an edit to `authorship: author_written` drops the old `author-written` override), `_derived` loses the property now set from its own key, and `_keys` is rewritten when the edit adds, removes or reorders keys. So no override survives whose recorded value the property no longer holds.

**On read**, properties and `Meta` render as frontmatter (their text read back per § Rendering, Property text), then, when the row has a body, exactly one empty line and the body (`markdown-profile.md` § Document); a document with no body ends at the closing `---` and its newline. **The default rendering** of a property’s value follows `file-schemas.md` § Frontmatter values: a number or date property renders bare, and a text property’s value is quoted exactly when that section says a YAML reader would misread it, so text that would read as a number renders quoted (`act: "1"`); `_as_written` covers any source that wrote it otherwise. Keys come in `_keys` order when it is set (a set property whose key `_keys` doesn’t list, such as one filled in Notion since, goes after the nearest listed key that precedes it in `file-schemas.md`’s order, else first), else in `file-schemas.md`’s order for the document followed by the other `Meta` keys in stored order; `_` keys never render. A key in `_as_written` renders its `value` while its property still holds `stored`, and the property’s value once it doesn’t (the author changed it in Notion). A property in `_derived` renders only once it differs from the recorded value. An empty property renders nothing, except keys the schema requires on every write (an outline’s `pov`), which render empty, and keys `_as_written` keeps.

**Chapter identity.** The path decides `Chapter`, `Artifact` and `Scene`. A frontmatter `chapter` that disagrees with the path is an error: nothing is written, and the error names both. Renumbering is `move`.

**Entries** (`file-schemas.md` § Entry collections; layout 2) are rows under the same rule as Assets rows: the body is the page content, the frontmatter is the properties above, and everything else follows this section (`Meta` for unmapped keys, such as the extra fields a carried-over entry holds, then `_keys`, `_as_written` and `_derived`).

- **Identity.** The path decides `Number` (a journal entry’s `Date` and `Session`); a frontmatter `id` (a journal entry’s `date` or `session`) that disagrees with it is an error, as for chapters, except the number § IDs assigns, which the binding writes into both. An entry is never renumbered (bar § IDs’ race rule) or deleted, so `move` and `delete` of one are refused.
- **Links.** `superseded_by: D-052` on a decision is the later row’s `Supersedes` relation holding this row (its dual, `Superseded By`, is what renders here); `resolved_by` is the question row’s own `Resolved By`. Each renders as `D-` and the related row’s `Number`. Removing `superseded_by` removes this row from the later row’s `Supersedes` (its other items kept), and changing it moves this row to the new later row’s; removing `resolved_by` clears `Resolved By`. **A multi-row import** (a `migrate` copy into Notion, the layout upgrade, any batch of new entries) creates every entry row first and sets these relations after, once every number they name has its row. An ID with no row in the project (an entry citing a decision never logged) leaves the relation empty and keeps the value in `_as_written`, `stored` empty.
- **Lists** (`skills`, `decisions`, `questions`, `affects_books`) are stored as their YAML text (§ Values). A block list, such as a series’ `integrated`, is stored as its items one per line, each `- <item>` at the margin, since Notion strips leading whitespace (`Meta`’s storage form, above); it renders as the key, then each item indented two spaces, and a source indented any other way keeps its text in `_as_written`. The same holds for a block list in any database’s text property.
- **Derived keys.** `storystormer_project` and `storystormer_kind` are not stored: they render from the root row’s `Slug` and the collection (`decision`, `question`, `journal`). A source value that differs from the derived one is stored in `Meta` and renders as written instead.
- **Old-layout fields:** a layout-2 row holds `_entry` and none of the old layout’s field properties or `_layout`. Replacing a row sets every old-layout field property the hub has to `null`, which is how the layout upgrade converts an old row in place (§ Old-layout projects).

**Values.** Dates are `YYYY-MM-DD`, sent as `date:<Property>:start` with `date:<Property>:is_datetime: 0`. Numbers are numbers and render without a decimal point. A list (`tags: [hope, "sector: 7"]`, or a block list, whose items go at the margin: Entries, Lists) is stored as its YAML text and renders back as written, never split or joined. Relations take page ids when writing a property; query filters take page URLs (§ Queries). Selects accept only their listed options (*observed*: the connector rejects any other value, and adding one needs `ALTER COLUMN` naming every option to keep), so open lists (People types, worldbuilding types, tags, sources) are text. For a select, store the option the value maps to: an old spelling or retired value `file-schemas.md` maps (`author-written` → `author_written`, decision type `voice` → `theme`, question category `structure` → `Story Structure`), else the closest option by meaning (`premise` → `theme`, `process` → `structure`), else empty; never add an option. Whenever the stored option isn’t the source’s exact text, keep that text in `_as_written` (an old-layout log entry’s header parts, § Old-layout projects), so the rendering returns it. *Observed (2026-10-17)*: without this, 22 of 68 decision types and every question category came back remapped.

**Replacing a row** sets every property from the new content: a mapped key absent from it is set to `null`, and `Meta` is rewritten whole (`null` when no unmapped key remains, except on an entry, which always keeps `_entry`). Path-derived properties keep their values.

**Binding-maintained** (rebuilt on every write and on every edit that changes the body; never rendered): Chapters `Markers` = every `[OPEN: Q-###]` and `[NEEDS DEVELOPMENT` in the body, comma-separated (a parse of the plugin’s own marker format); Chapters `Related Assets` = the project’s character and worldbuilding rows the body names, matched by the model against an Assets query’s `Name`s (an index that can lag edits made in Notion); Chapters `Open Proposals` (notes rows) = the unchecked `- [ ]` items under `## Proposals`; Assets `Body Words` = the body’s word count (body only, never frontmatter; a word is a whitespace-separated token holding at least one letter or digit), counted from the body on every write and body-changing edit, never carried over or adjusted. It is **approximate** on a host with no exact counter (*observed (2026-10-17)*: estimates were off by −179 to +336 words), so it feeds only What Exists’ `~<n>w` and nothing compares, gates or decides on it; `Change Note` = the edit’s `reason` on every row the edit touches, cleared by a `write`, so Notion’s version history keeps each change’s note with it.

**Child pages** have only a title (its form: § Layout and root, Unmapped paths), so the whole document goes in the body: the frontmatter, when present, as a first block fenced as ```` ```yaml ```` holding the lines between the `---` markers verbatim (code is stored literally, so key order and values survive as written), then the body. `read` renders a leading `yaml` fence back as `---`, its lines, `---`, then one empty line and the body when there is one, the same join as a row’s (*observed (2026-10-24)*: the fence is its own block, so the read always has an empty line there; the profile’s frontmatter row makes the source agree). A child page carries no `Change Note`; its `reason` is dropped.

## Rendering: plugin markdown ↔ Notion

Edit anchors match the document as `read` returns it (`store.md`), so `read` returns plugin markdown and `write` sends Notion’s enhanced markdown (`notion://docs/enhanced-markdown-spec`). Every body this binding sends is in the markdown profile (`references/markdown-profile.md`), and in that form it comes back byte-identical through the read rules below (*observed (2026-10-24)*: every construct the profile allows and every rewrite it adopts, on a 243-construct probe; `tests/markdown-profile/probe-results.md`). Each rule is *observed* unless marked:

- **Normalization on write (the safety net).** Before a body or an edit’s replacement text goes into write form, any markup in it outside the profile is rewritten into profile form by the profile’s § Rewrite table: markup only, never words, never inside code, and nothing the profile keeps as written. Plugin text is in the profile already, so in practice this changes author text carried verbatim (an intake file, a migrated document, a quoted passage). It doesn’t stop to ask: the run’s report says so in one line naming the documents affected and, for each, what changed (`Normalized for Notion: primer.md (an HTML table → a pipe table), ch03-prose.md (two-space line breaks → bare newlines)`), adding any construct the profile lists under No in-profile form, which Notion changes and no rewrite keeps. `migrate` counts all of this in its preflight instead (its § The preflight). The normalized form is what the row holds, so every comparison against stored content (write’s identical-content no-op, the read-back below, `migrate`’s resume, left-behind and verification checks) is exact against it.
- **Backslashes and specials** (outside code): write doubles every `\` and sends every `_` as `\_`; read removes the backslash before **any** ASCII punctuation character, scanning left to right so `\\` yields `\`, and leaves a backslash before anything else alone. Notion escapes more than its documented set (*observed (2026-10-17)*: `6:00` came back `6\:00`; *observed (2026-10-24)*: `\_`, `\~`, `\[` and `\<` too), and every `\` an author wrote reaches Notion doubled, so a single backslash before punctuation is always Notion’s. So `C:\Users`, an author’s `\[lit\]` or `## 1\.`, `[OPEN: Q-001]` and `5 * 3` all round-trip. **The underscore** is escaped because in profile-form text it is always a literal character (`markdown-profile.md` § Inline), while Notion’s parser reads a run such as `_-_Brainstorming_&` inside a bare filename as emphasis (*observed (2026-10-24)*: `The_Good_Dog_-_Brainstorming_&amp;_Future_Plot_Points.md` came back with two italic runs, one reaching past the filename, and the entity decoded; sent with each `_` as `\_`, the name came back as written, apart from the entity, which Notion decodes regardless).
- **Inline tags** (*observed (2026-10-24)*: the fetch serializer changed after 2026-10-17 and now returns emphasis and code as HTML tags, on pages written before the change too): read first merges immediately adjacent identical runs: outside a `<code>` span it removes every unescaped `</b><b>`, `</i><i>`, `</s><s>` and `</u><u>` with nothing between the two tags, repeating until none is left (`<i><b>a</b></i><i><b>b</b></i>` merges to `<i><b>ab</b></i>`). In profile-form text two emphasis spans never touch (`markdown-profile.md` § Inline), so this only undoes a split Notion made itself (*observed (2026-10-24)*: on a long page, `**Morning Routine (6:00-9:00 AM):**` came back as `<b>Morning Routine (6</b><b>\:00-9\:</b><b>00 AM):</b>`; the same line written alone came back as one run). Notion nests the tags in one order, `<s>` outside `<i>` outside `<b>` outside `<code>`, splitting each run where an inner style starts or stops (*observed (2026-10-24)*, ring probe 7: `~~*a **b** c*~~` came back as `<s><i>a </i></s><s><i><b>b</b></i></s><s><i> c</i></s>`), so nesting in that order merges back to the source and nesting in any other order doesn’t (`**a *b* c**` came back `<b>a </b><i><b>b</b></i><b> c</b>`): that is the profile’s nesting order. Then it renders an unescaped `<b>` or `</b>` as `**`, `<i>` or `</i>` as `*`, `<s>` or `</s>` as `~~`, each tag where it stands, with no other merging (`<i><b>x</b></i>` → `***x***`), and `<code>x</code>` as a code span whose delimiter is one backtick longer than the longest backtick run inside, padded with one space only when the contents start or end with a backtick. `<u>` stays `<u>`. An escaped tag (`\<b>`) is text, under the backslash rule. Write sends markdown, which the connector accepts.
- **Property text** (`Meta`, `Tags`, every rich-text property): *observed (2026-10-24)*: Notion returns it serialized the same way, with `\_` and other escapes, `<br />` for a newline and `<code>` for a code span (an SB5 `Meta` value came back so). Notion also parses it as inline markdown (an unescaped `_x_` comes back as `<i>x</i>`, `__y__` and `**w**` as `<b>`) and strips the whitespace at the start of every line. So property text is sent in one of two forms:
  - **Literal text:** `Meta`, every property set from a frontmatter value (`Name` on every row but an old-layout log row, `Slug`, `Logline`, `Genre`, `Current Focus`, `Tags`, `Type`, `Category`, `Title`, `POV`, `Act`, a chapter’s `Summary`, an entry’s `Source`, `Integrated`, `Scope`, `Skills`, …), a title outside a code span, and an old-layout row’s Heads. Every ASCII punctuation character is sent with a backslash before it, `\` included, so Notion stores the text with no formatting, apart from its autolinks (it keeps some of the escapes and drops others, which the read doesn’t care about). Read applies the read order below, collapsing every link in it that isn’t escaped to its text: the text’s own brackets were all escaped, so any link is Notion’s autolink (an escaped `\[l\](https://a.example)` came back as `\[l\]([https://a.example](https://a.example))`). *Observed (2026-10-24)*: a `Meta` sent this way holding `_x_`, `__y__`, `*z*`, `**w**`, a code span, `a.md`, a link, `~~s~~`, `<u>u</u>`, an empty line between keys, and `_lines` strings with `\n` escapes and two trailing line breaks read back byte-identical (`probe-results.md` § Mini round trip).
    - **The read order**, for all property text: the inline-tag rule (adjacent runs merged first), then `<br>` or `<br />` as a newline, then the link collapse (literal text: every unescaped link; markdown: the autolink collapse), then the backslash rule. `Meta` then decodes its `_lines` strings and parses its `_` keys (§ Frontmatter ↔ properties, On read).
  - **Markdown:** an old-layout log row’s field properties and its `Name` (§ Old-layout projects). They hold profile-form text, read with the body’s rules: their emphasis and code come back as tags, which the inline-tag rule reads. A field value holding a line that started with whitespace (a nested sub-list) keeps its exact value in that row’s `Meta` `_as_written`, under the property’s name. Nothing in layout 2 is sent in this form.
- **Code:** inline spans and fenced blocks are sent and returned literally, never escaped or unescaped. A bare fence is sent as ```` ```plain text ```` (Notion otherwise guesses a language: a bare fence came back `javascript`). Notion returns a bare, `plain text`, `text` or `txt` fence as ```` ```txt ```` (*observed (2026-10-24)*), so read renders `txt` and `plain text` as a bare fence. Notion renames `js`, `sh`, `python` and `md` (to `javascript`, `bash`, `py`, `markdown`); normalization does that before sending.
- **A fence that holds fence lines** (a content line starting with three or more backticks or tildes, as in a four-backtick fence around a markdown example): after the write, read the document back and compare the rendered read, exactly, with the body’s normalized form (the plugin markdown before write form, never the write form itself). A mismatch is reported, naming the document and the first part that differs, and the write counts as failed: a row that already existed gets its content put back with `replace_content` from the fetch taken before the write; a row this write created is withdrawn (§ Withdrawing a row), so no mangled row stands for the path, and the report names its URL for the author to delete. *Observed (2026-10-24)*: one such write never closed the fence and silently turned the 27 sections after it into the fence’s body, with no warning from the connector, while five isolation writes kept the same fence intact (PL10). The profile keeps these out of plugin output; author text can hold one.
- **Blank lines:** read puts one blank line between blocks; consecutive list items and the lines of a block stay together. Runs of blank lines collapse to one (Notion strips them). `<empty-block/>` (an empty paragraph made in Notion) reads as nothing, so a later write drops it; writes never send it.
- **Line breaks inside a block:** write sends a single newline inside a paragraph, quote or list item as `<br>` (a bare newline can split the block); read renders `<br>` and `<br />` (Notion’s form since 2026-10-24) in a block as a newline, and inside a quote each line after one starts with `> ` (so two in a row read as a lone `>` line, the source’s paragraph break within the quote). In table cells write sends `<br>` and read renders `<br>` or `<br />` as `<br>`.
- **Indentation:** write sends one tab per nesting level (a child indented by its parent’s marker width is one level deeper). Notion returns spaces at the parent’s marker width, two under `- ` and under a to-do, three under `1.`–`9.`, four under `10.`–`99.`, which is the profile’s nesting, so read keeps them as returned (*observed (2026-10-24)*: no tab came back); a tab that does come back reads as its parent’s marker width.
- **Tables:** write sends each pipe table as `<table header-row="true">` with one `<tr>` per row and one `<td>` per cell, cell text in write form with `\|` sent as a bare `|` (Notion’s pipe-table parser splits a cell at `\|`, breaking the table). Notion returns a pipe table with `| --- |` separators (*observed (2026-10-24)*; a `<table>` on an older page), and read re-renders either in the profile’s one form: `| a | b |` rows, a `|---|---|` separator, an empty cell as `|  |`, a literal `|` in a cell as `\|`, a cell break as `<br>` (Notion returns `<br />`).
- **Scene breaks:** a `* * *` line is sent escaped, `\* \* \*` (Notion otherwise makes it three nested empty bullets), and reads back as `* * *` (*observed (2026-10-17)*, and again 2026-10-24).
- **Mentions:** a page, database or data-source mention renders as `[<title>](<url>)` (the fetch fills in the title even when the tag was sent self-closing), which the connector turns back into a mention on write; a user mention renders as its name; a date mention renders as the date (`2026-10-16`, a range as `start – end`, with time and zone when set) and is written back as text. A mention never renders as nothing.
- **Autolinks:** Notion links anything that looks like a domain, writing `[x.md](http://x.md)`, in bodies, property text (`Meta` included) and titles; inside a path only the basename is linked (`chapters/chapter-02/[ch02-prose.md](http://ch02-prose.md)`) (*observed (2026-10-17)*, and again 2026-10-24). Read collapses every `[t](http://t)` and `[t](https://t)` outside code, where the URL is exactly the scheme plus the link text, to `t`; any other link is the author’s and stays. Notion’s autolink is never percent-encoded and stops at `&` and `_`: `Tom&Jerry.md` came back as `Tom&[Jerry.md](http://Jerry.md)` and `\_index.md` as `\_[index.md](http://index.md)` (*observed (2026-10-24)*), which the collapse reads as written. A link whose target is a bare filename becomes `https://<filename>` (*observed (2026-10-24)*), which the read can’t tell from an author’s link, so the profile writes such a target as `./<filename>`.
- **Child-page tags:** `<page url=…>` and `<database>` tags in a row’s content are not part of its document (they are other paths, which `list` reads: § Operations), and `replace_content` keeps them.
- **HTML comments** are stored as a visible paragraph of literal text and come back escaped, `\<!-- … -->`, which the backslash rule reads as written (*observed (2026-10-24)*); tell the author once that they show in Notion.
- **Leading H1:** a create may silently drop the body’s first block when it is an H1, a `# …` heading; `replace_content` and `insert_content` keep it. So when a body to create starts with `# `, read the page back after the create and, only when the read-back lacks the H1, `insert_content` that H1 line alone at `start`; then `read` returns what was written. Creates usually drop it and occasionally keep it, synchronous, batched and child-page creates alike, so the read-back decides, never the kind of create (*observed (2026-10-24)*: a create dropped `# Intake — Original Filename Mapping`, and inserting that one line at `start` restored the document exactly; in the second ring a synchronous single-page create and a child-page create kept their H1, and an unconditional insert duplicated it; *observed (2026-10-25)*: in the SB7 ring every H1-led synchronous create dropped it, 17 of 17 canon rows, 6 of 6 story documents, 5 of 5 chapter rows and every archive and pipeline child page, while the style guide and three notes pages kept it).
- **Final newline:** Notion stores none. `read` ends every document with exactly one newline, and normalization ends every body with exactly one (the profile’s rewrite row for the document’s end), so the comparison is exact with no exception (*observed (2026-10-17)*: 31 sources without one came back with one).

**Known limit: author text outside the profile that normalization never touched.** Text reaches a row without the normalization on write above when an author writes or edits it directly in Notion, or when it was stored before this normalization (rows a 0.20.x `init` or `migrate` wrote). Where that text is outside the profile, Notion keeps its own form and the read returns it, so the document no longer matches its source byte for byte, and an edit anchor taken from an older copy can stop matching. Still *observed (2026-10-24)* (`tests/markdown-profile/probe-results.md`):

- **Spacing and spellings:** blocks the source ran together gain an empty line; `*` and `+` bullets, padded markers, `1)`, loose lists, nesting at other widths, leading and trailing spaces, `#####`, closing `#`s, setext headings, rules other than `---`, and other pipe-table spellings come back in Notion’s form.
- **Emphasis:** underscores become asterisks; emphasis nested in, or sharing a boundary with, other emphasis or a link comes back as adjacent runs (`**a *b* c**` → `**a *****b***** c**`), except where the split runs are identical and the read merges them (`*a **b** c*`, `***a** b*` and emphasis around a code span come back as written).
- **Links and images:** a bare URL or email becomes a link to itself; a title or a reference-style link becomes a plain inline link; a link to a bare filename becomes `https://<filename>`; a footnote becomes a bracketed link; an image with a relative target loses the target.
- **HTML:** a `<table>` comes back as a pipe table, `<details>` as a `<toggle>`, and `<b>`, `<strong>`, `<em>`, `<code>` and `<a>` as markdown; `<mark>`, `<del>`, `<sup>` and `<img>` are stored as text.
- **Code:** a tilde fence comes back as backticks, an indented code block as a paragraph, and a renamed language under Notion’s name.
- **Entities:** every HTML entity is decoded.

Two of these change even normalized text, because the profile has no form that keeps them (its § No in-profile form): a fenced code block inside a quote becomes an inline code span, and an entity whose character would be markup is decoded (`&lt;b&gt;` reads back as a real `<b>` tag). The write report names them. A non-breaking space is stored as U+00A0 (an edit anchor confirmed it), but the fetch returns a plain space (*observed (2026-10-24)*: the ring round lost 36 on the way out of Notion), so normalization turns U+00A0 into a plain space on the way in (the profile’s rewrite row). The 2026-10-17 list’s other items no longer reproduce and are retired: `***` closing a whole span, ordered lists continued past a heading, `~~**x**~~`, `_` inside words, multi-paragraph quotes and trailing two-space breaks all round-trip.

So a document normalized on the way in comes back exactly as sent, and one written in Notion or before normalization may not; `init` keeps local intake originals because normalization changes their markup (§ Scaffolding, step 5), and `migrate` names what it normalizes in its preflight.

**Truncation:** if a fetch reports `truncated`, `unknown_block_count` or `unknown_block_ids`, fetch each listed block id and splice its content in at its `<unknown url=…>` placeholder, in order, treating a truncated part the same way. The read fails, naming the page, when a fetch is truncated but lists no ids, when a part can’t be fetched, or when any part is still marked truncated after splicing: a partial page is never returned as the document. (Unobserved through 12,700 words.)

## Stored and computed

Stored rows: every Assets, Chapters and entry path, and child pages. No snapshots are written. **Computed** (`store.md` § Local-mode clauses): `state.md`, `.storystormer/config.json`, `decisions/_index.md`, `questions/_index.md`, `characters/_index.md`, `outline/_index.md`, `voice/README.md`, and in the old layout `decisions.md` and `questions.md` (§ Old-layout projects). `read` renders them as below. A `write` of one is diffed against the **baseline read** its content was prepared from (an `edit`, against the read it was applied to), never a fresh rendering that may already hold another session’s rows, and each change goes through the writable realization listed. Anything with no realization is refused by name, never dropped silently.

| Document | Renders from | Writable realizations |
|---|---|---|
| `state.md` (layout 2) | frontmatter: the bound row (§ Frontmatter ↔ properties, so `_keys` and `_as_written` apply: a `stage` with a suffix renders as written). The root row renders `slug`, `session_count` and `last_session`; a book row renders none of them, and renders `target_word_count` only when its own `Target Word Count` is set (absent, the book inherits the series value: `file-schemas.md` § `state.md`). Body: exactly the four sections, in order, `## Summary`, `## What Exists` (computed on each read, below, then the row’s carried lines), `## What's Next`, `## Last Session`, each from the row’s stored section of that name (a missing one renders as its heading alone). **What Exists** (standalone, or a book’s `state.md` over that book’s rows plus the shared root rows), recomputed on each read in `file-schemas.md`’s line order: Primer, Treatment, Manifest, Structure from their Assets rows (`Version`, `Last Updated`, `built_from_decisions` and `target_chapter_count` from `Meta`), a line whose row doesn’t exist rendering `not yet created` (`- **Treatment** — not yet created`); Character bios as `<Name> (<Type>, ~<Body Words>w)`; Worldbuilding as `<Name> (<Category>)`; Voice (`sample` when a writing-sample or voice-sample row exists, `+ style guide` when the style-guide row does, else `README only`); Chapter outlines, Blueprints, Prose chapters and Chapter notes (Chapters rows per `Artifact` against the structure’s chapter count, or a count with no denominator, `6 written`, when there is no structure row; prose counts a chapter with a prose row or any scene row, skipping rows whose `Status` is `retired`; Chapter notes adds how many are stale, `Meta` `prose_version` below the chapter’s prose `Version`, and the sum of `Open Proposals`); Decisions (rows in scope, `Scope` = `series` or `book-<slug>` for a book, and how many are integrated: standalone, `Integrated` starts with `yes`; series, its `<slug> treatment` item says `yes`); Open questions (`Status` = open, in scope, counted by `Priority`). **Carried lines:** a `- **<Label>** — …` line whose label isn’t one of those but names documents the project holds (`**Research**`, `**Handoff**`, `**Methodology**`, an author’s `**Notes**` line about `notes/`) is the author’s, not computed: it is stored verbatim, in order, as the only content of the row’s own `## What Exists` section, and renders after the computed lines. A line whose label is a computed one (a second `**Blueprints**` line, say), a sub-bullet, or a free paragraph is not carried.

**Series root `state.md`** renders What Exists in the shape of `file-schemas.md` § Series-level state.md: Series document (the `series.md` row’s `Version` and `Last Updated`, and the rows of its Cross-Book Setups and Payoffs table), Shared manifest (version, date, counts), Shared character bios (counts by `Type`), Shared decisions (total, and counts by `Scope`), then one line per book row by `Book Order`: title, primer and treatment versions, outline and prose counts, `Stage`.

**IDs.** `Number` is the project’s own sequence, rendered zero-padded to three digits (`D-018`; four past 999), and it is the number `store.md` § New entries says the store assigns. A `new` write of a decision or question (§ Operations) keeps the proposed number when no row of the project holds it, else takes one more than the project’s highest (query sorted by `Number` descending, `limit: 1`). So a skill that proposed the next number gets it unless another session took it first, and **imports** (`migrate` copying entries in, which keep their numbers) keep theirs, gaps and all, so references stay true. After creating, query the project for that `Number`: if two rows hold it, the one whose page id sorts later is renumbered to the new highest plus one and checked again (both sessions see the same pair, so exactly one moves). When a row ends up with a different number from the one proposed, rewrite every reference to the proposed ID in the same submission (the entry’s own `id`, another new entry’s `superseded_by`, `resolved_by` or body, prose that cites it) before sending, or on rows already sent after a race, and report each ID used, both numbers when it moved: that report is the number the skill uses from then on. Notion’s `UNIQUE_ID` is not used (*observed*: its prefix needs two or more characters, it counts per database across every project sharing it, it renders as a bare `1`, `2`, and a property named `ID` becomes `userDefined:ID`).

**Several rows from one call.** A write or edit can touch several rows (a decision whose `superseded_by` sets the later row’s `Supersedes`, a `books` change that creates a book row, a migration’s batch of entries). Apply the changes in document order, recording each one (the row and its prior values, or that it was created); if one fails, undo the completed ones in reverse (prior values and content restored in place on rows that existed; rows this call created withdrawn, § Withdrawing a row) and report what was attempted, with each withdrawn row’s URL for the author to delete. If an undo fails, name the rows it left changed.

**Withdrawing a row.** A row the session just created and must not stand (a race’s losing journal row, a failed write’s new row, an undo) is withdrawn, never trashed: one `update_properties` that retitles it `<Name> (duplicate, withdrawn)` and clears the relation that places it in the project (`Project`; `Parent` for a book row), so no selector, listing, index or relation count finds it. A Projects row (a book row) also gets its `Slug` suffixed, `<slug>-withdrawn`, so no slug check can match it, and § Locate, `init`’s slug check (§ Scaffolding, step 3) and `migrate`’s § Same slug skip every Projects row whose `Name` ends ` (duplicate, withdrawn)`. A child page has no such relation: retitle it to its path title followed by ` (withdrawn)`, outside the code span, and `list` skips a `<page>` tag whose title ends in ` (withdrawn)` or ` (duplicate, withdrawn)`. The report names each withdrawn row’s URL so the author can delete it in Notion. A withdrawal that fails is reported with both rows’ URLs (or the row’s, alone), and the run stops.

**`open` and `history` of a computed document.** `open` gives the bound Projects row’s URL (its relation lists reach every source row) and shows the rendering in the chat: a stated exception to `store.md`’s never-paste rule, because the document exists only as that rendering. `history` names the rows that hold it (the Projects row for `state.md` and `config.json`; for an index, or an old-layout log, the Decisions or Questions rows, each with its own history) with the version-history route below.

**Batched creates and cost.** `notion-create-pages` takes up to 100 pages in one call, so a run creating many rows in one data source (a migration’s documents, a collection’s entries) or many child pages under one parent sends them in batches, each one call plus its async poll, and follows only the H1-opening bodies whose read-back lacks the H1 with an `insert_content` of their H1 line. Estimate a migration into Notion at a few calls per batch of documents (create and poll), one more per H1-led body whose read-back lacks the H1 (its `insert_content`; the read-back is the document’s own), one create per batch of entries (the 2026-10-17 ring sent its old log rows 5–10 per create; entry rows are pages like any other, so they batch like documents, *unobserved*), plus a numbering check per batch, the source reads and about ten for a new hub (*observed (2026-10-17)*: 34 rows, 109 log entries and 56 child pages took about 310 Notion calls; logs went 5–10 rows per create).

**Async:** every create and update passes `allow_async: true`. When the reply is an `async_task`, poll `notion-get-async-task` (honour `poll_after_seconds`) until `succeeded` before reporting, reading back, or the next dependent call; `failed` is a failed call. **A call that fails to queue** (the error says it “could not be queued”; *observed (2026-10-24)*: both async creates of a run failed with a 503, “Async Public API operation could not be queued”, and their synchronous retries succeeded) never ran, so it is sent once more without `allow_async`, synchronously: a create, a `replace_content` or an `update_content` alike. A batched create retried this way is split into parts within the synchronous size (Capabilities: about 5k words of content per call), each sent on its own; only a failure of a retry is a failed call. **Two in a row stop async for the session:** once two consecutive async attempts fail to queue (the count is of async attempts only: a synchronous resend between them neither counts nor resets it; an async call that queues resets it to zero), send every remaining create and update of the session synchronously, every later skill in it included (a skill run after the switch starts synchronous), without `allow_async` and with batches split the same way, rather than trying async first each time (*observed (2026-10-24)*: every async call of a 112-call migration, about 20, failed to queue, and every synchronous retry succeeded), and say so once in the report (*observed (2026-10-25)*: a development loop that treated each skill as a fresh count saw every async attempt of the session, 6 of 6, fail to queue). The count belongs to the session, not to one skill or agent: a brief carries the session’s count in (and whether it has switched), a subagent adds its own attempts to it, starts synchronous when the session already has, and returns `async: switched` in its log when it switched, so the main session sends the rest of the session, later dispatches and later skills included, synchronously, and reports the switch once. **A body over the synchronous size** (a 12,700-word chapter) in a synchronous send goes in parts of about 5k words, split only between blocks (never inside a list, table, quote or fence): the create (or the `replace_content`, with the child-page tags) takes the first part, each further part goes in with `update_content` whose `old_str` is the end of the part before it (its last block, or more of it until it is unique on the page) as the page stores it: taken from a fetch of the page after the previous part landed, never from the markdown that was sent, since Notion stores markup in its own form (*observed (2026-10-25)*: a bold block sent as `**X**` was stored as `<b>X</b>`, so the sent text as `old_str` matched nothing) and whose `new_str` is that text plus the part, then the whole body is read back, an H1 the create dropped (the read-back lacks it) goes back with `insert_content` at `start`, and the body is compared with its normalized form. Only the queueing error is retried blind. A timeout, a dropped reply or any other unknown outcome may have run, so query for the row first (its selector query, or the child page’s title under its parent) and send again only when it isn’t there; re-applying an update first compares the row with the content it was meant to get. A create resent blind could leave two rows for one path (§ Operations, `write`: two rows stop the next write).

**Concurrency guard:** before a write or edit that replaces an existing row, re-run its selector query and compare `Version` with the baseline (a child page: re-fetch and compare its fence’s `version`, or its whole rendering when it has none). Rows without a `Version` compare only what the change touches. Projects rows (`state.md`, `config.json`): re-fetch the row and compare its whole rendering with the baseline’s, What Exists’ computed lines excluded (they are recomputed on every read); with `state.md` down to four short sections this is one comparison of a few KB, though the fetch still carries the row’s relation lists. Entries (Decisions, Questions and Journal rows) carry no `Version`: re-fetch the row and compare its whole rendering with the baseline’s, one small fetch. A `new` write needs no guard.

**`replace_content` and children:** a replace that omits a child page or database is refused with a list (*observed*). Keep their tags in `new_str`; never pass `allow_deleting_content` unless the author has approved deleting exactly what that list names. The hub’s content is never replaced.

## Queries

Use **rows mode** (`mode: "rows"`, the data-source URL, structured filters and sorts), which works on every plan: the filters from § Path map (`relation_contains` the root for `Project`; `relation_contains` the book row, or `is_empty`, for `Book`; `Parent` `relation_contains` the root for book rows), plus `enum_is` for selects, `number_equals` for numbers and `string_is` for text, with `limit: 100`. **A `relation_contains` value is the related page’s full URL** in the form `https://www.notion.so/<id>` (the 32-character id without dashes), never a bare page id. The connector now returns relations as `https://app.notion.com/p/<id>` (*observed (2026-10-24)*); both forms name the same page, so compare pages by the id in them, and keep sending the `www.notion.so` form, which was observed to scope a query correctly on 2026-10-24 (the `app.notion.com` form as a filter is unobserved). A bare id is wrong: a bare id, dashed or not, is silently ignored and the query returns every project’s rows (*observed*, 2026-10-17), which would pull other projects into logs, listings, the next-number query and the duplicate checks. When a result could span projects (any count, number or duplicate check), confirm each row’s `Project` relation holds the root before trusting it. Rows mode returns properties, not bodies, and has no cursor (*observed*: 100 rows and `has_more`). It leaves an empty relation out of a row entirely (*observed (2026-10-24)*: no `Book` key on a standalone row), so an absent relation is an empty one, never a reason to fetch the row. Past 100:

- **Chapters, Decisions, Questions:** sort by `Chapter` or `Number` ascending; re-query with `number_greater_than_or_equal_to` the last key, drop URLs already seen, and repeat until fewer than 100 come back (*observed* on 101 Chapters rows). Ties can’t stall it: `Number` is unique per project, and one `Chapter` holds at most a few dozen rows (four artifacts plus scenes, per book).
- **Assets:** query one `Kind` at a time. If a single `Kind` returns 100, fall back to SQL mode with `ORDER BY url LIMIT 100 OFFSET n` (`url` is unique, so pages never overlap; take quoted column names from the fetched `<sqlite-table>`), which is unlimited only on Business or Enterprise with Notion AI and shares a workspace limit elsewhere. Failing that, fetch the root row’s `Assets` list, fetch the rows not yet seen, and apply the query’s `Kind`, `Book`, `Slug` and `Category` filters to them in the model, since the list holds every Assets row of the project.

SQL is never required, and nothing queries two data sources in one call.

## Locate

1. **Hubs.** Find hubs (§ Layout and root). Each complete hub is searched; each partial hub is reported with its link and the databases it lacks, never searched or repaired. No hub means no projects here, which is not a failure.
2. **Projects.** Query each complete hub’s Projects data source (its URL from the hub fetch) in rows mode with no filter, sorted by `Last Session` descending, `limit: 100`. Skip every row whose `Name` ends ` (duplicate, withdrawn)` (§ Withdrawing a row). Rows with an empty `Parent` are projects; rows with a `Parent` are books, named under their series by `Book Order`. If 100 rows come back, query again with `Parent` `is_empty` for the projects alone, and say the book lists may be incomplete.
3. **Fields** come from the row properties, the values a frontmatter-only read of `state.md` renders (§ Stored and computed), so no row is fetched: title ← `Name`, slug ← `Slug`, `stage` ← `Stage` (or its `_as_written` value in `Meta`), `last_session` ← `Last Session`, project type ← `Project Type`, last edited ← `Last Edited` (Notion’s own last-edited time of the Projects row, which every session’s `state.md` update moves; empty on a hub created before the column, § Schema upgrades, and reported as unknown). It is for telling copies apart only: nothing treats an unchanged `Last Edited` as proof that a project’s rows are unchanged, since whether every change to every row moves it is unprobed (*observed (2026-10-24)*: a rewrite Notion treated as a no-op left it unchanged). The root is the row’s page id.

**Returns**, per project: the hub (its link, and whether it sits at the private root or in a teamspace), title, slug, root, stage, last session, last edited and, for a series, its books. Last edited is what tells a same-slug pair apart (*observed (2026-10-17)*: a moved copy carries the source’s `last_session` unchanged, so both copies showed the same date): show it beside each copy of a slug that appears twice. Several complete hubs → every hub’s projects, labeled by hub. Keep the hub’s data-source URLs (six, or five on a hub without a Journal yet) with the pick, so binding needs no second search. **Fails** when search errors; a hub whose fetch or query errors is reported against that hub, beside the others. **Cost:** one `notion-search` (plus `notion-get-self` where used), one `notion-fetch` per result titled exactly `StoryStormer` at a hub location, and one query per complete hub (two past 100 rows).

## Scaffolding a project (`init` on Notion)

1. **Hub.** Find hubs (§ Layout and root). One complete hub → use it and its databases, after § Schema upgrades (a hub from an earlier version gains its Journal and `Layout` here). Several → ask which. Any partial hub → stop and tell the author; don’t repair it by guessing and don’t create another. None → ask once whether it goes at the private root (default) or in a teamspace (`notion-get-teams`), then `notion-create-pages` titled `StoryStormer` with no parent (private) or `parent.teamspace_id`.
2. **Tables**, for a new hub only: the six `CREATE TABLE`s in order, then the two `ADD COLUMN`s; keep the returned data-source URLs.
3. **Project row.** First query the hub’s Projects data source for `Slug` = the slug, skipping a withdrawn row (§ Withdrawing a row): an existing row (a retried init, say, after a failed pointer write) stops init with the question Dropbox asks, another slug or whether they meant that project. Otherwise, before any other row of the project, one Projects row from the new `state.md` frontmatter. This is this binding’s exception to `init`’s order (`file-schemas.md` § `journal/`: the config and indexes, then `s01`, then the rest, `state.md` last): the row is `state.md` and the config at once, and every other row relates to it. It is created with `Slug` = the slug and `Layout` = 2 (the computed config’s `layout`), and the body’s stored sections as its content (§ Stored and computed, `state.md`); in a series, the series row and one row per book with `Parent` set and `Book Order` 1…n. Then the session’s `journal/<date>-s01.md` as a Journal row (a `new` write). The two indexes are computed, so `init`’s writes of them are skipped.
4. **Pointer.** When the session has an open folder, write its `.storystormer/config.json` through the local binding as exactly `{"storage": {"kind": "notion", "root": "<row page id>"}}` and nothing else, so resolution finds the project next session. The pointer is read only by resolution; `store.read('.storystormer/config.json')` on this binding returns the computed config (§ Stored and computed), never the pointer.
5. **Intake.** Continue `init` through the contract; intake documents become rows. Notion keeps no snapshot folders, so init’s intake archive is `.storystormer/intake/<timestamp>/` (the snapshot-folder timestamp form, so a re-run keeps the earlier record), as child pages: `superseded-prose/<original filename>`, `intake-original-names.md`, and `sources/<original filename>` for each text source init read but didn’t re-file. **The same layout whoever writes it:** an archive is the tree init writes into its snapshot folder on a snapshots store, so `migrate`, re-filing a source’s `.storystormer/history/<timestamp>-init/`, writes `.storystormer/intake/<timestamp>/` + each file’s path inside that folder unchanged (an older archive’s `originals/` and `superseded/` stay as they are), where `<timestamp>` is the folder’s name without its `-init` suffix (`2026-05-11T14-33-init` → `2026-05-11T14-33`; an older `2026-08-15-init` → `2026-08-15`). Because this binding normalizes author markup on the way in (§ Rendering), init keeps every local intake original (never deletes it) and says so in the report. Notion holds markdown only, so a non-markdown original (`.docx`, `.rtf`, `.scrivx`, …) stays where it is in the open local folder, is never deleted, and is named in the report with the canonical path it would have had (with no open folder, the report says it was not stored). Attaching it as a file needs the connector’s file upload plus an HTTP POST, which the plugin can’t require.

## Old-layout projects

A project whose root row’s `Layout` is empty (on a hub without the column too) is in the old layout (`file-schemas.md` § The old layout). It is read-only until `migrate`’s layout upgrade runs (`store.md` § Resolve step 4), so this binding keeps only how it **reads**; the old logs’ writable realizations are retired. In the old layout:

- **Paths.** `decisions.md` and `questions.md` are computed (below) from the project’s **unconverted** rows, those whose `Meta` lacks `_entry`. A **converted** row (one holding `_entry: 2`, which only the upgrade’s conversion writes while `Layout` is empty) is an entry in any layout: it lists, reads and writes at its entry path (`decisions/D-018.md`) from its body and frontmatter, and never appears in, or renders from, the old log. Journal rows the upgrade created list at their paths too. The two indexes don’t exist, and an entry path naming an unconverted row is a missing-path error for `read` and `list`; only the conversion’s `write` reaches one (below).
- **`state.md`:** the frontmatter renders as in layout 2. The body is the row’s page content, all of it, in stored order (its trailing `<page>` tags not rendered): the text before the first `## ` heading (a `# <title> — Project State` H1, say), then every `## ` section the row holds, named or not (*observed (2026-10-17)*: a `## Previous Session` of 36 KB). `## What Exists` is computed as in layout 2 and placed after `## Summary` (first, when there is none), its computed lines followed by the carried lines of the row’s stored `## What Exists`, which never renders as a section of its own; its Decisions count reads `Integrated` as its `**Integrated into treatment**` line (a series: its `<slug> treatment` line).
- **The config** renders as `storage` alone, with no `layout`, which is how resolution finds the old layout. The old config’s mirrored fields aren’t rendered: their values are the rows’ own, so on this backend the upgrade has nothing to move.
- **`decisions.md`** renders as the Projects row’s `Decisions Head` verbatim (the source’s frontmatter and everything before its first entry, stored without its trailing blank lines and rendered followed by one), or `# Decisions` and a blank line when it is empty, then the project’s unconverted Decisions rows sorted by `Number` (§ Queries past 100), each per the entry rules below. **`questions.md`** is the same from `Questions Head` (default `# Open Questions`) and the unconverted Questions rows.

**Log entries** (`file-schemas.md` § The old layout) render from one row each, and the rendering returns the entry exactly as the source wrote it unless a property was changed in Notion since. *Observed (2026-10-17)*: real logs are richer than the columns (extra bold fields, free paragraphs, status prose, header suffixes, a retained second copy of a question’s fields), and a column-only rendering lost about 1,350 words of one project’s questions.

- **What a row holds**, as the old writes parsed it. The header gave `Number`, then `Date` and `Type` (decisions) or `Priority` and `Category` (questions), each select per § Frontmatter ↔ properties, Values. Below it a **field** starts at a line beginning `**<Label>**:` and runs to the line before the next such line, so free paragraphs, sub-lists and bold run-in paragraphs (`**Why it works.** …`) ride with the field above them. The first occurrence of each mapped label goes to its property, the value verbatim after `**<Label>**: ` (a value that starts on the next line, such as a `Possible approaches` list, keeps its leading newline; the empty lines that set a list value off belong to neither the value nor `_layout` and are not stored, since the rendering supplies them). Decisions: `Scope`, `Affects books`, `Topic` → `Name`, `Summary`, `Details`, `Affects`, `Source`, the first run of consecutive `**Integrated into …**` fields → `Integrated` (every line as written, in order: `**Integrated into treatment**: no`, `**Integrated into structure**: yes (<date>)`, or a series’ `**Integrated into**:` with its book lines), `Superseded by` → the later row’s `Supersedes`, with any text after its `D-###` (` — narrowed by …`) kept on the placeholder line (below). Questions: `Scope`, `Affects books`, `Title` → `Name`, `Question`, `Why it matters`, `Possible approaches`, `Dependencies`, `Source`, `Date`, `Status`. Any other field (`**Resolves**`, `**Open**`, `**Note**`, `**Midpoint update, 2026-08-16**`), a repeat of a mapped label, and text before the first field stay in `_layout` (below). A row may hold a `Date` the entry never showed (a question’s creation date) or a `Name` derived from its Summary or Question when it had no `Topic` or `Title`; both are recorded in `_derived`, so neither renders.
- **Status.** `Status` ← the state the status text names (`open`, `resolved`, `invalidated`; the closest for any other wording, `half-resolved` → `open`), read through any emphasis at the start of the text, also when the emphasis holds more than the word (`**Status**: **resolved** (D-051) …` and `**Status**: **Resolved (D-029) — Tommy drops it.**` are both `resolved`, the second with its resolution prose inside the bold), `Resolved By` ← the row of its first `D-###` when resolved, `Resolution` ← the prose after the status word and its parenthetical (`midpoint candidate identified, act climax undecided`, with any paragraphs under it), or an invalidation’s reason. When the cited `D-###` has no row in the project (an entry citing a decision that was never logged), `Resolved By` stays empty and the canonical form is `resolved`; `_as_written.Status` keeps the number as written. The canonical form the properties render is `open`, `resolved (D-<n>)` or `invalidated (<Resolution>)`, the first two followed by ` — <Resolution>` when it is set, so the prose renders for every status.
- **`Meta` on a log row** is in `Meta`’s storage form (§ Frontmatter ↔ properties: literal text, each `_` key on one line as JSON) and holds, each only when needed: `_as_written` with **one entry per header part**, `date`, `type`, `priority`, `category`, each `{"stored": "<the property value>", "value": "<the source’s text for that part>"}` (a remapped type or category, a case change: `"category": {"stored": "Story Structure", "value": "structure"}`), plus `"suffix": {"value": "<text after the last part>"}` (` ✅ RESOLVED`; on a question it also records `"stored": "<Status>"` and covers `Status`, so it drops once the question is reopened), and `"Status": {"stored": "<the canonical status>", "value": "<the source’s status text>"}` (`stored` is the canonical status without its ` — <Resolution>` tail: `open`, `resolved (D-<n>)` or `invalidated`, so it covers `Status` and `Resolved By`, and an edit to `Resolution` alone reaches the rendering through `⟦Resolution⟧`) (`**resolved (D-029)** — Tommy. …`, `✅ resolved 2026-08-17 (D-068). …`), with the Resolution prose replaced by `⟦Resolution⟧` where it matches the property, so `Meta` doesn’t carry the prose twice (*observed (2026-10-17)*: 2.2k characters repeated); `_derived`; and `_layout`, the entry below its header verbatim with each mapped field’s first occurrence replaced by a line holding `⟦<Property>⟧` (followed by its tail for `Supersedes`), stored as one double-quoted string with `\n` for each line break (a row stored in the earlier form holds a `|2-` literal block, which read still accepts), written whenever the entry isn’t the default rendering below (another field order, an extra field, no blank line after the header).
- **Rendering.** The header is `## D-<Number> · <Date> · <Type>` or `## Q-<Number> · <Priority> · <Category>`, each part taken from its `_as_written` entry while that entry’s property still holds `stored`, else from the property, then the `suffix` while it applies. Parts are independent: changing only `Priority` in Notion keeps the source’s `structure` and its ` ✅ RESOLVED`. Then `_layout`, each `⟦<Property>⟧` line replaced by its field: `**<Label>**: <value>` (the label alone on its line when the value starts with a newline or a list item; a list value gets exactly one empty line before it and, when another field follows, exactly one after it, the profile’s form for a list under a field label), `Integrated` verbatim, `**Superseded by**: D-<n>` from the `Superseded By` row followed by the placeholder line’s tail, `**Status**:` with `_as_written.Status`’s `value` while its `stored` still matches the row (`Status`, and `Resolved By` for `resolved (D-<n>)`), else the canonical status. A placeholder whose property is empty renders the bare label (`**Dependencies**:`), so a field the source left empty survives; a field the default layout would show drops when its property is empty; a property set since, which `_layout` doesn’t name, goes after the field before it in the default order; a property in `_derived` renders only once it differs from the recorded value. With no `_layout`, the default: the header, a blank line, then decisions `**Scope**` and `**Affects books**` (series only), `**Topic**`, `**Summary**`, `**Details**`, `**Affects**`, `**Source**`, `Integrated`, `**Superseded by**`; questions `**Scope**`, `**Affects books**` (series), `**Title**`, `**Question**`, `**Why it matters**`, `**Possible approaches**` (a list value set off as above, per `file-schemas.md` § The old layout; a value typed in Notion as bare lines renders one `- ` item per line), `**Dependencies**`, `**Source**`, `**Date**` (only when the source entry had one or it was set in Notion since: a `Date` in `_derived` is the row’s creation date and doesn’t render), `**Status**`; empty fields omitted. Entries are separated by one blank line (a longer gap in the source collapses to one); the page bodies of these rows are not rendered.

**The upgrade on this binding.** `migrate`’s layout upgrade reads the two logs (the unconverted rows) and `state.md` in the old rendering, plus every converted entry at its path, then converts the project in place, under its approved plan. It **resumes** by the same reading: a run that stopped partway finds its converted rows as entries, skips them, and converts only the rows still in the logs.

1. **Schema:** § Schema upgrades (the Journal, `Layout`, `Retracted`) before anything else.
2. **Entries:** each entry still in the logs is written to its path (`decisions/D-018.md`) with a plain `write`. While `Layout` is empty, that write alone reaches the unconverted row holding the entry’s `Number`, and replaces it in place: content = the entry’s body, properties from its frontmatter, every old-layout field property `null`, and `Meta` rewritten in the current form with `_entry: 2`, `_words` (§ Frontmatter ↔ properties) and no `_layout` or header-part overrides (§ Frontmatter ↔ properties, Entries). Its concurrency guard compares that row’s rendered log entry with the same entry in the baseline log read. A row already holding `_entry` is never converted again: the conversion refuses it by name, so no old rendering ever rewrites a converted row’s body. A converted row is an entry, so one that is damaged (half-written, or failing its fidelity check) is repaired as any entry is: an ordinary `write` at its path of the entry composed from the old text, never a second conversion. Links (`Supersedes`, `Resolved By`) are set once every row is converted (Entries, Links: a multi-row import).
3. **Journal:** the entries the upgrade composes, as `new` writes (the upgrade’s own entry, on a resume, extended rather than created again).
4. **Verify the entries, before `Layout`:** converted rows read at their entry paths in any layout, so the entries are verified here: each collection’s count against its baseline (the old logs’ headings as the first run read them, which on a resumed run is the headings of the log as it renders now plus the rows already converted, since a converted row leaves the log), every entry read back and matching what was written, and no Decisions or Questions row of the project left without `_entry`. A failure stops the run here, in the old layout.
5. **`state.md`:** the layout-2 write (§ Stored and computed), whose one `replace_content` drops the H1 and every section outside the four.
6. **Last, `layout: 2`** in the config sets `Layout`, only once step 4 has passed; it switches every rendering to layout 2. The two indexes, computed, are checked after it (each lists every ID once).

**Re-entering the upgrade.** A project whose `Layout` is 2 but which still has a Decisions or Questions row without `_entry` (an old state repaired by hand, or restored from history) may enter the upgrade again: those rows are unconverted log rows whatever `Layout` says (§ Frontmatter ↔ properties, `_entry`), and the upgrade converts them as above.

Nothing is snapshotted (`history: native`). Every converted row keeps its prior properties and content in its own version history, and the Projects row keeps the Heads, which the upgrade leaves in place and layout 2 never renders. The two logs as rendered wholes have no history of their own, so they survive the upgrade only row by row.

## `checkpoint`

`history: native`, so `checkpoint` refuses with exactly: “Nothing to checkpoint: this project lives in Notion, which keeps every page’s version history itself (open any page, then ••• → Version history). No snapshot was written.”

## Worked example: `decisions` logs a decision

1. **Resolve** once: `kind: notion`, root = the project row’s id, layout 2 (the row’s `Layout`); the hub fetch gave the six data-source URLs.
2. **Number.** `store.read('decisions/_index.md')`: one rows query of the project’s Decisions, rendered with no fetch. The highest is `D-068`, so the skill proposes `D-069`, and `D-069` supersedes `D-041`.
3. **Create** with `new`: the selector query (`Number` = 69) finds no row, so `notion-create-pages` into Decisions with `Name` = the topic, `Number` 69, `Type`, `Date`, `Source`, `Integrated` `no` and `Project`, all literal text where they are text (§ Rendering, Property text), and `content` = the body in write form; wait on the async task. The selector query again finds one row, so the report is `D-069`.
4. **Supersession.** `store.edit('decisions/D-041.md', …)` adds `superseded_by: D-069`: re-fetch `D-041` for the guard, then one `update_properties` on `D-069`’s row adding `D-041` to its `Supersedes` (§ Frontmatter ↔ properties, Entries).
5. **Index:** computed, so the skill’s row upkeep is skipped.
6. **Journal.** `store.edit` of the session’s `journal/2026-10-25-s12.md`: re-fetch it for the guard, `update_content` appending the paragraph, `update_properties` adding `D-069` to `Decisions`.
7. **`state.md`:** What Exists’ count is computed, so only Last Session changes: re-fetch the Projects row for the guard, then one `replace_content` of its four short sections and child-page tags.
8. **Cost:** 11 calls plus async polls: the index query (1), the selector query before and after the create and the create itself (3), `D-041`’s guard fetch and the update on `D-069` (2), the journal’s fetch, `update_content` and `update_properties` (3), and the Projects row’s fetch and `replace_content` (2); one more when `D-041`’s `Meta` holds a `_keys` that must now list `superseded_by`. No call carries more than the Projects row with its relation lists; the old layout’s guard fetched that row with a 36 KB `## Previous Session` in it.

## Adversarial case: `blueprint` gathers every character in chapter 12

1. `store.read('chapters/chapter-12/ch12-outline.md')`: rows query Chapters with `Project` `relation_contains` root, `Book` (`is_empty`, or the book row in a series), `Chapter` `number_equals` 12, `Artifact` `enum_is` outline, then fetch. The row’s `Related Assets` holds the URLs of the Assets rows the outline names.
2. `store.list('characters/*.md')`: rows query Assets with `Project`, `Book` `is_empty` and `Kind` `enum_is` character, which returns `Name`, `Slug`, `Type` and the URL of each.
3. The characters whose URLs are in chapter 12’s `Related Assets` are the indexed set. `blueprint` still reads the outline body (and chapter 11’s notes End State) and adds any named character the index missed, since the index lags edits made in Notion. Each becomes `characters/<Slug>.md` and is read with `store.read`. Worldbuilding works the same way with `Kind` = worldbuilding and paths from `Category` and `Slug`.

## Adversarial case: two sessions log `D-069` at once

1. Sessions A and B each list `D-068` as the highest and propose `D-069`. Both selector queries find no row; both create.
2. Both run the selector query again and see two rows holding 69. B’s page id sorts later, so B renumbers its row: the highest is 69, so `Number` = 70, and the check runs again and finds one row. A’s row is untouched.
3. B rewrites the proposed ID wherever its same submission cited it (here, nothing else yet) and reports `D-070 (proposed D-069)`; its journal entry, its prose and any `resolved_by` use `D-070`. A reports `D-069`.
4. Had both also created `journal/2026-10-25-s12.md`, the same comparison would make one of them the loser: that session withdraws its own row (retitled `2026-10-25-s12 (duplicate, withdrawn)`, its `Project` cleared, its URL in the report for the author to delete), its `new` write fails, and the skill takes `s13`.
