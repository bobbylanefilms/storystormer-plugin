# Dropbox Binding

The store is a folder in the author’s Dropbox, reached through the Dropbox connector. The tree is the local tree, file for file and byte for byte, so the same folder synced to a machine is also a valid local project. Read `references/store.md` first; this document only says how each operation is realized here.

## Capabilities

```
identity: path · write: delete-create · edit: read-modify-write · list: folder-walk · history: snapshots · open: url · size: 5 MiB / 5 MB · confirm: batch
```

## Tools

The Dropbox connector’s `list_folder`, `fetch`, `create_file`, `create_folder`, `delete`, `move` and `check_job_status`. Resolution’s tool check passes when all seven are present. Two more are **optional**, used when present, and each falls back on its own: without `copy` (a server-side copy, which realizes snapshots, § Snapshots), snapshots are read-then-write; without `get_file_metadata` (the cheaper concurrency check, § Write step 2), the guard is the full re-read. Either can be present without the other, and neither’s absence fails anything. The connector’s `search` is not used (§ Locate lists `/StoryStormer/` and reads each project directly).

**Verified on:** 2026-10-16.

## Root

`/StoryStormer/<project-slug>/`, named by the config’s `storage.root` (`"/StoryStormer/<slug>"`). A contract path joins onto it: `treatment.md` is `/StoryStormer/<slug>/treatment.md`. Call the connector with that joined path (an fq_path); show the author `path_display`. Where a response carries only `path` (an ns_path, `ns:<id>//…`), pass it on exactly as returned and never strip the prefix to build a call.

When `storage.local_root` names a folder that exists on this machine, resolution picks the local binding instead (`store.md` § Resolve); nothing here applies.

**A synced copy the config doesn’t name.** When a session binds here and the config has no `local_root`, check through the local binding whether `<Dropbox sync root>/StoryStormer/<slug>/.storystormer/config.json` exists on this machine (the sync root is the Dropbox folder itself, `~/Dropbox` or `~/Library/CloudStorage/Dropbox`; a host whose folder connection can’t reach that path skips the check). If it does, and it matches the config this binding read (the copy is in sync), say so in the first response: the project is synced to this machine, and adding `local_root` would let sessions work on that folder directly, much faster than through the connector. Offer to add it; it is a config write and needs the author’s yes. On a yes, add `"local_root": "<that folder’s absolute path>"` to the stored config’s `storage` block (the synced folder’s config is the same file). When the session was opened on a separate folder holding a pointer to this project, resolution reads that pointer, not the stored config, so add the same `local_root` to the pointer too (it names the synced copy of the block’s own Dropbox root, the one `local_root` a pointer may carry, `store.md` § Resolve). Then resolve again, which binds the local binding rooted at the synced folder.

## Stored and computed

Everything is **stored** as a real file; nothing is computed. That includes the snapshot folders (`history: snapshots`), `characters/_index.md`, `decisions/_index.md`, `questions/_index.md`, `outline/_index.md`, `voice/README.md` and `.storystormer/config.json`, which reads `{"layout": 2, "storage": {"kind": "dropbox", "root": "/StoryStormer/<slug>"}}`, plus `local_root` in the `storage` block when the author syncs the folder to a machine. Every clause in `store.md` § Local-mode clauses that says “stored” applies.

**The entry indexes** are kept one row at a time (`file-schemas.md` § Who rebuilds an index), and here a row costs one read and one rewrite of a small file: the `edit`’s `fetch` of the index (about 9 KB for 115 decisions) is its baseline, its guard and its prior content all at once, indexes take no snapshot, and the rewrite is § Write’s delete and create, so about four calls (fetch, delete, poll, create) and 20 s. **The window:** the guard can’t cover the gap between that fetch and the delete-and-create, so another session editing the same index inside it loses its row. Nothing here detects that at write time; the next listing’s ID check (`file-schemas.md`, the same section) finds the missing row and rebuilds the index, so the loss is repaired, never permanent.

## Operations

| Operation | Realization |
|---|---|
| `list(glob)` | **A glob inside one folder** (`decisions/*.md`, `journal/*.md`, `questions/Q-*.md`): one `list_folder` on that folder with `recursive: false`, following `cursor` until `has_more` is `false`; keep the `file` entries; each one’s contract path is its `path_display` (present in this mode) with the leading `/StoryStormer/<slug>/` removed, compared case-insensitively, or, where `path_display` is absent or empty, its `path` stripped as for a recursive walk below. A not-found error is an empty listing. This is the listing a new entry’s number comes from, so it never walks the tree. **Any other glob:** one `list_folder` on the root with `recursive: true` and `max_results: 600`, then `list_folder` with only `cursor` until `has_more` is `false`. Pages may hold zero entries while `has_more` is `true`; keep going. Paginate to the end without asking (the walk is one operation, not a browse). Keep entries whose `object_type` is `file`; folders and mounts are not documents. Each entry’s `path` is an ns_path and its `path_display` is absent or empty in recursive mode, so: drop `ns:<id>//`, then drop the leading segments that match the root (`StoryStormer/<slug>`, compared case-insensitively); the rest is the contract path, in the casing Dropbox returns. Match the glob case-insensitively |
| `read(path)` | `fetch` with the joined path. `text` is the document plus **one extra trailing newline** that the connector’s extraction appends (the stored bytes are exact); normalize the end to exactly one newline (`store.md` § Operations, the final newline): strip every trailing `\n`, then add one, and return that, saying how many the stored file ended in (the fetch’s count less the connector’s one) when a caller checks sizes (`migrate`’s § Verify). `.json` reads the same way. An error saying the file could not be found is the contract’s missing-path error; any other error (failed extraction) is an error too, never an empty document. **A large result:** a fetch of about 65 KB or more may not come back inline (the host saves the result to a file instead, *observed (2026-10-25)* at 65 KB, 71 KB and 100 KB); the content is then read from that saved result, as stored there, and never retyped from a preview or from memory. *Frontmatter only:* no partial read; `fetch` whole and keep the frontmatter block |
| `write(path, content)` | Follow § Write, step by step. In short: full prior read, guard, no-op check, size check, then create (absent path) or delete-then-create (existing path) with the recovery below |
| `write(path, content, new)` | `create_file` with the joined path, and nothing else: a `new` write never deletes, snapshots or runs the guard. `ALREADY_EXISTS` on the first try is the contract’s failure (the path exists; *observed (2026-10-25)*: a second `create_file` of an existing path answered `ALREADY_EXISTS` and left the first file’s content, and so did a different-case path, `d-001.md` against `D-001.md`); nothing was written. `PARENT_NOT_FOUND` → `create_folder` each missing level as in § Write step 4, then `create_file` again (*observed (2026-10-25)*, a first entry into a collection folder that didn’t exist yet). A transient error (rate limit, internal error) → retry once after about a second. **An unknown outcome** is an `ALREADY_EXISTS` that follows any earlier attempt of this call (a transient error, a `create_folder` round), or a retry that fails transiently too: `fetch` the path. Content equal to this call’s (§ Operations, `read`, the final newline) means the create landed; other content is the failure; not found after two transient errors means nothing landed, so report it and hold the content. **A numbered entry** (`decisions/D-###.md`, `questions/Q-###.md`): on the failure, take the next number, put it in the path, the `id` and every citation of the proposed number inside the content, and `create_file` again; after five numbers in a row are taken, stop and report the numbers tried rather than climb further. Report the number used and, when it moved, both (`store.md` § New entries). A journal entry’s failure goes back to the skill, which picks the next session number |
| `edit(path, edits, reason)` | `read(path)`. That read is the guard’s re-read: if it differs from the baseline (its `version`, or its whole content when it has none), stop per the guard. Apply the edits in order in the model under the contract’s grammar; a missing or ambiguous anchor fails the whole call with nothing written. Then `write` the result (its guard is already satisfied by this read). `reason` is not recorded; the snapshot is the history |
| `history(path)` | Book-level documents: `list('.storystormer/history/**')` and keep the paths that are exactly `.storystormer/history/<one folder>/<path>`, compared case-insensitively (each snapshot folder keeps root-relative paths, so `books/book-2/treatment.md` matches only book 2’s, and `treatment.md` never matches a book’s or a nested archive’s copy). Chapter artifacts: `list('<chapter folder>/.history/*')` filtered, case-insensitively, to `ch<NN>-<stage>-v*.md`. Return them newest first. Older versions may also sit in Dropbox’s own version history or Deleted files, which no connector tool reads; point the author to <https://help.dropbox.com/delete-restore/recover-older-versions> if they need something the snapshots lack |
| `open(path)` | Give the author the `url` from a `fetch` of the path, taken **after** the last write: `create_file` returns no url, and a delete-create makes a new file with a new url. The url is the owner’s Dropbox link; `fetch` creates no shared link, and `open` never calls a sharing tool |
| `move(from, to)` | `move` with `[{source_path, destination_path}]`, then `check_job_status` as for `delete`. Missing destination folders are created by the move. An existing destination fails the entry (`to/conflict`): don’t pass `autorename`; stop and report both paths |
| `delete(path)` | `delete` with one path, then `check_job_status` until `completed`; report the entry’s result. The file goes to Dropbox’s Deleted files, recoverable for the account’s retention period, never wiped |

## Write

1. **Prior content, in full.** Overwriting needs the whole current document in hand, since it is the rollback: the baseline read once the guard (step 2) has confirmed the path unchanged since it, a read-then-write snapshot’s read, an `edit`’s read, any read of the path taken since this run’s last write to it (a post-write verify counts; no second read is needed), the content this run itself last wrote there, or `read(path)` now. A frontmatter-only read is never the prior content. A missing path means this is a create, with no prior content. The existence read may be skipped when the path is absent from a `list` taken in this run or its parent folder was created in this run; `create_file`’s `ALREADY_EXISTS` still guards it.
2. **Guard, then no-op.** On an existing path, run the concurrency guard (`store.md`); on a mismatch, stop with nothing written. **The equivalent check** (`store.md` § Concurrency guard), when `get_file_metadata` is present: record a stamp at the baseline: the `rev` whenever any response for the baseline carries one (`get_file_metadata` always does; `fetch`’s `metadata` sometimes does, so look), else the `server_modified` in the baseline `fetch`’s `metadata`, or, when the baseline is this run’s own write of the path, the `modified_time` and `file_id` that `create_file` returned. Before the overwrite, `get_file_metadata` the path and compare: `rev` with `rev` when the stamp has one (preferred; it changes on every revision), otherwise `server_modified` (and `id` where the stamp holds it). A `server_modified`-only stamp is weaker: it has one-second resolution and is the server’s time, so it misses a change made within the same second as the baseline revision; use it only when no `rev` is to be had. Equal → unchanged, and the baseline is the prior content (step 1). Different, missing, or an error → `read(path)` in full and run the guard as written. Only then compare: content identical to the prior content → no call.
3. **Size, before anything is removed.** The new content must fit `create_file`’s 5 MB, and so must the prior content (it is the rollback). If either doesn’t, stop and report it; never delete a document that couldn’t be written back.
4. **Absent path:** `create_file`. On `PARENT_NOT_FOUND`, `create_folder` each missing level from the highest down (one level per call; `ALREADY_EXISTS` on a folder means it is there, carry on), then `create_file` again.
5. **Existing path:** `delete` with `[{source_path}]`, one path per call (never batch its delete with another write’s, so two documents are never absent at once), except for the kinds § Batched rewrites names, below; it answers `in_progress` with an `operation_id`, so call `check_job_status` with that id and `wait_ms: 5000` until `completed`. The normal case is one poll: the first `check_job_status` returns `completed` (every one of 50 consecutive overwrites in the 2026-10-17 live test, and every write in the skill loops), so an overwrite costs about four calls (delete, poll, create, and a verify `fetch` when the run takes one), about 20 s. Entry `failed` → stop: nothing changed; report it. Entry `success` → `create_file` the new content. If polling itself errors or times out, poll again; if it still can’t answer, `fetch` the path: present means the delete hasn’t happened (stop, nothing changed), missing means it has (go on to the create).
6. **Retry the create once** after about a second on `ALREADY_EXISTS` (the delete not yet landed) or on a transient error (rate limit, internal error). This retry belongs to an overwrite only. A `new` write never retries `ALREADY_EXISTS` (§ Operations), since there it means another session holds the path: retrying would race two sessions’ `D-069`s through the gap this step allows.
7. **Recovery** if the create still fails:
   - **A create with no prior content:** nothing was removed; report the failure and hold the content in the conversation.
   - **An overwrite:** `create_file` the prior content at the path. If that create (or the retried new one) answers `ALREADY_EXISTS`, something now occupies the path (a lost response, another device): `fetch` it and report which content is there instead of assuming either.
   - **Both creates fail** (the connector is down): wait and retry the restore once more. If the path is still absent, that is the one case this call ends with it absent: say so plainly, say the prior version is in the snapshot (when the document has one) and in Dropbox’s Deleted files, hold the new content in the conversation, and stop the run before any further writes.

**Batched rewrites.** Only these kinds may batch their deletes: entries (`decisions/D-###.md`, `questions/Q-###.md`), the two indexes (`decisions/_index.md`, `questions/_index.md`) and journal entries (`journal/*.md`), each a few KB. Every other document, `state.md` included, takes step 5’s one delete per call. A skill that rewrites several documents of these kinds in one step may batch their deletes, which cuts the overwrite from about four calls a document to about two (*observed (2026-10-25)*: eight rewrites in `treatment-update` took 12 write calls instead of 32). The conditions, all of them, before the batch’s `delete`:

- **Every prior content is in hand** (step 1) for every path in the batch, since each one is that document’s rollback.
- **The guard has passed for each** (step 2), and the no-op check dropped any whose content is unchanged. For paths in one folder, one `list_folder` of that folder with `recursive: false` can stand in for each path’s `get_file_metadata`: its file entries carry each file’s `rev` and `server_modified` (*observed (2026-10-25)*: one listing stamped eight decision entries).
- **Each fits** (step 3).
- **Every path is one of those kinds.** Any other document keeps its own delete, as above.

Then one `delete` with an entry per path, and `check_job_status` until `completed`; read each entry’s result. An entry `failed` means that document is unchanged: leave it out of the creates and report it as not written. Then `create_file` each document whose entry succeeded, one at a time, with step 6’s retry. A create that still answers `ALREADY_EXISTS` after that retry means something now occupies the path (a lost response, another device): `fetch` it and compare, as in step 7, and report which content is there (this call’s, the prior, or another); it is never silently left out, and it counts as a failed create for the rollback. **A create that still fails partway** (rollback): stop creating new content; `create_file` the prior content at every path of the batch that is still absent, the failed one included unless the fetch found it occupied, so the batch ends with every path present; the documents already created keep their new content, since each is a whole document. Report which documents landed new and which were restored. A restore that fails too follows step 7’s last case for that path, and the run stops before any further writes. Snapshots, where the skill takes one, are written before the batch’s delete, as for a single overwrite.

## Snapshots

`history: snapshots`, so every snapshot `store.md` calls for is written here as files before the overwrite begins and **after** the concurrency guard has passed (a newer version is never snapshotted as the one being replaced). A snapshot path should be new: if the timestamped folder already exists (two runs in one minute), append `-2`, `-3`, … to its name rather than write into it, and on a retry of the same run reuse its own folder only for files whose content already matches.

- **By `copy`** (the contract’s `copy` realization), when the connector offers it: one `copy` call with an entry per document of the set (`source_path` the document, `destination_path` its snapshot path, no `autorename`), then `check_job_status` with `wait_ms: 5000` until `completed`, and check every entry is `success`. The connector copies the current revision (it takes paths, not revisions), which can be newer than the guarded baseline if something wrote in between, so **after the copy, run the guard again** on each source: the stamp check with `get_file_metadata` (§ Write step 2), also checking each copy’s `size` against the source’s, or, without that tool, the full re-read (which the overwrite needs anyway; run it after the copy rather than before). Any mismatch means the snapshot may hold a newer version: stop per the guard (show the author both, write nothing more) and say the snapshot folder holds that copy. Dropbox copies the stored bytes exactly and creates missing destination folders itself (*observed* 2026-10-17: three missing levels in one call), so the content never passes through the model and no `create_folder` is needed. Check that a new timestamped folder really is new first (`get_file_metadata` on it answers not found, or the parent’s `list_folder` lacks it). An entry failing `to/conflict` means its snapshot path is taken (handle it as above); any other failed entry falls back to read-then-write for that document.
- **By read then write**, without `copy`: `read` each document, then create it at its snapshot path. A new timestamped folder never exists yet, so `create_folder` it first (and `.storystormer/history/` or the chapter’s `.history/` when absent; `ALREADY_EXISTS` means it is there) rather than meeting `PARENT_NOT_FOUND` on the first create.

Where snapshots go and how they are named is defined once in `references/file-schemas.md`: § `.storystormer/history/` (book-level documents, one timestamped folder per operation, files that change together snapshotted as a set) and § `chapters/` folder → Per-chapter history (chapter artifacts, flat version-and-date-named files in the chapter’s `.history/`).

## Confirmation

The connector’s tool descriptions ask the model to summarize each create, copy, delete and move and get explicit confirmation before calling it. Here **the plan-first approval (`references/plan-first.md`) is that confirmation** for every mutation in the run, snapshot copies and files and the delete half of each overwrite included; don’t re-ask per file or per call. Work outside the approved plan still needs its own approval.

The descriptions also ask, after each mutation, for a note on how to revert it. Give it once per run, in the report, not per file: name the snapshot folder (or chapter `.history/` files) that holds what was replaced, and say that replaced and deleted files are also in Dropbox’s Deleted files (<https://help.dropbox.com/delete-restore/recover-deleted-files-folders>). For files the run created, say they can be deleted; for moves, name the original paths they can go back to.

## Locate

The well-known root is `/StoryStormer/`; each child folder holding `.storystormer/config.json` is a project.

1. **List** `/StoryStormer/` with `list_folder` and `recursive: false` passed explicitly (the connector recurses when the argument is left out: *observed (2026-10-24)*, a Locate that omitted it walked every project’s tree), following `cursor` until `has_more` is `false`, and keep the entries whose `object_type` is `folder`. Each child’s name is the last segment of its `path_display`, or of its `path` when that is absent (never the whole value, which already includes `/StoryStormer/`). A not-found error means no projects here, which is not a failure.
2. **Config:** `fetch` `/StoryStormer/<child>/.storystormer/config.json`, remove the trailing newline, and parse it. Not found → not a project; skip it. **The pointer test** looks at the keys: a config whose only key is `storage` is a pointer, which isn’t a project here; skip it. One holding `layout` and `storage` is a layout-2 project; one holding `storage` and other keys but no `layout` (the mirrored `title`, `project_type`, …) is an old-layout project, listed like any other (resolution offers its upgrade, `store.md` § Resolve step 4). A config that doesn’t parse, or a fetch that errors → list the folder as unreadable, with the error. A config whose `storage.kind` is `local`, or that has no `storage` block, is a local project kept in this synced folder: list it as a synced local project (`store.md` § Resolve binds it here, through this binding).
3. **State:** `fetch` `/StoryStormer/<child>/state.md` and keep the frontmatter (§ Operations, `read`) and the `server_modified` in the response’s `metadata`. Missing or unreadable → list the project with its stage, last session and last-modified time unknown.

**Returns**, per project: title (`state.md`’s `title`; the config holds none, so with `state.md` unreadable the title is unknown and the slug stands in), slug (the folder name), root `/StoryStormer/<child>`, `stage`, `last_session`, last modified (`state.md`’s `server_modified`), a series’ `books`, and the config’s `local_root` when it has one (resolution checks it, `store.md` § Resolve). **Fails** when the listing itself errors. A child whose config or `state.md` can’t be read or parsed is reported against that child and marks this Locate **incomplete**, so the locator doesn’t auto-bind a lone project (`store.md` § Resolve). **Cost:** one `list_folder` (plus a page per `cursor`) and up to two `fetch`es per child folder, so about 21 calls for ten projects.

## Scaffolding a project (`init` on Dropbox)

1. **Slug check.** List `/StoryStormer/` as § Locate step 1 does (the raw folder listing, not Locate’s project list) and look for a child named the slug, compared case-insensitively. None → go on. One that holds `.storystormer/config.json` (§ Locate step 2’s read) is a project: stop and ask the author for another slug or whether they meant that project. One without a config is someone’s folder: ask before writing into it.
2. **Folders.** `create_folder` `/StoryStormer/` (when the listing found none; `ALREADY_EXISTS` means it is there), then `/StoryStormer/<slug>/`. `ALREADY_EXISTS` on the slug folder means it appeared since the check (another session): run step 1 again before writing anything.
3. **Project.** Continue `init` through the contract, in `file-schemas.md`’s order for `init` (§ `journal/`): the stored config `{"layout": 2, "storage": {"kind": "dropbox", "root": "/StoryStormer/<slug>"}}`, the two header-only indexes, `journal/<date>-s01.md`, the rest, and `state.md` last (its `slug` is the folder name). Intake keeps this binding’s text-only rule (§ Quirks).
4. **Pointer.** With an open folder that is not this root’s synced copy, `init` writes the pointer there (`storystormer-init` § Where a new project lives).

## Quirks

- **Case-insensitive paths:** `TREATMENT.md` and `treatment.md` are the same file, and a folder’s stored casing wins (writing `characters/x.md` into an existing `Characters/` lands there). Create folders in the contract’s casing; return what Dropbox returns.
- **Listed names are raw:** a path taken from a listing is used exactly as listed, byte for byte. An entity-like sequence in a filename (`The_Good_Dog_-_Brainstorming_&amp;_Future_Plot_Points.md`) is part of the name and is never decoded (*observed (2026-10-25)*: a fetch with `&` for `&amp;` answered not found).
- **NFC:** paths must be Unicode NFC; a decomposed form (`e` plus a combining accent) is rejected. Normalize a slug before joining it.
- **Size:** `fetch` reads up to 5 MiB; `create_file` writes up to 5 MB (`CONTENT_TOO_LARGE`), so a file between the two can be read but not written back (§ Write step 3). No story document comes near either; if one does, stop and report it rather than split it.
- **Async jobs:** `delete` and `move` answer `in_progress` even for one file, and per-entry failures appear only in `check_job_status`’s result. Never treat the first response as the outcome.
- **The trailing newline:** `fetch` adds one `\n` to every file it reads; `create_file` stores content byte for byte. Normalize the end on every read (§ Operations, `read`), or anchors, the no-op check and read-then-write snapshots drift by a line each round trip; the guard and the no-op check ignore a missing or extra final newline anyway (`store.md` § Operations). A `copy` snapshot never meets it.
- **Text only:** `create_file` writes UTF-8 text, so a binary file (a `.docx`, an image) can’t be stored; `init` leaves a binary intake original in the open folder and names it (`storystormer-init` § Prose Chapter Stashing). Text formats (`.txt`, `.fountain`, `.rtf`) store as they are.
- **New file, new id:** every overwrite deletes the file and creates another, so its `file_id` and `url` change. Never keep either across a write.

## Worked example: `treatment-update` replaces `treatment.md`

1. **Guard** against the baseline, the read the new treatment was prepared from: `get_file_metadata` `treatment.md` and compare its `rev` with the baseline’s (its `server_modified` when the baseline has no `rev`); if it differs (or there is no metadata tool), `fetch` it and compare its `version` with the baseline’s. If the document changed, stop and show the author both.
2. **Snapshot** (`file-schemas.md` § `.storystormer/history/`: the primer and treatment snapshot as a pair). Check `.storystormer/history/<timestamp>-treatment-update/` is new, then one `copy` with two entries (`primer.md` and `treatment.md` → that folder), `check_job_status` until both entries report `success`, and run step 1’s check again on `treatment.md` (with the copy’s `size`), so the snapshot is known to hold the guarded version. Without `copy`: `create_folder` the folder (and `.storystormer/history/` first if absent), `fetch` `primer.md` (and `treatment.md` unless step 1 just fetched it), and `create_file` each, unchanged, into it.
3. **Write.** `delete` `treatment.md`, `check_job_status` (normally `completed` on the first poll) until the entry reports `success`, then `create_file` the new `treatment.md`, whose frontmatter the skill has already set (`version` bumped). On `ALREADY_EXISTS` or a transient error, wait a second and retry once; if the create still fails, recover per § Write step 7 with the baseline content, which step 1 confirmed is what was there.
4. **No extra confirmation.** The plan-first approval covered the snapshot copy (or creates), the delete and the create. The report names the snapshot folder and Dropbox’s Deleted files as the way back, once.
5. **Open.** `fetch` `treatment.md` and give the author its `url`.

## Worked example: `decision-capture` logs a decision

1. **Number.** `list('decisions/*.md')`: one non-recursive `list_folder` of `decisions/`. The highest is `D-068`, so the skill proposes `D-069`.
2. **Create.** `create_file` `decisions/D-069.md`. Another session created `D-069` since that listing, so the answer is `ALREADY_EXISTS`: no retry, no fetch.
